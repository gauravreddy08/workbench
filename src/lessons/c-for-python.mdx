C is the old, plain programming language that most of the fast software you use is written in. Python itself is a C program. The parts of PyTorch that do the math, llama.cpp, and the code that runs on a GPU are C, or C's bigger sibling C++.

That matters because the answer to "why is this slow?" or "what does this function actually do?" usually lives in that code, not in the docs. If you can read it, you can check a speed claim yourself instead of taking it on trust, and you can follow a bug past the point where the Python stops.

You don't need to write C for this. You need to read it, the way you can read a recipe in a language you half-speak. You already know most of the ideas from Python and from [Where do my variables live?](/lessons/stack-and-heap/); this lesson gives them their C spelling. It is the key that opens [Why is NumPy 100x faster?](/lessons/cpu-caches/), [Why is Python slow?](/lessons/python-speed/) and [FlashAttention and kernels](/lessons/flash-attention/).

Five lines in, there are stars in strange places, a loop with nothing before the first semicolon, a line starting with `#`, and `x + i` where `x` is supposed to be a list of numbers. You close the tab and believe the issue.

C isn't hard. It's *unfamiliar* in about ten specific ways, and each maps onto something you already know from Python. By the end you'll read that function and judge the issue yourself. (It's right, sort of.)

<Origin year="1972" title="A language for a machine with bytes">

In 1969 Ken Thompson wrote the first Unix in assembly, then made a small language called B to write tools in. B had no types. Every value was one "word" of the machine, and the program just did arithmetic on words.

Then Bell Labs got a PDP-11. It addressed memory in single bytes, and it would soon have hardware for decimal (floating-point) numbers. A typeless language couldn't say "this is one byte of text" versus "this is a two-byte integer" versus "this is a floating-point number." Dennis Ritchie added exactly that: types, so the compiler knew how many bytes each value took and which machine instructions to use on it. He called the result C. By 1973 the Unix kernel itself was rewritten in C, which proved a high-level language could be fast enough for an operating system.

That is the "why" behind most of C's strangeness. C is a thin, honest layer over memory. Every rule you are about to meet exists because the compiler needs to know, ahead of time, exactly how many bytes things are and where they sit.

</Origin>

## The Idea

### Types: how many bytes is this?

In Python you write `x = 3` and never think about size. Python ints grow as large as you need: `2 ** 100` just works. That's a luxury, paid for with a full object on the heap for every number (you weighed them in [Where do my variables live?](/lessons/stack-and-heap/): 28 bytes for a small int).

C makes you say what kind of number you want, because that decides how many bytes it gets:

```c
char   c = 'A';     // 1 byte. A tiny integer; also how C stores text.
int    n = 42;      // 4 bytes. Whole numbers from about -2.1 billion to +2.1 billion.
long   big = 42;    // 8 bytes on Mac and Linux (only 4 on Windows!).
float  f = 0.5f;    // 4 bytes. Same as torch.float32.
double d = 0.5;     // 8 bytes. Same as a Python float, torch.float64.
```

Read `int n = 42;` as "make a 4-byte box called `n`, holding 42." The type comes first, then the name. The `;` ends the statement, like a newline does in Python.

The fixed size is a real limit. An `int` that goes past 2,147,483,647 doesn't grow; it breaks (Break It). When the exact width matters, as it does in a weight file, C has names that spell it out: `int32_t`, `int64_t`, `uint8_t` (u for unsigned: no negatives).

C will tell you the size of anything with <Term w="sizeof">A built-in that gives the size in bytes of a type or variable, worked out when the program is compiled. sizeof(double) is 8.</Term>. You'll fill in a table of these in Build It. Notice the link to your memory math: a 7B-parameter model in `float` is 7 billion × `sizeof(float)` = 28 GB. Same arithmetic.

### Compiling: translate once, run many times

Python reads your `.py` file every time you run it, turns it into <Term w="bytecode">A list of simple instructions for Python's own virtual machine, like LOAD_FAST and BINARY_OP. The real CPU can't run these; a program has to read and act on them one by one.</Term>, and then a big loop inside `python3` reads each bytecode instruction and does what it says. That loop is the <Term w="interpreter">A program that runs another program by reading its instructions one at a time and carrying each one out. CPython's interpreter is a C function with a giant switch statement in a loop.</Term>, and it's written in C.

C skips the middleman. A <Term w="compiler">A program that translates source code into the CPU's own instructions (machine code) once, ahead of time. cc, clang and gcc are C compilers; nvcc compiles CUDA.</Term> translates your file into the CPU's own instructions, once, and saves them as an <Term w="executable">A file of machine code the operating system can load and run directly, with no interpreter in between. On a Mac it's a Mach-O file; on Linux, ELF.</Term>:

```bash
cc -O2 sum.c -o sum    # translate sum.c into machine code, save it as ./sum
./sum                  # run it; no cc, no interpreter, just the CPU
```

`-O2` means "optimize": rearrange the code to be faster as long as the output is the same. `-O0` means "translate literally." The compiler takes "the output is the same" very seriously, which bites benchmarks (Break It).

The deeper reason compiled C is fast is the types again. When the compiler sees `total += x[i]` and knows both are `double`, it emits one floating-point add instruction. When Python sees `total += v`, it has to look up what `total` and `v` are *right now*, find the right add function, make a new float object for the result and update reference counts. [Why is Python slow?](/lessons/python-speed/) takes that apart in detail; you'll put a number on it in Measure.

### Boxes with addresses: `&` and `*`

Every variable in C is a box in memory, and every box has an <Term w="address">The number of the first byte of a box in memory. Memory is one long row of numbered bytes, so an address is just a big integer, usually printed in hex like 0x16fd0040.</Term>. You already saw this: `int n = 42;` is four bytes somewhere, holding 42.

Two operators let you talk about the box instead of what's in it:

- `&n` means **"the address of `n`."** Not the 42, but where the 42 lives.
- A <Term w="pointer">A variable whose value is an address. Its type says what kind of thing lives at that address, so C knows how many bytes to read there.</Term> is a variable that holds an address. You declare one with a star: `int *p = &n;` reads as "`p` is a pointer to an int, and it holds the address of `n`."
- `*p` (a star in front of an existing pointer) means **"go to that address and use what's there."** So `*p` is 42, and `*p = 7;` changes `n` to 7. This is called <Term w="dereferencing">Following a pointer to the box it points at, to read or write the value there. Written with a star in front: *p.</Term>.

The star doing two jobs is the single most confusing thing in C, so say it slowly. **In a declaration** (`int *p`), the star means "is a pointer." **In an expression** (`*p + 1`), the star means "follow it." The spacing doesn't matter: `int *p`, `int* p` and `int * p` are the same. llama.cpp writes `float * x`, CPython writes `PyObject *op`.

Why bother? Because C functions get **copies** of their arguments. If you want a function to change your variable, you hand it the address:

```c
void double_it(int *v) {   // v holds an address
    *v = *v * 2;           // go there, read, double, write back
}

int n = 21;
double_it(&n);             // pass where n lives; now n == 42
```

This "pass a pointer so the function can write into it" pattern is everywhere. When you see a function that returns `void` (nothing) but takes a pointer, the pointer is usually the output. Hold onto that; it's in the llama.cpp reading task.

### The bridge: a Python name is a pointer

Here is the sentence that makes CPython readable: **every Python variable is a C pointer to an object on the heap.**

When you write `x = [0.5, 1.5, 2.5]`, CPython builds a list object somewhere in memory and makes `x` hold its address. In CPython's C, the type of that address is `PyObject *`, "pointer to a Python object." Every function in CPython takes and returns `PyObject *`. `b = x` copies the address, not the list. `id(x)` in CPython is literally that address as an integer; `hex(id(x))` looks just like the `%p` output you'll print from C.

### Arrays: one block, and `p + 1` means "the next one"

A C array is a run of boxes of the same type, back to back with no gaps:

```c
int a[8] = {10, 20, 30, 40, 50, 60, 70, 80};   // 8 × 4 = 32 bytes, contiguous
```

`a[i]` reads element `i`, like Python. What's new is what the name `a` turns into when you use it: a pointer to the first element. And you can do arithmetic on pointers.

This is <Term w="pointer arithmetic">Adding a whole number to a pointer to move it along an array. p + 1 moves one element forward, which is sizeof(element) bytes, not one byte.</Term>, and it has one rule: **`p + 1` means "the next element," not "the next byte."** If `p` points at an `int`, `p + 1` is 4 bytes further on. If it points at a `double`, 8 bytes. C multiplies by the element size for you, which is why the pointer needs a type.

So `a[i]` is just shorthand. It's defined as `*(a + i)`: start at the beginning, step `i` elements forward, read what's there. Move the slider:

Notice what's *not* in the array: its length. A C array doesn't know how long it is. That's why C functions that take arrays almost always take the length too, like `ggml_vec_add_f32(const int n, ...)`. When you see `(int n, float *x)` read it as "a list of `n` floats, starting here."

### Tensors: a data pointer plus a rule

Now the payoff for ML. A NumPy array or a PyTorch tensor is, underneath, a C array plus a small description of how to read it:

- a **data pointer**: the address of the first number,
- a **dtype**: how many bytes each number is (`float32` = 4),
- a **shape**: `(3, 4)`,
- <Term w="strides">For each dimension, how many elements to skip in memory to move one step along it. PyTorch's t.stride() counts in elements; NumPy's .strides counts in bytes.</Term>: for each dimension, how far to jump to take one step.

Element `[i, j]` lives at `data + offset + i * stride[0] + j * stride[1]`. That's pointer arithmetic, done once per dimension. The memory is always one flat row; the shape and strides are a lens on top.

Here's the trick that makes PyTorch fast and occasionally confusing: transposing, slicing with steps, and many reshapes don't move any numbers. They make a new lens (new shape, strides and offset) over the same block. Try each view:

This explains an error you've probably hit: `t.T.view(-1)` fails, because flattening without a copy needs a <Term w="contiguous">A tensor whose elements sit in memory in exactly the order you'd read them, row by row, with no gaps. Many fast kernels require it; .contiguous() makes a copy that is.</Term> layout, and `.T` isn't one. `.contiguous()` fixes it by copying. And a CUDA kernel that receives "a tensor" receives, in C terms, a `float *` plus these numbers. That's all a kernel ever gets.

### Structs: named fields at fixed places

A Python class bundles named attributes. A C <Term w="struct">A bundle of named fields stored together in one block of memory, each at a fixed distance from the start. Like a Python class with only attributes, no methods, and a fixed layout.</Term> does the same with less magic:

```c
struct point { float x; float y; };    // 8 bytes: x at +0, y at +4

struct point pt = {1.0f, 2.0f};
pt.x = 3.0f;                           // field of a struct: dot, like Python

struct point *pp = &pt;
pp->x = 4.0f;                          // field through a pointer: arrow
```

The arrow `->` is the one new symbol. `pp->x` is shorthand for `(*pp).x`: follow the pointer, then take the field. Because almost everything in CPython and PyTorch is passed around by pointer, you'll see `->` far more than `.`.

Each field sits at a fixed <Term w="offset">How many bytes from the start of a struct a field begins. The compiler decides it from the field types, sometimes adding padding so fields line up on multiples of their size.</Term> from the start, decided by the compiler. Reading `pp->y` compiles to "load 4 bytes from the address in `pp`, plus 4." No dictionary lookup, no search: one instruction.

Now the real thing. Every Python object begins with the same two fields. In CPython's `Include/object.h`, simplified:

```c
// simplified from CPython, Include/object.h (the real one wraps the
// refcount in a union and has a different layout for free-threaded builds)
typedef struct {
    Py_ssize_t    ob_refcnt;   // how many pointers point at me
    PyTypeObject *ob_type;     // pointer to my type: float, list, ...
} PyObject;
```

And here is the actual definition of a Python list, from CPython's `Include/cpython/listobject.h` (comments trimmed):

```c
typedef struct {
    PyObject_VAR_HEAD
    /* Vector of pointers to list elements.  list[0] is ob_item[0], etc. */
    PyObject **ob_item;
    Py_ssize_t allocated;
} PyListObject;
```

`PyObject_VAR_HEAD` is a <Term w="macro">A find-and-replace rule the C preprocessor applies before compiling. #define NAME text makes every later NAME become text.</Term> that expands to `PyVarObject ob_base;`: a struct holding the refcount, the type pointer and `ob_size` (the length). `Py_ssize_t` is just "a signed 8-byte integer" on your machines. `PyObject **ob_item` has two stars: a pointer to the first of several `PyObject *`. ### Who frees the memory?

In [Where do my variables live?](/lessons/stack-and-heap/) you met the heap. In C you manage it by hand, with two functions:

```c
double *x = malloc(n * sizeof(double));   // ask for n*8 bytes; get the address
if (x == NULL) { /* out of memory */ }     // malloc returns NULL on failure
// ... use x[0] .. x[n-1] ...
free(x);                                   // give it back. Exactly once.
```

`malloc` returns a pointer to fresh, uninitialized bytes, and nobody tracks who's still using them. Forget `free` and you have a <Term w="memory leak">Memory a program asked for and never gave back. The process grows until it's killed or exits.</Term>. `free` and keep using the pointer, or `free` twice, and the crash shows up later, somewhere unrelated. So the real question in any C codebase is **ownership**: whose job is it to call `free`?

Python answers it with the `ob_refcnt` field you just saw. Store a new pointer to an object, the count goes up; drop one, it goes down; at zero, the object is freed on the spot. In CPython's C that's `Py_INCREF(op)` and `Py_DECREF(op)`, on nearly every page. The docs describe ownership with two phrases worth knowing: a <Term w="new reference">A pointer the function hands you along with the duty to Py_DECREF it when you're done. You own it.</Term> and a <Term w="borrowed reference">A pointer you may use but don't own: someone else keeps the object alive, so you must not Py_DECREF it, and it may vanish if that owner lets go.</Term>. PyTorch does the same one level up: a tensor's storage is refcounted, and the last tensor to let go returns the memory.

### Headers and macros: enough not to be scared

Lines starting with `#` aren't C. They're instructions to the <Term w="preprocessor">A text-editing pass that runs before the compiler proper. It pastes in files, expands macros, and deletes code that's switched off.</Term>, which edits your file before the compiler sees it:

- `#include <stdio.h>` pastes in the file `stdio.h`, a <Term w="header">A .h file that lists what functions, types and macros exist, without (usually) their full code, so other files can use them. Roughly Python's import, done by copy-paste.</Term> that declares `printf` and friends.
- `#define N 1024` makes every later `N` become `1024`. Macros can take arguments too, like `#define PyList_GET_ITEM(op, index) (_PyList_CAST(op)->ob_item[(index)])`, which is real CPython. Read a macro as "this name is shorthand for this code."
- `#if defined(__AVX2__)` ... `#endif` keeps the code between them only if the condition holds at compile time. This is how one file supports many CPUs: Intel chips with <Term w="AVX2">A set of Intel/AMD instructions that work on 8 floats at once (256 bits). Apple Silicon and the Spark's ARM cores don't have it; they have NEON, which does 4 floats at once.</Term> get one loop, everything else gets another. On your Mac and your Spark, `__AVX2__` is not defined, so that block is simply deleted before compiling.

There's also a short list of words you can skip on a first read. They change *how* the code is compiled or exported, not *what* it computes: `static`, `inline`, `extern`, `const` (a promise not to modify), `restrict` / `__restrict__` (a promise that pointers don't overlap), `PyAPI_FUNC(...)`, `GGML_API`, `Py_ALWAYS_INLINE`, `__device__`, `__forceinline__`.

### Reading a real function

Here's the recipe. It works on CPython, ggml and CUDA alike:

1. **Read the signature like a sentence.** Return type, name, then each argument's type and name. Ask: which pointers are inputs (often `const`), which are outputs, and which `int` is the length?
2. **Skip the noise words** from the list above, and skip `assert` and error handling on the first pass.
3. **Find the loop.** Most performance-relevant functions are one loop over an array. What's the index, what are the bounds, what happens per element?
4. **Translate stars and arrows.** `p[i]` is element `i`. `p->f` is field `f` of the thing `p` points at. `*out = v` is "write `v` to where `out` points."
5. **For `#if` blocks, ask which one your machine gets.**

PyTorch's core is C++, which adds classes, `::` for namespaces (`at::Tensor`), templates in angle brackets (`std::vector<float>`) and references (`Tensor&`, pointers you don't have to dereference). The recipe still works; the inner loops look like C.

### One more: a GPU kernel

A CUDA <Term w="kernel">A function that runs on the GPU, launched once but executed by thousands of threads in parallel, each usually handling one element. Not the operating-system kernel; same word, different thing.</Term> looks like a C function with one twist: there's usually no loop. The loop is replaced by thousands of threads, each running the same function with a different index. NVIDIA's CUDA C++ Programming Guide introduces kernels with a vector add; this version is mine, the same idea plus the bounds check real kernels need:

```cuda
__global__ void add(int n, const float *x, const float *y, float *out) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // which element am I?
    if (i < n) out[i] = x[i] + y[i];
}

// launched from the CPU with 256 threads per block, enough blocks to cover n:
// add<<<(n + 255) / 256, 256>>>(n, x, y, out);
```

`__global__` marks it as a kernel. `threadIdx.x` is this thread's number inside its block, `blockIdx.x` is the block's number, `blockDim.x` is threads per block. Multiply and add, and every thread gets a unique `i`. The rest is the C you now read: a length, three pointers to floats, and `out[i] = x[i] + y[i]`. [FlashAttention and kernels](/lessons/flash-attention/) builds on exactly this.

**A. CPython, `Objects/listobject.c`: `PyList_GetItem`**, the C API's `x[i]`:

1. What does it return, in plain words? What does it return on failure, and how does the caller find out *which* error?

3. Does it touch the refcount of the item it returns? What does that make the result?

<details>
<summary>Answers</summary>

1. A pointer to element `i`'s object. On failure, `NULL` (address 0), with the exception recorded on the side by `PyErr_...`; the interpreter later raises it as the `IndexError` you know. "Return NULL, set an error" is CPython's `raise`.

**B. CPython, same file, inside `list_resize`**: how much room a list grabs when it grows (`newsize` is the length it needs to hold):

new_allocated = ((size_t)newsize + (newsize >> 3) + 6) & ~(size_t)3;

`>> 3` shifts the bits right by 3, which divides by 8. `& ~3` clears the bottom two bits, rounding down to a multiple of 4.

1. Compute `new_allocated` for `newsize` 1, 5 and 9.
2. Roughly what fraction of extra room does a big list get?

<details>
<summary>Answers</summary>

1. 1 + 0 + 6 = 7, rounded down to a multiple of 4: **4**. 5 + 0 + 6 = 11, so **8**. 9 + 1 + 6 = 16, so **16**. The comment above it in the source lists the pattern: 0, 4, 8, 16, 24, 32, 40, 52, 64, 76...

**C. llama.cpp, `ggml/src/ggml-cpu/vec.h`**: the function from The Problem, in full:

```c
inline static void ggml_vec_add_f32 (const int n, float * z, const float * x, const float * y) {
    int i = 0;
#if defined(__AVX2__)
    for (; i + 7 < n; i += 8) {
        __m256 vx = _mm256_loadu_ps(x + i);
        __m256 vy = _mm256_loadu_ps(y + i);
        __m256 vz = _mm256_add_ps(vx, vy);
        _mm256_storeu_ps(z + i, vz);
    }
#endif
    for (; i < n; ++i) {
        z[i] = x[i] + y[i];
    }
}
```

1. Which arguments are inputs and which is the output? What's the Python one-liner?
2. On an Intel machine with AVX2, what does the first loop do per step, and why does the second loop still exist?

<details>
<summary>Answers</summary>

1. `n` is the length, `x` and `y` are inputs (`const`: won't be changed), `z` is the output, written through the pointer. NumPy: `z[:n] = x[:n] + y[:n]`.
2. Each step loads 8 floats from `x + i` (the address of `x[i]`), 8 from `y + i`, adds the 8 pairs in one instruction, and stores 8 results at `z + i`. The second loop mops up the last 0-7 elements. Each `for` starts with an empty first part because `i` carries over from the loop before.
3. `__AVX2__` isn't defined on ARM, so the first loop is deleted and only the plain loop compiles. The issue is right that there's no hand-written vector code *here*. </details>

| Version | Your ns/element | My ns/element |
| --- | --- | --- |
| Python `for` loop | | 10.1 |
| Python `sum()` | | 1.8 |
| C `-O0` | | 0.85 |
| C `-O2` | | 0.57 |

How to read the ladder:

- **Python loop to C `-O2`, about 18x.** The interpreter tax from Fig 001: per element, Python dispatches bytecode, checks types, makes a float object, adjusts refcounts. C does one add. `sum()` sits between: its loop is C, but it still follows a pointer to each float object.
- **`-O0` to `-O2`, about 1.5x.** At `-O0`, `total` is stored to memory and reloaded every pass. At `-O2` it lives in a register.
- **`-O2` stalls at ~0.57 ns, roughly 2-3 clock cycles.** Each add needs the previous `total`, so the adds form a chain and wait on each other. The compiler may not reorder them, because float addition isn't exactly associative: `(a + b) + c` can differ from `a + (b + c)` in the last bits, and C promises the result you wrote.
- **`-ffast-math` drops that promise**, so the compiler keeps several running totals in vector registers: 2.5x faster, last digits may change. GPUs make this trade constantly, which is why two runs of a model can disagree in the 6th decimal place.
- **NumPy** sums in a tree-shaped order with vector instructions (pairwise summation): faster, and more accurate than one long chain.

At 0.12 ns per 8-byte element NumPy is reading about 65 GB/s, so the next limit is memory, not instructions. That's where [How slow is slow?](/lessons/latency-numbers/) and [Why ~17 tokens per second?](/lessons/bandwidth-bound/) pick up.

**1. Read past the end.** In `pointers.c`, print `a[i]` for `i` from 0 to 6 over `int a[4]`. Mine printed 10, 20, 30, 40, three garbage numbers, and exited normally. Rebuild with `cc -O0 -g -fsanitize=address` and run again: AddressSanitizer stops at the first bad read with `stack-buffer-overflow` and the line number. C doesn't check, so tools do. When a C extension corrupts memory, this flag is how you find it.

**2. Overflow an int.** Sum 0 to 99,999 into an `int`, then into a `long`. My `int` said 704,982,704; the `long` said 4,999,950,000, matching Python's `sum(range(100000))`. Signed overflow is <Term w="undefined behavior">Something the C standard puts no rules on at all. The compiler may assume it never happens and optimize as if it can't, so the program can do anything.</Term>, so at `-O2` you aren't even promised the wrapped number. Python ints never overflow; every `int32` index in a tensor library can.

**3. Let the optimizer delete your benchmark.** Make `sum.c` repeat the timed loop 5 times and keep the best. At `-O2` I got **0.00 ns per element**: the array never changes between repeats, so the compiler did the work once and the timed repeats did nothing. It promises the same *output*, not the same *work*. If a C benchmark looks impossibly fast, it is. Print results, vary the input, or time one pass.

**4. Return the address of a local.** Write `int *bad(void) { int x = 5; return &x; }` and print `*bad()`. Clang warns "address of stack memory associated with local variable 'x' returned." Run it anyway: mine printed 5, which looks fine, and that's the danger. `x`'s stack frame is gone, and the next call will overwrite it. This is why the heap exists, and why `-Wall` stays on.

## Explain It Back

Answer out loud, in plain words, as if in an interview.

1. Why does C make you declare types, when Python doesn't?

<details>
<summary>Model answer</summary>

The compiler turns code into machine instructions before it runs, so it must know each value's size and which instruction to use: an integer add and a float add are different instructions, and 4-byte and 8-byte values load differently. Python decides that at runtime, on every operation, by checking the object's type field: flexible, and much slower. Types also make pointer arithmetic work: `p + 1` moves by the size of what `p` points at.

</details>

2. What does "a Python variable is a pointer" mean, concretely, in CPython?

<details>
<summary>Model answer</summary>

Every object lives on the heap as a C struct that starts with a refcount and a pointer to its type. A variable, a list slot, a dict value: each just stores the address of such a struct, typed `PyObject *` in C. Assignment copies the address and bumps the refcount; nothing is copied. `id(x)` is that address. A list is a struct holding a pointer to an array of these pointers, which is why a list of floats is a pointer per number plus a separate object per number.

</details>

3. What is a tensor in memory, and why is `t.T` free?

<details>
<summary>Model answer</summary>

One contiguous block of numbers plus metadata: a pointer to the start, the element type, the shape, the strides (how far to jump per step in each dimension) and a starting offset. Element `[i, j]` is at start + offset + i × stride0 + j × stride1. Transposing swaps shape and strides; no number moves. The bill comes later: the view isn't contiguous, so some operations need `.contiguous()` (a real copy), and reading it row by row jumps around memory, which the cache dislikes.

</details>

4. You have a C function `void f(int n, const float *x, float *out)`. What can you guess before reading the body?

<details>
<summary>Model answer</summary>

It returns nothing, so the result goes through `out`. `x` is an input array it promises not to change, `n` is almost certainly the number of elements in both, and the body is probably a loop over `i` from 0 to `n`. Nothing tells me who allocated `out` or how big it is, so the caller must have allocated at least `n` floats; if not, it writes past the end and C won't stop it.

</details>

5. How does this scale? Your summing loop handles 10 million doubles in 5.7 ms. What happens at 10 billion, and what changes first: the code or the hardware?

<details>
<summary>Model answer</summary>

10 billion doubles is 80 GB, so first it has to fit: fine in the Spark's 128 GB (spec sheet), not on most laptops, where it spills to disk and gets thousands of times slower. If it fits, time is linear: 1,000x the elements, ~5.7 seconds. The index must be a `long`, or it overflows at 2.1 billion. The serial loop is limited by the chain of dependent adds, not memory. Break the chain (several accumulators, vectors, threads) and you hit memory bandwidth: 80 GB at the Spark's ~273 GB/s (spec sheet) is about 0.3 seconds, a floor no code can beat. Past that, only more machines help.

</details>

## Go Deeper

- **Brian Kernighan and Dennis Ritchie, *The C Programming Language*, 2nd ed. (1988).** "K&R." Short, precise, written by C's creator. Chapter 5 (Pointers and Arrays) and 6 (Structures) are the two you need for reading.
- **Brian "Beej" Hall, *Beej's Guide to C Programming*.** Free at [beej.us/guide/bgc](https://beej.us/guide/bgc/). Friendly, modern and funny; the pointer chapters are the gentlest good explanation around.
- **Python docs, "Extending and Embedding the Python Interpreter" and the "Python/C API Reference Manual".** [docs.python.org/3/extending](https://docs.python.org/3/extending/index.html) and [docs.python.org/3/c-api](https://docs.python.org/3/c-api/index.html). How C code talks to CPython; the "Reference Counting" and "Objects, Types and Reference Counts" sections explain new vs borrowed references properly.
- **NVIDIA, *CUDA C++ Programming Guide*.** [docs.nvidia.com/cuda/cuda-c-programming-guide](https://docs.nvidia.com/cuda/cuda-c-programming-guide/). The "Programming Model" chapter: kernels, threads, blocks, and the vector add this lesson's kernel imitates.
- **Dennis Ritchie, "The Development of the C Language" (HOPL-II, 1993).** C's history from B, in Ritchie's words, including why types and pointers look the way they do. The source for the Origin box.
- **The source itself.** CPython's [`Include/cpython/listobject.h`](https://github.com/python/cpython/blob/main/Include/cpython/listobject.h) and `Objects/listobject.c`, and llama.cpp's `ggml/src/ggml-cpu/vec.h` on [github.com/ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp). Files move between versions; search the repo for the function name if a path breaks.
- **Edward Z. Yang, "PyTorch internals" (2019).** [blog.ezyang.com/2019/05/pytorch-internals](http://blog.ezyang.com/2019/05/pytorch-internals/). How a tensor is storage plus sizes, strides and offset, and how to find your way around PyTorch's C++. The natural next read after Fig 004.
