## The Problem

You add a feature to the ranking service: for every document a user saves, call an LLM to write a two-line summary, then run the cross-encoder to score it against the user's saved queries. The obvious code does both inside the request handler. It works on your laptop. Each save takes about 6 seconds, and the user stares at a spinner for all of it.

Then three things happen in one week.

A customer imports 4,000 documents at once. Your API server suddenly has 4,000 requests each holding a connection open for 6 seconds, the LLM provider starts answering 429, and because the handler retries inline, the requests take 30 seconds and the load balancer times them out. The user retries the import. Now there are 8,000.

You deploy a fix mid-afternoon. The rolling restart kills every in-flight request. Some summaries were written, some weren't, and nothing records which.

And the research team asks you to re-score the whole corpus, 5 million documents, with the new ranker checkpoint. You write a loop. It dies at 3.2 million because one document has a malformed byte that crashes the tokenizer. You don't know which 3.2 million finished. You start over.

All three have the same shape. Slow, failure-prone work is welded directly to whatever asked for it. If the asker is slow, impatient, or dead, the work suffers; if the work is slow or broken, the asker suffers. The fix is to put a buffer in between, a to-do list that both sides can read and write at their own pace and that remembers what's done. That's a queue.

In December 2013 Kreps wrote "The Log: What every software engineer should know about real-time data's unifying abstraction" for LinkedIn's engineering blog. His argument was that a log, an ordered list of things that happened, kept for a while, is the idea underneath databases (the write-ahead log), replication, and data integration alike. Put a log in the middle, and every system becomes a reader that can catch up, fall behind, or start over without anyone else noticing. Kreps, Narkhede and Rao left to found Confluent in 2014. Most companies now run some version of that log.

## The Idea

### A to-do list between two programs

You already know the shape from a restaurant. The waiter doesn't cook. They write the order on a ticket, clip it to the rail, and go back to the dining room. The cooks take tickets off the rail when they're free. If ten tables order at once, the rail gets long, but nobody in the dining room is kept waiting at the kitchen door, and nobody in the kitchen is rushed.

In software, the waiter is the <Term w="producer">The program that creates jobs or messages and puts them on the queue. Your API server, usually.</Term>, the cooks are <Term w="consumer">A program that takes messages off the queue and does something with them. When the something is a unit of work, people call it a worker.</Term>s (or workers), and the rail is a <Term w="message queue">A separate service that holds messages from producers until consumers take them. The producer doesn't need to know who consumes, or whether they're up right now.</Term>, run by a <Term w="broker">The server that stores the queue and hands messages out. Redis, RabbitMQ, SQS, and Kafka are all brokers of some kind.</Term>. A message is just bytes, usually a small JSON blob that says what to do: `{"doc_id": 81723, "task": "summarize"}`. Not the document itself; a pointer to it.

That one change buys four separate things, and it's worth knowing them by name, because each is a reason someone will give you in a design review.

1. **Decouple speed.** The API can accept 2,000 saves a second; the workers can summarize 20. Without a queue, the slow side sets the pace for the fast side. With one, the API stays fast and the backlog lives somewhere designed to hold it.
2. **Absorb spikes.** Traffic arrives in bursts: an import, a cron job, Monday morning. The queue stores the burst and the workers work it off over the next few minutes. You size the workers for the *average* rate, not the peak, as long as the backlog drains before the next burst.
3. **Retry independently.** If a summary fails because the LLM returned 503, the worker retries it later. The user's request finished long ago and never knew. And if the API deploys, the queued jobs don't care.
4. **Fan out.** One event, "document saved", can be read by the summarizer, the ranker, the search indexer and the analytics pipeline, each on its own schedule. The producer writes once and doesn't need to know any of them exist. Adding a fifth reader doesn't touch the producer.

The price: the work is now **asynchronous**. The user gets "accepted" instead of the answer, so you need a way to report the result later (poll `GET /jobs/<id>`, a webhook, a websocket push). And you've added a new system that can fail. Most of this lesson is about making that new system fail safely.

### How many workers? Little's Law again

In [Waiting vs working](/lessons/waiting-vs-working/) you met Little's Law: **in flight = arrival rate × time each one spends inside**. A worker pool is the cleanest case of it there is. Each worker handles one job at a time, so "jobs in flight" is "busy workers".

<Predict id="worker-count">

Saves arrive at a steady 30 per second. Each job (summary plus ranker) keeps a worker busy for 2 seconds. How many workers do you need, at minimum? What happens to the queue if you run one fewer than that?

<Fragment slot="answer">

Busy workers = 30 jobs/s × 2 s = **60 workers**, and that's the floor where they are busy 100% of the time. With 59 workers the pool finishes 29.5 jobs/s while 30 arrive, so the queue grows by 0.5 jobs every second, forever: 1,800 jobs after an hour, and each new job waits behind all of them. A queue does not add capacity. It only moves the waiting somewhere safer. In practice you'd run 70-80, for headroom: as [p99 and load testing](/lessons/tail-latency/) showed, waiting time explodes as utilization approaches 100%, even when the averages "fit".

### Handing over a job: acks and leases

When a worker takes a job, the broker has a decision to make: delete it now, or keep it until the worker says it's finished? That "I'm finished" message is an <Term w="ack">Acknowledgement. The consumer telling the broker "I've handled this message, you can forget it." Until the broker gets one, it assumes the message might still need doing.</Term>.

If the broker deletes on handover, a worker crash loses the job. If the broker keeps it until the ack, it needs to know when to give up waiting, because a crashed worker never sends anything. A dead process doesn't announce that it's dead. From the broker's side, "still working on it" and "was `kill -9`'d ten minutes ago" look identical: silence.

So the broker gives each handed-out job a <Term w="lease">Temporary ownership of a job with a deadline. If the holder doesn't finish (ack) or renew before the deadline, the job is given to someone else.</Term>. Amazon SQS calls the lease length the <Term w="visibility timeout">SQS's name for the lease: after a consumer receives a message, it's hidden from other consumers for this long. If not deleted by then, it becomes visible again and gets redelivered. Default 30 s.</Term>: once a worker receives a message, it becomes invisible to everyone else for, say, 30 seconds. If the worker deletes it (the ack) in time, it's gone for good. If not, it becomes visible again and some worker gets it. That's <Term w="redelivery">The broker handing the same message out again because the previous attempt never acked. The consumer gets a message it, or a dead colleague, may have already partly processed.</Term>.

Two practical details follow from leases.

**The lease must outlast the job.** If a job takes 90 seconds and the lease is 30, the broker hands the same job to a second worker while the first is still happily working on it, then a third. Nothing crashed, and the job runs three times. Long jobs either set a long lease, or **heartbeat**: every so often the worker says "still on it" and the broker pushes the deadline back (SQS: `ChangeMessageVisibility`). Celery's Redis transport has exactly this trap: its `visibility_timeout` defaults to one hour, and a task scheduled or running longer than that gets delivered again.

**A short lease means fast recovery, a long lease means slow recovery.** When a worker really does die, its job sits untouched until the lease expires. In Figure 002 that was 3 seconds. With a one-hour lease, a crash means an hour's delay for that job. You pick the lease from the job length (longest normal job, times a safety factor) and heartbeat if the spread is wide.

### At-most-once, at-least-once, and the myth of exactly-once

Those three rows in Figure 003 have names, and you'll hear them in every design discussion about messaging.

- <Term w="at-most-once">Each message is processed zero or one times. Never duplicated, but can be lost. What you get when you ack (or delete) before doing the work.</Term>: ack first, then work. A crash loses the job. Fine for things where losing one is cheaper than doing one twice: a metrics sample, a "user is typing" ping.
- <Term w="at-least-once">Each message is processed one or more times. Never lost (while the broker survives), but can be duplicated. What you get when you ack only after the work is done.</Term>: work first, then ack. A crash means a redelivery. Nothing is lost, but some things happen twice. This is the default for almost every serious queue.
- <Term w="exactly-once">Each message has its effect exactly one time, even with crashes. Not achievable as a delivery guarantee across arbitrary systems; achievable as an effect, by combining at-least-once delivery with deduplication.</Term>: what everyone wants.

Here's why you can't get exactly-once *delivery*. Look at the bottom row again. The worker saved the result and then died before the ack reached the broker. Or the ack was sent and the network dropped it. Either way, the broker sees silence, and silence after a save looks exactly like silence before a save. The broker has to choose: redeliver (risk a duplicate) or not (risk a loss). There is no third option, because the broker can't see inside the worker. Move the ack earlier and you've just moved the gap. This is a cousin of the classic "two generals" problem: two parties talking over a channel that can lose messages can never be *sure* they agree.

So the industry's real answer is: **at-least-once delivery, plus a consumer that makes duplicates harmless.** An operation is <Term w="idempotent">Doing it twice has the same effect as doing it once. "Set score to 0.83" is idempotent; "add 0.83 to the total" is not.</Term> when repeating it changes nothing. You make a consumer idempotent with an <Term w="idempotency key">A unique ID attached to a piece of work, so the receiver can recognize a repeat and skip it. For a job, the job ID or a natural key like (doc_id, model_version).</Term>, the same trick you saw for API retries in [the API lifecycle](/lessons/api-lifecycle/):

- **Write the result and the "done" mark in one transaction.** `INSERT INTO scores (doc_id, model, score) ... ON CONFLICT DO NOTHING`, where `(doc_id, model)` is the primary key. The second delivery's insert is a no-op. If you also bump a counter, bump it *only when the insert actually inserted*, in the same transaction. That's [Transactions](/lessons/transactions/) earning its keep: the effect and the record of the effect can't come apart.
- **Make the operation itself a "set", not an "add".** "Document 81723's score is 0.83" can be written any number of times. "Increment the user's processed count" can't, unless you dedupe first.
- **For external side effects** (sending an email, charging a card, calling a paid API), pass the key along if the other side supports it (Stripe takes an `Idempotency-Key` header), or record "sent" before you'd risk sending twice and accept that a crash in between might mean zero sends. Somewhere, someone picks at-most-once or at-least-once. You just get to choose where.

When Kafka advertises "exactly-once semantics" (added in 2017), it means something precise and narrower: a producer's retries don't create duplicates in the log, and a job that reads from Kafka and writes back to Kafka can commit its output and its read position atomically. That's real and useful. But the moment your consumer touches anything outside Kafka (a database, a model API, an email), you are back to at-least-once plus idempotency. People call the combination <Term w="effectively-once">At-least-once delivery plus an idempotent consumer, so each message's effect happens once even when the message is delivered more than once. The honest name for "exactly-once".</Term>.

### Poison messages and the dead-letter queue

Remember the document with the malformed byte that crashes the tokenizer. Under at-least-once, it's worse than you think. The worker claims it, crashes, the lease expires, another worker claims it, crashes... A <Term w="poison message">A message that fails every time it's processed, usually because of bad data or a bug, not a temporary outage. Retrying it forever wastes workers and can block the queue.</Term> can kill your whole pool in a loop, one worker at a time, forever.

The fix is to count attempts. Every claim bumps the job's attempt counter. When it fails (or its lease expires) and the count has reached a limit, say 3 or 5, the broker moves it aside into a <Term w="dead-letter queue">A separate queue where messages go after failing too many times. Nobody processes it automatically; a human looks, fixes the bug or the data, and re-queues them. Often shortened to DLQ.</Term> instead of back into the main queue. SQS calls this a redrive policy with `maxReceiveCount`; RabbitMQ calls it a dead-letter exchange; Celery leaves it to you.

Three rules make a DLQ useful instead of a graveyard:

1. **Store why it died.** The last exception and traceback, the attempt count, the worker that saw it. Otherwise you're debugging blind.
2. **Alert on it.** A DLQ that grows silently is the same as dropping messages.
3. **Have a re-drive tool.** After you fix the bug, you want one command that moves everything from the DLQ back to the main queue. Since the consumer is idempotent, re-driving something that half-succeeded is safe.

And separate *retryable* failures from *permanent* ones. A 503 from the LLM provider should be retried with backoff (and jitter, from [Rate limits](/lessons/rate-limits/)); a `UnicodeDecodeError` will fail identically on every attempt, so it can go straight to the DLQ.

### Job queues and logs: two different machines

Everything so far describes a <Term w="job queue">A queue where each message is a unit of work, handed to exactly one worker, and deleted once acked. Celery, RQ, Sidekiq, SQS, RabbitMQ.</Term>: each message goes to one worker and is deleted when acked. Celery, RQ (Redis Queue) and Sidekiq are libraries built on brokers like Redis or RabbitMQ; SQS is Amazon's hosted version. Under the hood in Redis, a queue is often just a list: producers push to one end, workers pop from the other.

Kafka is a different machine, and the difference matters. It's a <Term w="log">An append-only, ordered sequence of records. New records only go on the end; nothing is changed in place. Each record gets a position number, its offset.</Term>. Messages aren't deleted when read. They're appended to the end of a file and kept for a fixed time (the default is 7 days) or up to a size limit, whether anyone has read them or not. That design gives a log three powers a job queue doesn't have:

- **Many independent readers.** The summarizer, the search indexer and the analytics loader each keep their own position in the same log. A slow reader doesn't slow the others, and a new reader can start from the beginning.
- **Replay.** Found a bug in the summarizer that ran for two days? Fix it, reset its offset to two days ago, and it reprocesses everything. With a job queue, those messages are gone the moment they were acked.
- **History as data.** The log *is* a record of what happened, in order. That's Kreps' point: you can rebuild a search index, a cache, or a whole database table by reading the log from the start.

The job queue has its own advantages: per-message acks, per-message retries and DLQs, no need to think about positions, and simple scaling by just adding workers. Rule of thumb: if each message is a **task** to get done once, use a job queue. If each message is an **event** (a fact about something that happened) that several systems care about, use a log.

### Partitions, consumer groups, and why ordering is per partition

One log on one disk can only go so fast. So a Kafka <Term w="topic">A named stream of records in Kafka, like "documents-saved". Physically split into partitions.</Term> is split into <Term w="partition">One independent, ordered log inside a topic. Records within a partition have a strict order; records in different partitions have none. Partitions are spread across brokers.</Term>s, each its own little append-only log, living on different machines. When a producer writes a record, it picks a partition, usually by hashing the record's **key**. Same key, same partition, every time.

On the reading side, consumers join a <Term w="consumer group">A set of consumers that share the work of reading a topic. Kafka gives each partition to exactly one consumer in the group, so each record is processed once per group.</Term>. Kafka gives each partition to exactly one member of the group. That's how a log does load balancing: not message by message, but partition by partition.

Three consequences you should be able to say out loud:

1. **Ordering is only per partition.** Within P1, the events for document 17 are in the order they were written. Across partitions there is no order at all: C1 might process an event from P0 written an hour after an event C2 hasn't reached yet in P1. If order matters for some entity (the edits of one document, the events of one user), make that entity the key, so all its records share a partition. Global ordering would mean one partition, which means one consumer.
2. **Parallelism is capped by partitions.** Three partitions, at most three busy consumers per group. The fourth sits idle as a hot spare. Pick the partition count for the parallelism you'll need later; adding partitions afterwards changes which partition each key hashes to, which breaks per-key ordering across the change.
3. **One slow message blocks its whole partition.** A consumer reads its partition in order. If one record takes a minute, everything behind it in that partition waits, even though other consumers are idle. A job queue doesn't have this problem, since any free worker can take the next job. This is the deepest practical difference between the two, and why "Kafka as a job queue for slow, uneven jobs" often hurts. (Kafka 4.x is adding "share groups", queue-style consumption on top of a topic, for exactly this reason. Check the docs for its status.)

Kafka's delivery semantics are the same story as before, told with offsets. If you commit the offset *before* processing, a crash skips records: at-most-once. If you commit *after*, a crash replays from the last commit: at-least-once, possibly a few hundred duplicates. The client's default, auto-commit every 5 seconds in the background, can do either depending on timing, which is why serious consumers turn it off and commit after they've processed.

### Consumer lag: the one number to watch

How do you know whether a queue is healthy? Not by its size alone; a big backlog that's shrinking is fine. You watch <Term w="consumer lag">How far behind the consumers are. In Kafka, the newest offset minus the committed offset, per partition. In a job queue, the number of waiting messages, or better, the age of the oldest one.</Term>.

- In Kafka, lag for each partition is the latest offset minus the group's committed offset: "how many records written but not yet processed".
- In a job queue, it's queue depth, and even better, the **age of the oldest message**. Depth tells you how much; age tells you how late. 10,000 tiny jobs might be 5 seconds of work; 100 huge ones might be an hour. SQS publishes this as `ApproximateAgeOfOldestMessage`.

Lag has three shapes, and you saw all three in Figure 002. **Flat near zero**: keeping up. **Spike then decay**: a burst being absorbed, draining at (capacity − arrival rate). **A steady ramp**: arrivals exceed capacity, and it will never recover on its own. The ramp's slope is literally the shortfall. If lag grows by 600 jobs a minute, you're 10 jobs per second short, which by Little's Law is 10 × (job time) more workers.

The time to drain a backlog B, once you add capacity, is B / (capacity − arrival rate). Note what's on the bottom: with a backlog of 100,000 jobs, capacity 110/s and arrivals 100/s, draining takes 10,000 s, almost three hours, even though you're "over capacity". Headroom is what clears backlogs.

And notice what a queue does to backpressure. In [Rate limits](/lessons/rate-limits/) you saw that an unbounded buffer hides overload: the producer never feels the pressure. A queue is a very large buffer, on purpose. It is your *choice* to absorb rather than push back, which is fine for spikes and terrible for sustained overload. So bound it (a max length, or reject new jobs when the oldest is older than your deadline), and alert on lag. Otherwise the queue fills disk or memory and the failure is a lot bigger than a 429 would have been.

### The outbox pattern: writing to the database and the queue at once

One more trap, and it shows up the first day you wire a queue into a real app. The save handler does two things: insert the document row into Postgres, and enqueue a "summarize this" job.

```python
db.execute("INSERT INTO documents ...")   # 1
db.commit()
queue.enqueue({"doc_id": doc_id})         # 2
```

If the process dies between 1 and 2, the document exists and its job never will. Swap the order and the opposite happens: a job for a document that was rolled back. You can't wrap both in one transaction, because the database and the broker are two different systems. This is the <Term w="dual write">Writing the same change to two systems (say, a database and a queue) as two separate steps. A crash between them leaves the systems disagreeing, and neither knows.</Term> problem.

The fix is the <Term w="outbox pattern">Write the outgoing message into an "outbox" table in the same database transaction as the business change. A separate relay process reads the outbox and publishes to the broker, deleting or marking rows once sent.</Term>: write the message to an `outbox` table *in the same database transaction* as the document. Now they either both exist or neither does. A separate small process, the relay, reads unsent outbox rows, publishes them to the queue, and marks them sent.

### Which one do I reach for?

| Need | Reach for | Why |
| --- | --- | --- |
| Background jobs in a Python app | Celery or RQ on Redis | Simple, per-job retries. Turn on `acks_late` in Celery, or a worker crash loses the task. |
| Jobs on AWS, no servers to run | SQS (+ DLQ via redrive policy) | Visibility timeout and DLQ built in. Standard queues are at-least-once with best-effort order. |
| Jobs, and you already have Postgres | A jobs table + `SELECT ... FOR UPDATE SKIP LOCKED` | Jobs commit in the same transaction as your data. No outbox needed. Fine up to thousands of jobs/s. |
| Events many systems read, replay, history | Kafka, or Redpanda (Kafka-compatible) | Retention, offsets, consumer groups, per-key order. |
| Something in between, already on Redis | Redis Streams (`XADD`, `XREADGROUP`, `XACK`) | A log with consumer groups and a per-consumer pending list, so you can reclaim stuck messages. |

### Batch inference is a queue workload

Back to the 5 million documents. A batch job is a queue with one giant spike at the start: all the arrivals happen at once, and lag is "how much is left". Treat it that way and the 3.2-million-and-crash problem disappears.

- **Each job is a chunk, not a document.** Enqueue `{"shard": 412, "start": 412000, "end": 413000}`, not the documents themselves. One message per document means 5 million broker round trips; one per 1,000 documents means 5,000, and the worker can run the ranker on full GPU batches. Chunk size is a trade: bigger chunks are more efficient but redo more work when a worker dies mid-chunk.
- **Results are keyed, so redelivery is free.** Write scores with primary key `(doc_id, model_version)` and `ON CONFLICT DO NOTHING` (or overwrite; the score is the same either way). Re-running a chunk is harmless, so you never need to know exactly which ones finished. You just re-enqueue anything not in the results table.
- **Poison data goes to the DLQ, not into a crash loop.** The malformed document fails its chunk three times and gets parked, with its traceback, while the other 4,999 chunks keep moving. Even better, catch per-document errors inside a chunk and record them, so one bad document doesn't send 999 good ones to the DLQ.
- **Little's Law sizes it, lag tracks it.** Workers × throughput per worker tells you the finish time before you start. Lag over time tells you whether you're on schedule, and its slope tells you when you'll finish.

This is also what the batch APIs from model providers are under the hood: a durable queue of your requests, worked off whenever they have spare capacity, which is why they're cheaper.

## Break It

1. **Lease shorter than the job.** Set the lease to 0.01 s with 20 ms jobs, no kills. Every job's lease expires mid-work, `reap` hands it to someone else, and the naive table fills with duplicates while workers are perfectly healthy. Then add a heartbeat (`extend` every half-lease, from a thread in the worker) and watch it stop. This is the most common queue bug in production, and it looks like "random duplicates under load", because jobs slow down under load.
2. **No attempt limit.** Set `max_attempts` to a huge number. The poison jobs bounce between pending and in-flight forever, using a worker each time. With one poison message per 1,000 jobs and a slow failure (say the tokenizer hangs 10 s before crashing), a growing fraction of your pool ends up doing nothing but failing. Then put the limit back.
3. **Ack before work.** Move `ack` before `apply` and rerun the chaos test. Now you'll be short: fewer than 1,998 rows, nothing in the DLQ for them, and no error anywhere. Silent loss is worse than duplicates, because nothing tells you.
4. **Producer faster than consumers, no bound.** Run 2 workers and a producer at 500 docs/s for a few minutes. Watch `redis-cli info memory` climb and the oldest job's age grow without limit. Then add a guard to `enqueue`: if `LLEN q:pending` exceeds a limit, raise, and have the API return 503 with `Retry-After`. That's backpressure from [Rate limits](/lessons/rate-limits/), applied at the door of the queue.

## Explain It Back

Answer out loud, in plain words, as if in an interview. Then check.

<details>
<summary>1. Why would you put a queue between two services? What does it cost you?</summary>

It decouples them. The producer can accept work at its own speed while consumers process at theirs; bursts are stored in the queue and drained over time, so you size workers for the average load rather than the peak; failed work can be retried by the consumer without the original caller waiting or even being alive; and one event can feed several consumers that the producer doesn't know about. The cost: the work becomes asynchronous, so you need another way to deliver results (polling, webhooks); you add a system that must be run, monitored and sized; and you take on delivery semantics, which in practice means duplicates, so consumers must be idempotent. A queue also doesn't add capacity: if arrivals exceed capacity for long, it just grows.

</details>

<details>
<summary>2. What's the difference between at-most-once, at-least-once and exactly-once? Which do you build, and how?</summary>

At-most-once acks before the work, so a crash loses the message but never duplicates it. At-least-once acks after the work, so a crash causes a redelivery and nothing is lost, but some messages are processed twice. Exactly-once delivery isn't possible across systems, because if the worker finishes and its ack is lost, the broker can't tell that apart from a worker that died before finishing; it has to either redeliver or not. So you build at-least-once delivery with an idempotent consumer: give every job a key, and write the result together with "this key is done" in one transaction (insert with a unique key and ignore conflicts), or make the operation a "set" rather than an "add". The combination is sometimes called effectively-once. Kafka's exactly-once is real but only covers Kafka-to-Kafka pipelines; anything external still needs idempotency.

</details>

<details>
<summary>3. Your worker pool processes jobs from a queue. What happens, step by step, when a worker gets kill -9'd halfway through a job?</summary>

The worker had claimed the job, which moved it to an in-flight set with a lease deadline. The kill stops the process instantly; it can't ack, fail, or clean up. The broker sees nothing, since silence looks the same as slow work. When the lease deadline passes, the job is made visible again (put back in the queue) and its attempt count goes up; another worker claims it and runs it from the start. If the dead worker had already saved its result before dying, the second run produces the same result and the idempotent write ignores it. If the job keeps failing until it reaches the attempt limit, it goes to the dead-letter queue with its last error for a human to look at. The cost of the crash is one lease-length of delay for that job, plus the wasted partial work.

</details>

<details>
<summary>4. When would you use Kafka instead of a job queue like SQS or Celery?</summary>

When messages are events that several independent systems need, when you want to replay history (reprocess after a bug, build a new index from the past), or when you need per-key ordering at high throughput. Kafka keeps records for a retention period regardless of reads, and each consumer group tracks its own offset, so readers are independent and can rewind. A job queue is better for tasks that should be done once by one worker, especially slow or uneven ones: any free worker takes the next job, and each job has its own ack, retry count and DLQ. In Kafka, a partition is read in order by one consumer, so one slow record blocks everything behind it in that partition, and parallelism is capped by the partition count.

</details>

<details>
<summary>5. You need to re-score 50 million documents with a new ranker by tomorrow morning, 12 hours from now. How do you size and run it, and how does it scale?</summary>

Throughput needed: 50M / 43,200 s ≈ 1,160 docs/s. Measure one worker's real throughput on the target hardware, say 400 docs/s per GPU with batched inference, so you need about 3 GPUs' worth, and I'd plan for 4-5 to leave headroom for retries and stragglers (Little's Law: in-flight work = throughput × time per chunk tells you how many concurrent chunks to have running). Enqueue chunks of a few thousand documents rather than single documents, to keep broker traffic small and batches full. Write results keyed by (doc_id, model_version) with ignore-on-conflict, so redelivered chunks are harmless and a restart only needs to enqueue chunks with missing results. Use a lease longer than the slowest chunk (or heartbeat), an attempt limit with a DLQ, and catch per-document errors so one bad document doesn't fail a chunk. Watch lag (chunks remaining) over time; its slope gives the finish time, and if it's too shallow, add workers until you hit the next shared limit: the database's write rate, the storage you read documents from, or the network. Scaling past that means sharding the results store or writing results to files per chunk instead of one database.

</details>
