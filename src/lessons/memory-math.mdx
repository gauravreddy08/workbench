## The Problem

Here is the question from the diagnostic: *how much memory does an 8B model need?* The honest answer you gave was a shrug, and the common wrong answer is "8 GB, one byte per parameter". Neither will get you far.

Now make it real. Your team wants to use the Spark as a shared assistant: Llama 3.1 8B, long chats, 32K tokens of context each. You start vLLM, it thinks for a minute, and prints a line like *maximum concurrency for 32,768 tokens per request: 24x*. Is that good? Is it right? Where did 24 come from? Then you start it again with a 70B model in 4 bits at 128K context and it prints something like *2x*. Then a colleague runs a notebook on the same box and something gets killed.

Every one of those numbers comes from a few lines of arithmetic. By the end of this lesson you will do that arithmetic faster than vLLM boots.

<Fragment slot="answer">

About **17 to 18 GiB** for one user: 15 GiB of weights (8.03 billion × 2 bytes = 16.1 GB, which is 15.0 GiB), 1 GiB of KV cache (8,192 tokens × 128 KiB), and one to two GiB of runtime overhead and activations. The weights are the big fixed cost; one user's cache is small.

At 32K context each user's cache is 4 GiB. After the operating system (call it 10 GiB, you will measure it), the weights and overhead, roughly 100 GiB is left, so **about 25 users**. Whether 25 users get a *usable speed* is a different question, and the [envelope lesson](/lessons/back-of-envelope/) showed that bandwidth runs out first on the Spark. <Origin year="2019" title="One write-head is all you need">

In 2019 Noam Shazeer, one of the authors of the original transformer paper, published a short note with a cheeky title: "Fast Transformer Decoding: One Write-Head is All You Need." His complaint was that during generation, the keys and values stored for every past token were eating memory and memory bandwidth, and that most of that cost came from every attention head keeping its own private copy. His fix, multi-query attention, let all the query heads share a single key head and a single value head. The cache shrank by the number of heads.

It was too aggressive for some models (quality dropped), so in 2023 Joshua Ainslie and colleagues at Google proposed the middle ground, grouped-query attention: a few key/value heads, each shared by a group of query heads. Llama 2's 70B model adopted it that year, and by Llama 3 every size used it. When you count Llama 3.1 8B's parameters below, you will see this decision as a strange asymmetry in the attention matrices. When you size its KV cache, you will see it as a 4x discount. Memory was the reason the architecture changed.

</Origin>

## The Idea

### Four buckets

Think of a restaurant kitchen during service. There is equipment bolted to the floor: ovens, fridges, the walk-in. That is the same size whether you serve one table or forty. Then each table has an order ticket and a tray of their own food in progress, and that space grows with the number of tables and how long each one stays. While a dish is being plated there is a burst of counter space in use, gone a minute later. And there is the space you can never use: walkways, the fire-code clearance, the manager's desk.

GPU memory during inference has exactly those four buckets.

1. **Weights.** The model itself. Bolted to the floor: loaded once, shared by every user. Size = parameters × bytes per parameter.
2. **KV cache.** Each user's private tray. Grows with every token of every conversation. Size = bytes per token × context length × users.
3. **Activations.** The temporary numbers inside one forward pass: the vector flowing through a layer, the wide MLP intermediate, the scores at the end. Freed as soon as the layer is done. Small in decode, a short spike during prefill.
4. **Overhead.** Memory that is in use but holds none of the above: the CUDA runtime's own setup, library scratch space, memory the allocator holds but isn't using, and on the Spark, the whole operating system.

The whole lesson is one equation and the details that make it honest:

```text
users that fit  =  (memory − OS − weights − overhead − activation peak)  ÷  (KV bytes per token × context)
```

Weights and KV cache are pure arithmetic, so we start there.

### Bytes, GB and GiB

One unit trap first, because it will otherwise eat 7% of every answer. A <Term w="GB">A gigabyte: 1,000,000,000 bytes (10⁹). Used by disk makers, Hugging Face file sizes, and network speeds.</Term> is a billion bytes. A <Term w="GiB">A gibibyte: 2³⁰ = 1,073,741,824 bytes, about 7% more than a GB. Memory chips come in powers of two, so RAM and GPU memory are really sized in GiB, and PyTorch and `nvidia-smi` (which prints MiB) report in binary units.</Term> is 2³⁰ bytes. Llama 3.1 8B in bf16 is 16.06 GB *and* 14.96 GiB; both are right. Memory is built in powers of two, so when you compare against what a machine holds, work in GiB. The KV cache formula is naturally binary (128 KiB per token, so 8,192 tokens is exactly 1 GiB), which is one more reason to stay there.

### Counting parameters from config.json

Every model on Hugging Face ships a `config.json`. It is a dozen numbers that completely determine the shape of every weight matrix. Here are the ones that matter for Llama 3.1 8B:

```json
{
  "vocab_size": 128256,
  "hidden_size": 4096,
  "intermediate_size": 14336,
  "num_hidden_layers": 32,
  "num_attention_heads": 32,
  "num_key_value_heads": 8,
  "head_dim": 128,
  "tie_word_embeddings": false,
  "torch_dtype": "bfloat16"
}
```

You have written this model, so you know every piece. The job now is just to say how big each one is. Call `hidden_size` h, `vocab_size` V, `intermediate_size` I, heads n, KV heads k, `head_dim` d.

**The embedding table.** One row of h numbers per vocabulary entry: V × h = 128,256 × 4,096 = **525,336,576**. That is half a billion parameters before you reach the first layer, which surprises everyone the first time.

**Attention, per layer.** Four projection matrices. The query projection maps h inputs to n × d outputs. The key and value projections map h inputs to only k × d outputs, because with <Term w="GQA">Grouped-query attention: the model has fewer key/value heads than query heads, and each K/V head is shared by a group of query heads. Llama 3.1 8B has 32 query heads and 8 K/V heads, so groups of 4.</Term> there are only 8 key/value heads. The output projection maps n × d back to h.

```text
q_proj   4096 × (32 × 128) = 4096 × 4096 = 16,777,216
k_proj   4096 × ( 8 × 128) = 4096 × 1024 =  4,194,304
v_proj   4096 × ( 8 × 128) = 4096 × 1024 =  4,194,304
o_proj   (32 × 128) × 4096 = 4096 × 4096 = 16,777,216
                                   total  = 41,943,040
```

That asymmetry, K and V a quarter the size of Q, is Shazeer's idea from the box above, sitting in your parameter count.

**The MLP, per layer.** Llama uses <Term w="SwiGLU">A feed-forward block with three matrices instead of two: a "gate" and an "up" projection run side by side, the gate goes through the SiLU function and multiplies the up output elementwise, then a "down" projection maps back. More expressive per parameter than the old two-matrix MLP.</Term>, so there are three matrices, not two: gate (h × I), up (h × I), down (I × h).

```text
3 × 4096 × 14336 = 176,160,768
```

The MLP is four times the attention block. Most of an LLM's parameters live here.

**Norms.** Each layer has two <Term w="RMSNorm">A normalization that divides each vector by its root-mean-square and multiplies by a learned scale. The scale is one number per hidden dimension, so it has h parameters and no bias.</Term> layers (one before attention, one before the MLP), each with h = 4,096 learned scales: **8,192** per layer. One more after the last layer: 4,096. Rounding error, but count them; it is how you get an exact match.

**The output head.** The `lm_head` maps h back to V scores, another 525,336,576. Unless `tie_word_embeddings` is true, in which case the model reuses the embedding table and this costs zero. Llama 3.1 8B: false, so it is a separate matrix. Llama 3.2 1B: true, so it is shared. The flag is worth 525 million parameters (1 GB in bf16); always read it.

Add it up:

```text
per layer      = 41,943,040 + 176,160,768 + 8,192         =   218,112,000
32 layers      = 32 × 218,112,000                          = 6,979,584,000
embed + head   = 2 × 525,336,576                           = 1,050,673,152
final norm                                                 =         4,096
total                                                      = 8,030,261,248
```

**8.03 billion.** I checked this against transformers itself: building the model from this config on PyTorch's `meta` device (which creates tensor shapes without allocating any memory) and summing `numel()` over its parameters gives 8,030,261,248, to the parameter. The same method gives 1,235,814,400 for Llama 3.2 1B (tied head) and 70,553,706,496 for Llama 3.1 70B. You will write the counter yourself in Build It.

Two useful facts fall out of the breakdown. The MLP is 70% of the model, attention 17%, embedding and head 13%. And the shortcut for a quick estimate: per layer, attention is about 2h² + 2hkd and the MLP is 3hI, so for this family the layers come to roughly L × (2.5h² + 3hI). You can do that in your head in an interview: 32 × (2.5 × 16.8M + 176M) ≈ 7.0B, plus 1.05B of vocabulary matrices.

### Bytes per parameter

Weights in memory = parameters × bytes per parameter. The bytes depend on the format.

- <Term w="FP32">32-bit floating point, 4 bytes per number. The default for training math in the old days; almost nobody serves in it now.</Term>: 4 bytes. 8B model: 32.1 GB.
- **BF16 or FP16**: 2 bytes. 16.1 GB. This is what most checkpoints ship as (`torch_dtype` in the config). Why bf16 and not fp16 is the [number formats lesson](/lessons/number-formats/).
- <Term w="FP8">An 8-bit floating point format, 1 byte per number, with a scale factor per tensor or per channel so the small range still covers the weights.</Term>: 1 byte for the layers. Popular FP8 checkpoints usually leave the embedding and `lm_head` in bf16, so an 8B FP8 file is about 9.1 GB, not 8.0.
- **Integer formats with block scales.** You cannot just round a weight to one of 16 values (4 bits) without a sense of scale. So these formats chop each matrix into small blocks and store one or two scale numbers per block alongside the tiny integers. The scales are real bytes, and they are why "4-bit" is never 4.0 bits.

The cleanest example is llama.cpp's <Term w="GGUF">The single-file model format used by llama.cpp. It holds the weights (in many possible quantized types), the tokenizer, and the config in one file.</Term> type Q8_0: blocks of 32 weights, each stored as a signed 8-bit integer, plus one 16-bit scale per block. 32 bytes + 2 bytes = 34 bytes per 32 weights = **8.5 bits per weight**.

The other two 4-bit formats you will meet:

- <Term w="AWQ">Activation-aware Weight Quantization (Lin et al., 2023). Stores layer weights as 4-bit integers in groups of 128, each group with a 16-bit scale and a 4-bit zero point, choosing the scales so the weights that matter most for real activations lose least.</Term> checkpoints quantize the transformer layers in groups of 128 weights. Each group adds a 16-bit scale and a 4-bit zero point: 20 extra bits per 128 weights, so about **4.16 bits** per layer weight. But the embedding and `lm_head` usually stay in 16-bit. For Llama 3.1 8B that is 1.05 billion parameters at 2 bytes (2.1 GB) plus 6.98 billion at 4.16 bits (3.6 GB): about **5.7 GB**, which is what published AWQ files of this model weigh. The "4-bit model" averages 5.7 bits per weight.
- **Q4_K_M** in GGUF uses "K-quant" super-blocks of 256 weights, split into 8 sub-blocks of 32 with their own 6-bit scales and minimums. The basic 4-bit K type works out to 4.5 bits per weight. The "_M" mix keeps some of the most sensitive tensors (parts of the value and down projections, and the output head) in a 6-bit type. The average across the file lands around **4.8 to 4.9 bits**, so an 8B file is about 4.9 GB.

The general rule: **file size on disk is a very good estimate of weight memory.** Almost every byte of a safetensors or GGUF file is weight. When you do not know a format's internals, `ls -l` the file and divide by the parameter count to get its true bits per weight.

### The KV cache: per token, per request, per batch

You met the formula in the [bandwidth lesson](/lessons/bandwidth-bound/). Here it is again, because now it is the main event:

```text
KV bytes per token  =  2 (K and V) × layers × kv_heads × head_dim × bytes per value

Llama 3.1 8B, bf16:   2 × 32 × 8 × 128 × 2  =  131,072 B  =  128 KiB
```

Read each factor. The 2 is because every layer stores a key vector and a value vector for every past token. Layers multiply because each layer has its own attention. And only the *KV* heads count, not the query heads, because queries are recomputed from the current token every step and never stored. That last point is why GQA's 8-instead-of-32 heads is a 4x discount on memory.

From the per-token number, everything else is multiplication:

| | Llama 3.2 1B | Llama 3.1 8B | Qwen3 30B-A3B | Llama 3.1 70B |
|---|---|---|---|---|
| layers × kv_heads × head_dim | 16 × 8 × 64 | 32 × 8 × 128 | 48 × 4 × 128 | 80 × 8 × 128 |
| KV per token (bf16) | 32 KiB | 128 KiB | 96 KiB | 320 KiB |
| one request at 8K | 0.25 GiB | 1 GiB | 0.75 GiB | 2.5 GiB |
| one request at 128K | 4 GiB | 16 GiB | 12 GiB | 40 GiB |
| 32 requests at 8K | 8 GiB | 32 GiB | 24 GiB | 80 GiB |

Notice the 70B's 32-user row: the KV cache alone would fill an H100. Notice the 8B at 128K: one user's cache weighs more than the whole model. And notice the MoE: 30 billion parameters but a smaller cache per token than the 8B, because it has only 4 KV heads. Cache size depends on the attention shape, not on the parameter count.

Two practical modifiers. First, store the cache in FP8 and every number in that table halves; most serving engines offer it as one flag, with some accuracy cost you would measure. Second, "context" means the whole conversation so far, prompt *plus* everything generated. A request that allows 8K tokens grows toward that over its life; a serving engine has to decide whether to reserve the worst case up front or allocate as it goes. That decision is what [paged attention](/lessons/prefix-caching/) is about.

### Activations: small, temporary, spiky

During a forward pass, each layer produces temporary tensors: the normed input, q, k and v, the attention output, and the MLP's wide intermediates. Those are <Term w="activations">The intermediate values computed during a forward pass. In training you keep them for the backward pass; in inference you can throw each one away as soon as the next layer has used it.</Term>. At inference, nobody needs them after the next layer runs, so PyTorch frees them right away. Only one layer's worth is alive at a time.

**In decode**, a step processes one new token per user. For Llama 3.1 8B the biggest temporaries are the gate and up projections, 14,336 numbers each. Per token, everything alive in one layer is roughly (4h + 3I) × 2 bytes ≈ 120 KB. Times 64 users is under 8 MB. Noise.

**In prefill**, the step processes the whole prompt at once, so every temporary is N tokens tall. At N = 8,192 the MLP alone briefly holds about 8,192 × 3 × 14,336 × 2 bytes ≈ 0.7 GB, and the full set is about 1 GB. It lasts milliseconds, but it is the *peak* that has to fit, not the average. Two things make the peak much worse if you are careless:

- **Computing logits for every position.** The output head turns each token's vector into 128,256 scores. If you run the model's forward on a 32K prompt and ask for logits at every position, that is 32,768 × 128,256 × 2 bytes ≈ 8.4 GB of scores, of which you need exactly one row (the last). Per token that is about 250 KB, *twice* the KV cache. Hugging Face's `generate` avoids this by asking for only the last position (it passes `logits_to_keep=1`; I checked this in the source of a current transformers 5 release); a bare `model(input_ids)` call does not.
- **Naive attention.** Textbook attention builds an N × N score matrix per head. At 16K tokens with 32 heads in bf16 that is 32 × 16,384² × 2 bytes = 16 GiB, per layer, before softmax makes an fp32 copy. Fused kernels (PyTorch's SDPA, FlashAttention) never build that matrix, so their memory grows with N, not N². That is the [FlashAttention lesson](/lessons/flash-attention/).

Real engines cap the activation peak on purpose. vLLM, for example, splits long prompts into chunks and never runs more than a set number of tokens through the model in one forward pass (its `max_num_batched_tokens` setting), so the spike has a known size no matter how long the prompt.

### Overhead: the memory nobody asked for

This is the bucket that makes careful predictions wrong by a gigabyte or three, so it is worth knowing its parts.

**The CUDA context.** The first time a process touches the GPU, the CUDA driver sets up its state: loaded GPU code for every kernel library you link (PyTorch ships many), internal tables, scratch areas. That memory belongs to the driver, not to PyTorch, so PyTorch's own counters never show it. On discrete GPUs it is typically a few hundred MB to around 1 GB per process, depending on versions and on whether the driver loads kernel code lazily. Measure yours; it is per process, so two Python processes using the GPU pay it twice.

**The caching allocator.** Asking the CUDA driver for memory (`cudaMalloc`) and giving it back is slow and forces the GPU to synchronize. So PyTorch keeps a <Term w="caching allocator">PyTorch's GPU memory manager. When a tensor is freed, it keeps the block for reuse instead of returning it to the driver, so the next allocation of a similar size is instant.</Term>: freed blocks stay in PyTorch's pool for the next tensor. That gives you two numbers:

- `torch.cuda.memory_allocated()`: bytes currently held by live tensors.
- `torch.cuda.memory_reserved()`: bytes PyTorch has taken from the driver, including cached free blocks. Always ≥ allocated.

The gap between them is memory that is free *to PyTorch* but not to anyone else. If the pool's free blocks are the wrong sizes for a new request (a 300 MB tensor needs 300 contiguous MB within a block, and the pool has ten 100 MB holes), PyTorch has to ask the driver for more. That waste is <Term w="fragmentation">Free memory broken into pieces too small or oddly placed to satisfy a request. The total free is enough; no single piece is.</Term>, and it is why "out of memory" can happen when the numbers say there should be room. A tensor that grows by concatenation is the worst case: Hugging Face's default `DynamicCache` appends each new token's keys and values with `torch.cat`, which allocates a slightly bigger tensor and frees the old one, every step, in every layer.

I watched the caching behaviour on my Mac's GPU backend, which has the same design: allocating a 256 MiB tensor made the driver hold 1,024 MiB (it reserves in big chunks); after `del`, live tensors were 0 MiB while the driver still held 1,024 MiB; only `torch.mps.empty_cache()` gave it back. On CUDA, `torch.cuda.empty_cache()` does the same job. You will see the CUDA version of this on the Spark.

**Everything else.** cuBLAS scratch space, NCCL buffers if you use several GPUs, and in serving engines, memory captured by CUDA graphs (pre-recorded sequences of kernel launches that cut Python overhead, each with its own fixed buffers). Budget about 1 to 3 GiB in total for a single-GPU server and then measure.

### The Spark: one pool, shared with everything

On an H100 or a 4090, the GPU's memory is its own. The operating system, your browser, your Python process's CPU-side objects all live in separate system RAM. The 80 GB is yours.

The Spark has no separate GPU memory. As you saw in the [virtual memory lesson](/lessons/virtual-memory/), its 128 GB is one pool shared by the CPU and GPU. So the budget has a new line at the top: **the OS, the desktop if one is running, every CPU process, and the page cache all come out of the same 128 GB**. Some of that is reclaimable (the kernel will drop cached file pages under pressure); some is not. And the failure mode is different: on a discrete card, running out gives you a polite Python exception. On the Spark, the pressure lands on the whole machine, and you may meet the kernel's OOM killer instead, or a frozen desktop while the system thrashes.

Two consequences for measuring. Tools built for discrete GPUs may not know what to report: on unified-memory systems `nvidia-smi`'s memory columns can read "Not Supported" or show something other than what you expect, so check what yours prints and do not trust it blindly. And the honest "how much can I still use?" number comes from Linux: `free -h`'s *available* column, or `MemAvailable` in `/proc/meminfo`. PyTorch's `torch.cuda.mem_get_info()` asks the CUDA driver the same question; compare the two on your machine, because on unified memory the driver's idea of "free" may not count file cache the kernel would happily drop.

### Serving engines take it all up front

A serving engine cannot allocate KV cache memory one request at a time with `torch.cat` and hope; it would fragment, and it would discover it was out of memory in the middle of a user's answer. So engines like vLLM grab the cache's memory once, at startup, and hand out fixed-size pieces of it.

vLLM's version, roughly (the details move between versions; check the docs for yours):

1. You set <Term w="gpu_memory_utilization">A vLLM setting (default 0.9): the fraction of the GPU's total memory this vLLM instance is allowed to use for everything, weights and cache included.</Term> (default 0.9). That is the instance's budget: 0.9 × total memory.
2. It loads the weights.
3. It runs a fake forward pass at the largest size it will ever run (`max_num_batched_tokens` tokens) and records the peak activation memory, plus whatever non-PyTorch memory has appeared.
4. Whatever is left of the budget becomes the KV cache pool, divided into blocks of a few tokens each. It logs the pool's size in tokens, and the "maximum concurrency" it implies: pool tokens ÷ `max_model_len`.

```python
    with open("/proc/meminfo") as f:
        for line in f:
            if line.startswith("MemAvailable:"):
                return int(line.split()[1]) * 1024 / GiB  # value is in KiB
    return float("nan")

    with open(f"/proc/{os.getpid()}/status") as f:
        for line in f:
            if line.startswith("VmRSS:"):
                return int(line.split()[1]) * 1024 / GiB
    return float("nan")

        torch.cuda.synchronize()
        free, total = torch.cuda.mem_get_info()
        alloc, resv, peak = (torch.cuda.memory_allocated(), torch.cuda.memory_reserved(),
                             torch.cuda.max_memory_allocated())
    else:
        free = total = alloc = resv = peak = float("nan")
    row = dict(label=label, t=time.time(), alloc=alloc / GiB, reserved=resv / GiB, peak=peak / GiB,
               cuda_free=free / GiB, cuda_total=total / GiB, os_available=meminfo_available(), rss=rss())
    print(" ".join(f"{k}={v:.2f}" if isinstance(v, float) else f"{k}={v}" for k, v in row.items()))
    return row
```

- **Weights** should be the most boring number on the page: within a few MB of 8,030,261,248 × 2 bytes. The few MB are small buffers that are not parameters (rotary embedding frequencies, for example). If yours is off by a whole GiB or more, a tensor got upcast or duplicated.
- **The CUDA context** shows up as memory gone from the OS with nothing allocated in PyTorch. Somewhere from a few hundred MB to a GB or so is normal on discrete GPUs; I don't know the Spark's number, which is why it is the first row you measure. - **KV growth** should be very close to L × 128 KiB per sequence, because `DynamicCache` holds exactly the keys and values and nothing else. The *peak* during each prefill will sit well above the steady value: that is the activation spike, plus the brief double copy when the cache is concatenated. Expect `reserved` to climb to the largest peak and stay there.
- **After `del` and `empty_cache()`**, `alloc` returns to the weights and `reserved` drops close to it. If `os_available` does not come back fully, part of the gap is the context, which only goes away when the process exits.
- **The edge** should land a little below your prediction, not above it. The common reasons: fragmentation (`reserved` well above `alloc` at failure), the prefill spike at large B × L (push prompts through in chunks to remove it), and the OS reserve being larger than you assumed (a desktop session, a browser, a forgotten notebook). ## Break It

**Ask for every logit.** Replace `generate` with a plain `model(input_ids)` on a 32K prompt. Predict first: 32,768 × 128,256 × 2 bytes. Watch `peak`. The fix is one argument: request logits only for the last position (`logits_to_keep=1` in current transformers; check the model's `forward` signature in your version). Lesson: a single tensor nobody needed can be bigger than the whole KV cache.

**Use textbook attention.** Load the model with `attn_implementation="eager"` and prefill 8K, then 16K tokens. Predict the score matrix: heads × N² × 2 bytes per layer, plus an fp32 softmax copy. At 16K that is tens of GiB for a single layer's temporaries; it will fail where SDPA sailed through. Lesson: the activation peak depends on the algorithm, not just the model, which is the whole reason FlashAttention exists.

**Run two at once.** Start two vLLM instances on the Spark, each with the default `gpu_memory_utilization`. The second one will fail at startup, or, worse, the first one's budget plus the OS will leave nothing for the second and the machine will start reclaiming and swapping. Then try a notebook that loads a model while one vLLM instance is running. Lesson: on unified memory, a serving engine's budget is a claim on the whole machine. Write the reserve you need into your launch script.

**Fragment the pool.** Generate 4,000 tokens one at a time at batch 8 with `DynamicCache`, snapping every 250 tokens, and plot `reserved − alloc`. Then repeat with a pre-sized cache (transformers' `StaticCache`, which allocates the full length once; check the docs for how to pass it to `generate`) and compare. Try also with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, which lets the allocator grow a segment in place instead of making new ones. Lesson: allocating once and slicing beats growing, which is exactly what serving engines do.

## Explain It Back

Answer each out loud before opening it.

<details>
<summary>1. How much memory does Llama 3.1 8B need to serve one user, and where does it go?</summary>

About 17 to 18 GiB at 8K context in bf16. The weights are 8.03 billion parameters × 2 bytes, 16.1 GB or 15 GiB, loaded once. The KV cache is 128 KiB per token (2 for K and V, × 32 layers × 8 KV heads × 128 dims × 2 bytes), so 1 GiB at 8K. Then one to two GiB of overhead: the CUDA context, library workspaces, and the activation peak during prefill. In 4-bit the weights drop to about 5 GB, but the cache and overhead don't change. The answer people usually give, "8 GB", assumes one byte per parameter and forgets the cache.

</details>

<details>
<summary>2. Count a model's parameters from its config, in under a minute.</summary>

Embedding is vocab × hidden. Each layer has attention, which is q (hidden × heads × head_dim), k and v (hidden × kv_heads × head_dim each, smaller with GQA) and o (the same size as q), plus an MLP of three hidden × intermediate matrices for SwiGLU, plus two norms of size hidden. Multiply by the number of layers. Add a final norm and, if embeddings are not tied, an output head the same size as the embedding. For Llama 3.1 8B: 2 × 525M + 32 × 218M + 4K = 8,030,261,248. Check for biases, extra norms, or experts in other families, and check the result against the checkpoint's total bytes.

</details>

<details>
<summary>3. How does memory scale with context, users, and model size? Which one bites first?</summary>

Weights scale with parameters and bytes per parameter and are paid once, no matter how many users. The KV cache scales linearly with context × users × (layers × KV heads × head_dim), so doubling either context or users doubles it. Activations scale with how many tokens you push through at once and are capped by chunking. For short chats and one user, the weights dominate. For many users or long contexts, the cache overtakes them quickly: at 128K context one user of an 8B model needs more cache than the whole model. So on a server, users × context is what you are really buying memory for, and FP8 KV caches, GQA and paging are the levers. On the Spark there is a second wall: everything you fit also has to be read every step, so bandwidth limits users before capacity does.

</details>

<details>
<summary>4. Why does vLLM grab 90% of GPU memory at startup, before any request?</summary>

So it never has to allocate during a request. At startup it loads the weights, runs a fake forward pass at its largest batch to measure the activation peak, and turns the rest of its budget (gpu_memory_utilization × total) into a pool of fixed-size KV blocks. Requests get blocks from the pool and give them back; there is no fragmentation and no surprise out-of-memory halfway through an answer. The cost is that the memory looks used even when idle. On a dedicated GPU that is fine. On the Spark, where the pool is the whole computer, the setting has to leave room for the operating system and everything else.

</details>

<details>
<summary>5. memory_allocated says 15 GiB, but the system says 17 GiB are gone. Where are the other 2?</summary>

memory_allocated counts only live tensors. memory_reserved adds the blocks PyTorch's caching allocator is holding for reuse, which after a prefill spike can be gigabytes. Below that, the CUDA context and library code belong to the driver, invisible to PyTorch's counters. Other processes using the GPU add their own. And on the Spark, the OS, CPU-side Python objects and the page cache share the same pool, so free -h sees all of it. To account for it: compare alloc, reserved, the drop in the driver's free memory, and the drop in MemAvailable, step by step from a cold start.

</details>

## Go Deeper

- **"Transformer Inference Arithmetic"**, kipply (Carol Chen), 2022. The calculations in this lesson (parameters, KV cache, FLOPs, batch size) worked through for real models. Read the memory sections alongside your calculator.
- **"Efficient Memory Management for Large Language Model Serving with PagedAttention"**, Woosuk Kwon et al., SOSP 2023. The vLLM paper. Its opening measurements of how much KV cache memory earlier servers wasted to fragmentation and over-reservation are this lesson's overhead section, at scale.
- **"Fast Transformer Decoding: One Write-Head is All You Need"**, Noam Shazeer, 2019. Multi-query attention, and the clearest early statement that KV memory is the decoding problem.
- **"GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints"**, Joshua Ainslie et al., EMNLP 2023. Why Llama 3's attention looks the way it does in your parameter count.
- **"AWQ: Activation-aware Weight Quantization for LLM Compression and Acceleration"**, Ji Lin et al., MLSys 2024. Where the group-of-128 scales come from, and why some weights deserve more care.
- **PyTorch docs, "CUDA semantics" (memory management section) and "Understanding CUDA Memory Usage"**. The caching allocator, `memory_reserved`, `PYTORCH_CUDA_ALLOC_CONF`, and the memory snapshot tool that shows every allocation on a timeline. Use the snapshot when t5's numbers don't add up.
- **vLLM docs, engine arguments and the memory/optimization pages**. The current meaning of `gpu_memory_utilization`, `max_num_batched_tokens`, `kv_cache_dtype` and friends. These move between versions; this is where to check.
- **The GGUF and quantization type descriptions in the ggml / llama.cpp repositories.** The exact block layouts of Q8_0 and the K-quants, if you want to compute bits per weight from first principles instead of from file sizes.
