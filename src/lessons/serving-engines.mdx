## The Problem

You have spent weeks on your server. You wrote a KV cache, then continuous batching, then a prefix cache with LRU eviction, then quantized the weights and bolted on a draft model. Every change got a row on the scoreboard. You are proud of the c = 16 row now.

Then you pull a container, type one command, `vllm serve meta-llama/Llama-3.1-8B-Instruct`, and point the same harness at it. It loads in a couple of minutes. At c = 1 it is a bit faster than your best server. At c = 64 it is a lot faster, and its p99 TTFT is a fraction of yours. Nothing you did was wrong. It just does all of it at once, plus things you didn't think of, and none of it in Python on the hot path.

That's not a reason to feel bad. It is the best possible moment to read their code. You know what every piece is *for*, because you measured the problem each one solves. Most people meet vLLM as a black box with 200 flags. You get to meet it as "oh, that's my batching loop, but they put it in its own process", "that's my prefix cache, but in blocks", "that's my launch overhead, gone".

This lesson is about two skills. The first is knowing what production engines do that yours doesn't. The second, which lasts longer, is how to read a real systems codebase of a few hundred thousand lines without drowning: find the loop, find the data structure, follow one request.

<Origin year="2022–2025" title="From one request per GPU to engines with their own schedulers">

In 2022, serving a language model mostly meant what your naive server did: a batch went in, the whole batch came out when its longest member finished. Orca (Yu et al., OSDI 2022) proposed scheduling at every *iteration*, one token step at a time, so finished requests leave and new ones join mid-flight. That is continuous batching.

In June 2023 a group at UC Berkeley released vLLM. Its idea, PagedAttention, borrowed virtual memory from operating systems: store the KV cache in small fixed-size pages instead of one big reserved slab per request, so memory waste drops from most of it to almost none and many more requests fit in a batch. The paper (Kwon et al., SOSP 2023) reported 2–4× the throughput of the best systems of the time. In December 2023, the LMSYS team released SGLang, whose RadixAttention kept KV cache from finished requests in a tree so later requests sharing a prefix (a system prompt, a few-shot example, a chat history) could reuse it automatically.

By 2024 GPUs were so fast that the bottleneck moved to the CPU: Python scheduling, preparing inputs, launching kernels. In January 2025 the vLLM team announced V1, a re-architecture built around exactly that problem: separate processes so CPU work overlaps GPU work, a simpler scheduler, a persistent batch, CUDA graphs everywhere. This lesson describes that V1 shape. It will keep changing; the shape changes slower than the files.

</Origin>

## The Idea

### Three processes and a loop

Your server was one process. One FastAPI app, one model, a lock, a thread pushing text into a queue. Everything happened in one place, so every piece of CPU work, tokenizing, building the SSE chunk, the Python of `generate` itself, competed for the same interpreter and the same GIL ([Processes, threads and the GIL](/lessons/processes-threads-gil/)).

vLLM V1 splits that into separate processes connected by sockets. Click around. Each box says what it does, which of your lessons built the toy version, and where to look in the source.

The split is the most important design decision in the whole engine, so here is why it exists.

**The API server** speaks HTTP and text: validating JSON, applying the chat template, tokenizing, and on the way back, turning token ids into text and writing SSE chunks. All of that is CPU work, sometimes a lot of it (tokenizing a 100,000-token document takes real milliseconds).

**The engine core** is a <Term w="busy loop">A loop that runs continuously, checking for work and doing it, rather than sleeping until woken. Good when the work never stops; it keeps one CPU core busy.</Term> in its own process. Each trip around the loop is one <Term w="engine step">One iteration of the engine loop: choose which requests run, do one forward pass for all of them together, and process the outputs. Each running request gets (usually) one new token per step.</Term>: ask the scheduler what to run, hand that to the GPU, wait, update every request with its new token, send outputs back. It owns the two most important data structures: the request queues and the KV block pool.

**The GPU worker** owns the model weights and the GPU. It turns "these requests, this many tokens each, their KV lives in these blocks" into tensors and runs the forward pass. With one GPU, check yourself whether the worker runs inside the engine-core process or alongside it: vLLM's docs describe one worker per GPU, and for a single GPU the executor can run it in-process. With tensor parallelism (later in this lesson) there is one worker process per GPU.

The processes talk over <Term w="ZMQ">ZeroMQ: a small library for sending messages between processes or machines over sockets, with queueing built in. vLLM uses it between the API server and the engine core.</Term> sockets, with requests and outputs serialized into compact messages. Why pay for serialization when threads could share memory for free? Because of the GIL. If tokenizing and detokenizing ran on threads inside the engine process, every millisecond spent on them would be a millisecond the scheduler couldn't run, and the GPU would sit idle waiting for its next instructions. In separate processes, the API server can detokenize step N's outputs while the engine core is already scheduling step N+1. Same reason your data loader uses worker processes.

### What one step does

Your continuous-batching loop from [Batching](/lessons/batching/) probably looked like this: if anything is waiting and there's room, run a prefill for it; then run one decode step for everyone. Two kinds of steps, decided by phase.

vLLM V1's scheduler doesn't have phases. It has a <Term w="token budget">The maximum number of tokens the engine will process in one forward pass (vLLM: max_num_batched_tokens). Every step, the scheduler hands out tokens to requests until this runs out.</Term>. Each step, it hands out tokens:

1. **Running requests first.** Each one that's decoding gets 1 token (more with speculative decoding, which checks several draft tokens at once). That's cheap, and starving them would stall their streams.
2. **Then waiting requests, oldest first,** while the budget lasts. A new request needs its whole prompt processed. If the prompt is longer than what's left of the budget, it gets only part of it now and the rest in later steps. That's <Term w="chunked prefill">Processing a long prompt in pieces across several steps, mixed in with other requests' decode tokens, so one huge prompt can't freeze everyone else's streams.</Term>.
3. **For each one admitted, ask the KV cache manager for room.** If there's no room, someone has to give up their memory. That's preemption, below.

The output is a small record: for each scheduled request, how many tokens, and which new blocks it got. The worker runs one forward pass over *all* of those tokens together, a mix of prefill chunks and single decode tokens. The attention kernels are built to handle that mix in one call.

Why is a mix a good idea? Remember from [Why ~17 tokens per second?](/lessons/bandwidth-bound/) that a decode step is limited by reading the weights, and the compute units are mostly idle during it. A prefill chunk is the opposite: lots of compute per byte read. Mixing them lets the prefill use the compute that decode was wasting, inside the same weight read. Your two-phase loop paid for the weight read twice.

Three things to take from the journey. The request crosses the process wall twice per token (out and back), and that is fine because each crossing is microseconds and overlaps GPU work. The KV memory grows one block at a time, never reserved up front, which is why so many requests fit. And the GPU never sees a "request" at all. It sees a batch of token positions and a table saying where each one's keys and values live.

### Memory: blocks, and what happens when they run out

You built this in [Paged attention and prefix caching](/lessons/prefix-caching/), so only the production details here.

At startup, vLLM loads the weights, runs one fake forward pass at the largest batch it will allow to measure peak activation memory, and then turns the remaining memory, up to `--gpu-memory-utilization` of the total, into a pool of KV <Term w="blocks">Fixed-size pages of KV cache. Each holds the keys and values of a fixed number of tokens (16 by default on CUDA at the time of writing) for every layer.</Term>. For Llama 3.1 8B in bf16 the arithmetic is: 32 layers × 8 KV heads × 128 dimensions × 2 (K and V) × 2 bytes = 128 KiB per token, so 2 MiB per 16-token block. If 80 GB of the Spark's 128 GB went to vLLM, minus 16 GB of weights and a few GB of activations, that's roughly 30,000 blocks, around half a million tokens of KV. (Spec-sheet memory, back-of-envelope; vLLM prints the real number of blocks at startup. Read it.)

A **block table** per request lists its blocks in order. Prefix caching works by hashing: each *full* block gets a hash of its tokens plus the hash of the block before it, so a hash names an entire prefix, not just 16 tokens. A new request computes its block hashes, looks them up, and reuses every hit. When a request finishes, its blocks go back to a free queue in LRU order, but keep their hashes, so they stay reusable until something needs the memory. That's the `get_computed_blocks` and `allocate_slots` pair in Figure 002.

When `allocate_slots` says no, the scheduler picks a victim. With the default first-come-first-served policy, at the time of writing it's the request at the back of the running list, the most recently admitted one. Under the priority policy it's the lowest-priority one. Two ways to take its memory:

Two ways to pay. <Term w="Recompute">Preemption by discarding a request's KV cache and putting it back in the queue; when it runs again, its prompt and generated-so-far tokens are prefilled from scratch.</Term> spends compute: the victim's prompt plus everything it generated gets prefilled again later. <Term w="Swap">Preemption by copying a request's KV blocks to CPU memory and copying them back when it resumes. Spends transfer bandwidth instead of compute.</Term> spends bandwidth: on a data-center GPU that's two trips across PCIe, which is far slower than the GPU's own memory. vLLM V0 supported both. V1, at the time of writing, recomputes: in the code, preempting a request frees its blocks and sets its count of computed tokens back to zero. Recompute is simpler, prefill is the fast part of inference, and with prefix caching on, the victim's freed blocks often survive in the cache until it comes back, so the "recompute" is partly a cache hit.

On the Spark, would swap be a good idea? Think about where "CPU memory" physically is on a GB10.

<Fragment slot="answer">

Swap exists to move bytes out of scarce, fast GPU memory into plentiful CPU memory. On the Spark there is one pool of 128 GB LPDDR5x shared by the CPU and GPU (spec sheet). "Swapping to CPU" would copy bytes from one part of the same memory to another, burning the same ~273 GB/s of bandwidth that decode needs, and freeing nothing that couldn't simply be given to the KV pool in the first place. The right move on unified memory is to make the KV pool bigger (`--gpu-memory-utilization`, leaving headroom for the OS and everything else, since they share the pool too) and let recompute handle the rare overflow.

</Fragment>
</Predict>

Preemption is a scheduler policy question in disguise. First-come-first-served is fair and simple: the newest arrival pays. A priority policy lets you say paying customers or interactive traffic never get preempted by batch jobs. SGLang's default is cache-aware, below. None is free. Every preemption is wasted work and a stall in someone's stream, which is why the `vllm:num_preemptions` counter on the `/metrics` endpoint is one of the first things to look at when a deployment's p99 goes bad.

### Taking the CPU out of the loop

Here is what your server still did on every decode token, even after batching: Python decided what to run, built input tensors from Python lists, copied them to the GPU, then launched every kernel of every layer one by one. Llama 3.1 8B has 32 layers and each launches a handful of kernels (norms, projections, attention, activation, adds), so a forward pass is hundreds of launches. Each costs a few microseconds of CPU time. Four hundred launches at 5 µs is about 2 ms per step (rough, check it in your profile).

Is 2 ms a lot? It depends entirely on how long the GPU takes. A decode step on the Spark reads 16 GB at about 273 GB/s: about 59 ms. On an H100, with about 3.35 TB/s (spec sheet), the same read takes about 5 ms. The same 2 ms of launch overhead is 3% of a Spark step and 40% of an H100 step. Production engines were built for the second case, which is why they fight so hard for every millisecond on the CPU side, and why you should expect their c = 1 advantage on your Spark to be smaller than the hype.

Four tricks, each one a box in Figure 001:

- <Term w="CUDA graphs">A CUDA feature that records a whole sequence of kernel launches once, then replays all of them with a single launch. The shapes and memory addresses have to stay the same between replays.</Term>. vLLM captures one graph per batch size it expects (a list of sizes, chosen at startup), pads each real batch up to the nearest captured size, and replays it. Most of the time in startup logs labelled "capturing CUDA graphs" is this. It also uses `torch.compile` to fuse small operations before capturing ([Why is Python slow?](/lessons/python-speed/) showed you what compile does). Attention, whose shapes vary the most, can be left out of the graph and run between pieces of it; vLLM calls this piecewise capture.
- **A persistent batch.** Instead of rebuilding input tensors from scratch every step, the model runner keeps them on the GPU and the scheduler sends only what changed: which requests joined, which left, which got new blocks. Most steps, almost nothing changes.
- **Overlapping steps.** With async scheduling, the engine core can schedule step N+1 while the GPU is still running step N, so the GPU never waits for Python. SGLang has the same idea under the name overlap scheduler. Check each engine's docs for whether it's on by default in your version.
- **Paged attention kernels.** The attention backend is a separate pluggable piece: FlashAttention, FlashInfer, Triton kernels and others, chosen per GPU and model. Each one reads keys and values from scattered blocks through the block table, and handles a batch where some requests contribute 2,000 prompt tokens and others contribute one. Writing one of these is the next lesson, [FlashAttention and kernels](/lessons/flash-attention/).

### SGLang: same skeleton, different bets

Open SGLang and you'll find the same shape: a tokenizer manager in the HTTP process, a scheduler process running a loop, a detokenizer manager process, a model runner with CUDA graph capture, paged KV memory, an OpenAI-compatible API. The differences are in what it treats as the first-class problem.

**RadixAttention.** vLLM's prefix cache is a hash table of full blocks. SGLang's is a <Term w="radix tree">A tree where each edge is labelled with a sequence of tokens, and a path from the root spells out a prefix. Shared prefixes share a path, so looking up a new prompt means walking down as far as it matches.</Term> of everything it has computed. Each node holds the token sequence on its edge and the indices of the KV memory for those tokens. A new request walks down the tree as far as it matches, reuses all the KV along the way, and only prefills the rest. When memory runs low, it evicts least-recently-used *leaves* first, so the shared trunk (the system prompt everyone uses) survives longest.

**Cache-aware scheduling.** Because the tree shows which waiting requests share prefixes, SGLang's default schedule policy, at the time of writing, is longest-prefix-match: it prefers waiting requests that will hit the most cache, and there's also a depth-first ordering that groups requests sharing a subtree. Plain first-come-first-served is an option. The trade is throughput against fairness: a request with an unusual prefix can wait longer.

**Structured outputs.** Ask a model for JSON and it will usually comply. "Usually" is a problem when a parser on the other end crashes. <Term w="Constrained decoding">Generating text that is guaranteed to match a format (a JSON schema, a regular expression, a grammar) by forbidding, at every step, any token that would break the format.</Term> fixes it: a grammar compiler turns your schema into a state machine, and at each step the engine builds a mask of tokens that are legal from the current state, and the sampler sets every other token's probability to zero. The SGLang paper also introduced jump-forward decoding: when the grammar allows only one possible continuation (the `"name": "` after `{`), skip the model and append those tokens directly. Both engines now support structured outputs through pluggable grammar backends (XGrammar, llguidance, Outlines); SGLang's grammar backends sit in `python/sglang/srt/constrained/` at the time of writing, vLLM's in `vllm/v1/structured_output/`. The mask is computed on the CPU while the GPU runs the forward pass, which is why you saw `get_grammar_bitmask` sitting between "execute" and "sample" if you peeked at vLLM's step.

### The other two engines you'll hear about

**TensorRT-LLM** is NVIDIA's engine. Historically it compiled a model ahead of time into an optimized engine for a specific GPU and set of shapes, then served it with in-flight batching (NVIDIA's name for continuous batching) and paged KV cache. Its edge is kernels: NVIDIA writes the FP8 and FP4 paths for its own hardware first. Newer releases moved toward a PyTorch-based workflow that's closer to vLLM in how you use it; check the current docs before assuming either. NVIDIA has a DGX Spark playbook for it too.

**llama.cpp** is a different animal: C and C++, no Python on the hot path, designed for one or a few users on whatever hardware you have, CPU, Apple Metal, CUDA, and more. It loads models from <Term w="GGUF">llama.cpp's single-file model format: weights (usually quantized), tokenizer and metadata in one file, laid out so it can be memory-mapped and used without parsing.</Term> files that it memory-maps, so a model "loads" by mapping pages ([What happens when you save a file?](/lessons/files-and-disks/)). Its quantization formats squeeze models to 4 bits and below for machines without much bandwidth. It's the natural choice on unified-memory machines like your Mac and a good one on the Spark at batch 1. It also ships `llama-server` with an OpenAI-compatible API, which means your harness works against it unchanged. Its throughput at high concurrency is not its goal.

### Beyond one GPU: tensor parallelism

A 70B model in bf16 is 140 GB. It does not fit on one 80 GB GPU, and even if it did, decode would read 140 GB per token. The standard fix inside a machine is <Term w="tensor parallelism">Splitting each layer's weight matrices across several GPUs so every GPU holds a slice of every layer, computes its part of each token, and they combine partial results with fast communication.</Term>.

Why does this help decode? Each GPU reads only its share of the weights per token, so with 2 GPUs each step reads half the bytes from each GPU's memory, in parallel. The cost is the <Term w="all-reduce">A collective operation where every GPU contributes a tensor and every GPU ends up with the sum. Its time is set by the interconnect's latency and bandwidth.</Term>: two per layer, so 64 per token for a 32-layer model. Each one is small at batch 1 (one hidden vector, 4,096 × 2 bytes = 8 KB), so it's latency that matters, not bandwidth. Inside a server, GPUs talk over NVLink at hundreds of GB/s with microsecond latency, and tensor parallelism is close to free. Across two Sparks linked by their ConnectX-7 network ports, each all-reduce pays a network round trip, and 64 of them per token add up; that's why NVIDIA's multi-Spark playbooks are mainly about fitting models that don't fit in one Spark, not making small ones faster. In vLLM it's one flag, `--tensor-parallel-size`, and one worker process per GPU. The other splits, pipeline parallelism (layers on different GPUs) and expert parallelism for mixture-of-experts models, come up in [Training on many GPUs](/lessons/distributed-training/).

### The frontier: splitting prefill from decode

Go back to the mixed batch. Mixing prefill into decode steps is good for throughput, but every prefill chunk makes that step longer for every decoding request in it. A user mid-stream sees a stutter whenever someone else's long prompt arrives. Chunking caps the stutter but doesn't remove it. And the two phases want different hardware: prefill wants compute, decode wants bandwidth and lots of memory for KV.

<Term w="Disaggregated serving">Running prefill and decode on separate groups of GPUs (or machines), transferring each request's KV cache from the prefill group to the decode group after its prompt is processed.</Term> takes this to its conclusion. Two 2024 papers made the case: DistServe (Zhong et al., OSDI 2024) showed that separating the phases and sizing each pool for its own latency target serves more requests within both a TTFT and an inter-token-latency target; Splitwise (Patel et al., ISCA 2024) argued from production traces at Microsoft that the phases could even run on different GPU generations. Mooncake, from Moonshot AI, built a whole serving system around a distributed KV cache. The cost is shipping KV: for Llama 3.1 8B, a 2,000-token prompt is 2,000 × 128 KiB = 250 MiB of KV to move before the first decode step. That needs fast networking, and libraries like NVIDIA's NIXL exist to move it. Both vLLM (through KV connectors) and SGLang support disaggregated setups at the time of writing; the details move fast, so read their docs, not this paragraph.

You won't run disaggregation on one Spark. You should be able to explain it, because it's the current answer to "TTFT and inter-token latency fight each other; what do you do at scale?"

What the shape should look like. These are reasoned ceilings and expectations, not measurements; the Spark numbers are from spec-sheet bandwidth.

**c = 1 tok/s.** The ceiling is still ~17 tok/s (16 GB per token at ~273 GB/s). Both engines should get a large fraction of it, plausibly 85–95%, and beat naive `generate` clearly. If your own batched server is within 10–20% of them at c = 1, that's honest: at batch 1 on a bandwidth-bound box there isn't much left to win. Quantized rows break the ceiling, of course, because they read fewer bytes.

**c = 64 throughput.** This is where the engines earn their reputation. A step at batch 64 still reads the weights once, plus the KV of 64 sequences (at ~300 tokens each, about 64 × 300 × 128 KiB ≈ 2.5 GB). So a step costs roughly (16 + 2.5) GB ÷ 273 GB/s ≈ 68 ms for 64 tokens: a ceiling around 900 tok/s. Expect a good fraction of that. Your own server probably falls further from its ceiling here than at c = 1, because the CPU work per step grows with the batch and yours is all on the hot path.

**TTFT p99 at c = 64.** Chunked prefill and the token budget keep it bounded. Compare to your server: if yours runs a full prefill phase whenever someone arrives, its p99 TTFT and its inter-token stutter should both be visibly worse.

**Shared system prompt.** Both engines should show a large TTFT drop on cache hits, like your prefix cache. SGLang's default cache-aware policy may do better on throughput at c = 16 with many shared prefixes, at some cost to fairness. Look at the distribution, not just the median.

**Profiles.** On the Spark at c = 16, expect the GPU trace to be dominated by matrix-multiply kernels reading weights, with attention a small slice at short context that grows as contexts get long. The engine-core flame graph should be mostly waiting. Your own server's flame graph should show Python doing real work between GPU calls. `--enforce-eager` should open small gaps between kernels; on the Spark they'll be a small share of a long step, which is the H100-vs-Spark arithmetic from the Idea section, measured.

**Against Fireworks.** Still far behind on per-stream tok/s; that's HBM bandwidth and probably lower precision on their side, not software. Write down the ratio at c = 1 and compare it to the ratio of memory bandwidths. If the two ratios are close, you've found the floor: what's left of the gap is hardware.

## Break It

**Turn off CUDA graphs.** Restart vLLM with `--enforce-eager` and rerun c = 1 and c = 64. Check your prediction. Startup also gets faster, since nothing is captured. If the slowdown is small, you've confirmed that on a slow-memory box the CPU overhead is a small slice; on a data-center GPU the same flag hurts far more.

**Turn off prefix caching.** vLLM: `--no-enable-prefix-caching`. SGLang: its disable-radix-cache flag. Rerun the shared-system-prompt set. TTFT on repeated prompts jumps back to full prefill. Then look at `vllm:prefix_cache_hits` and `vllm:prefix_cache_queries` on `/metrics` with caching back on, and compute the hit rate yourself.

**Starve the KV pool.** Restart vLLM with a small `--gpu-memory-utilization` (or `--num-gpu-blocks-override` to a few hundred blocks) and run c = 64 with long outputs. Watch the startup log's block count, then `vllm:num_preemptions` climb on `/metrics` and the p99 of e2e latency blow up while throughput drops: requests are recomputing prefills they already did. This is the failure mode behind "it was fine until traffic doubled".

**Make it your naive server.** `--max-num-seqs 1`. vLLM now serves one request at a time. Run c = 16. TTFT climbs as (c − 1) × service time, exactly your baseline staircase, though each service is faster. Everything that makes vLLM good at serving many users is the scheduler; take it away and a fast kernel stack still queues.

**Hang up mid-stream.** Start a 1,024-token request against vLLM and kill the client after a second. Watch `vllm:num_requests_running` drop: the API server notices the disconnect and aborts the request, freeing its blocks. Your naive server kept generating for a ghost. Find the abort path in the code (the engine core has an aborts queue it drains every step).

## Explain It Back

Answer each out loud, as if in an interview, before opening the answer.

<details>
<summary>Why does vLLM run the API server and the engine core as separate processes instead of threads?</summary>

Because of the GIL and because the GPU must never wait for Python. Tokenizing, detokenizing and writing SSE chunks are CPU work that grows with the number of users. If they ran on threads in the same process as the scheduler, they would take turns holding the GIL with it, and every millisecond they held it would be a millisecond the next step wasn't scheduled and the GPU sat idle. In separate processes they run truly in parallel on other cores: the API server can turn step N's tokens into text while the engine core schedules step N+1. The price is serializing requests and outputs over sockets, which is microseconds per message and overlaps GPU work.

</details>

<details>
<summary>Walk me through one engine step in vLLM.</summary>

The engine core's loop calls the scheduler. The scheduler has a token budget for this forward pass. It gives each running request its next token (or a few with speculative decoding), then admits waiting requests oldest first, chunking a long prompt if the budget runs out. For each, it asks the KV cache manager for blocks, reusing cached prefix blocks by hash. If memory runs out it preempts the newest running request by freeing its blocks for recompute later. The output is a small record of which requests run, how many tokens each and which new blocks they got. The GPU worker applies that diff to its persistent batch, builds positions and block tables, runs one forward pass over the mixed batch, replaying a CUDA graph if the shape matches, and samples. The scheduler updates each request with its new token, checks stop conditions, and sends outputs back to the API server, which detokenizes and streams them.

</details>

<details>
<summary>Recompute vs swap for preemption: what does each cost, and which would you pick on the Spark?</summary>

Recompute throws the victim's KV away and prefills its prompt plus generated tokens again later: it costs compute, which is the cheap part of inference, and prefix caching often makes it partly free because the freed blocks are still cached when the request returns. Swap copies the KV to CPU memory and back: it costs bandwidth, two trips over PCIe on a normal server, and memory on the CPU side. On the Spark, CPU and GPU share one LPDDR5x pool, so swap would copy bytes within the same memory, using the bandwidth decode needs and freeing nothing you couldn't just give to the KV pool. Recompute, and a bigger pool.

</details>

<details>
<summary>How does serving scale from one GPU to eight, and then to a cluster? What breaks at each step?</summary>

On one GPU, throughput grows with batch size until the KV cache fills memory or prefill compute saturates; past that, requests queue or get preempted. Across eight GPUs in one server, you either run eight independent copies behind a load balancer (data parallelism: throughput scales nearly linearly, nothing shared, but each copy must fit on one GPU) or split one model across them with tensor parallelism (each GPU reads an eighth of the weights per token, two all-reduces per layer over NVLink, so per-token latency drops and bigger models fit). Tensor parallelism stops paying off across machines because every all-reduce becomes a network round trip, so across a cluster you go back to data parallelism over replicas, add pipeline or expert parallelism for models too big for one node, and route requests to replicas that already hold their prefix in cache. At the largest scale, prefill and decode get their own pools, and the bottleneck becomes moving KV caches between them.

</details>

<details>
<summary>Why are DistServe and Splitwise interesting? What problem does disaggregation solve, and what does it cost?</summary>

Prefill and decode want different things: prefill is compute-bound and bursty, decode is bandwidth-bound and steady. On the same GPUs they interfere: every prefill chunk stretches the decode steps of everyone in the batch, so TTFT and inter-token latency trade off against each other, and you can't size the hardware for both. Disaggregation runs them on separate pools, so each can be sized and tuned for its own latency target, even on different GPU types. The cost is shipping each request's KV cache from the prefill pool to the decode pool before decoding starts: for an 8B model that's 128 KiB per token, about 250 MiB for a 2,000-token prompt, so it needs fast interconnects and careful overlap, and it adds a hop to TTFT.

</details>
