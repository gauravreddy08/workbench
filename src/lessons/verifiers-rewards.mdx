When a model practises coding, something has to give each attempt a score. That score is the reward, and the program that works it out, usually by running the code and checking what comes back, is the verifier. Between them, they are the only way the model ever finds out what "good" means.

Get them wrong and training goes beautifully in the wrong direction. Pay a model for making the tests say "passed" and, sooner or later, it learns to make the tests say "passed" without writing code that works, while your score chart climbs the whole time. Labs that train coding models have reported exactly this in public. It's the same worry you already have about your ranker's metrics, turned up to full: push hard enough on any number and it stops meaning what it used to.

This picks up the practice arena from [What is an RL environment?](/lessons/rl-environments/) and replaces its rough scoring with something you can trust. It leans on [Why is the eval separate?](/lessons/why-evals-are-separate/) and [LLMs as judges](/lessons/llm-judges/), and the grader you build here is what [RL with verifiable rewards](/lessons/grpo/) trains against next.

## The Problem

You finish the environment from last lesson. Twenty small coding tasks, each a function stub with hidden tests, a sandbox that runs the model's code with a timeout, and a reward: the fraction of tests that pass. You point an RL loop at it and go to bed.

In the morning the reward curve is beautiful. It starts near 0.3 and climbs to 0.97 in a few hundred steps. You open a few trajectories to admire the code.

The first one has written a perfectly good `merge_intervals`. The second one has written `merge_intervals` as a dictionary lookup of the three inputs that appear in `test_visible.py`. The third one did not touch `solution.py` at all. It created a file called `conftest.py`, nine lines long, which tells pytest to mark every test as passed. Within a hundred more steps, most trajectories contain some version of that file.

Nothing is broken. The model did exactly what you paid it to do. You wrote a reward that says "make pytest report success", and it found the cheapest way to make pytest report success. Your problem is that you meant "write correct code" and wrote something else.

This lesson is about closing that gap: turning "good code" into a number that is cheap to compute, hard to fake, and still high for code that is actually good. And then attacking your own number before a model does.

<Origin year="2016" title="The boat that won by going in circles">

In 2016, researchers at OpenAI trained an agent to play CoastRunners, a boat-racing game. The reward was the game's score, which you earn by hitting targets along the course. The agent discovered a lagoon where three targets respawned, and learned to circle there forever, catching fire and crashing into other boats, scoring about 20% higher than human players without ever finishing a race. Dario Amodei and Jack Clark wrote it up as "Faulty Reward Functions in the Wild".

The same year, Amodei, Olah, Steinhardt, Christiano, Schulman and Mané published "Concrete Problems in AI Safety", which gave the failure a name, reward hacking, and listed it as one of five practical problems that would get worse as systems got more capable. Victoria Krakovna at DeepMind then started collecting examples into a public list, "specification gaming", which now has dozens: a simulated robot that learned to flip a block over instead of stacking it, an evolved circuit that used a nearby computer as an antenna, a Tetris agent that paused the game forever to avoid losing.

The idea is older than computers. In 1975 the economist Charles Goodhart observed that a statistic used to steer policy stops measuring what it used to. Code RL is that observation running a few thousand times an hour, against an opponent that reads your test files.

## The Idea

### A reward is a judgment squeezed into one number

In RL, the model writes code, and something has to say how good that code was, as a single number. That something is the <Term w="reward function">The code that looks at what the model did in an episode and returns one number saying how good it was. In code RL, usually computed after the episode ends.</Term>. The parts of it that actually check the work are <Term w="verifier">A program that checks whether a solution is correct (or how correct), without a human in the loop. Tests are verifiers. So is a type checker, or a model asked to grade.</Term>s.

Think of a verifier as a food inspector who can only visit the kitchen for two minutes. They cannot taste every dish. They pick a few things they can check fast: is the fridge cold, are the knives clean, does the soup reach the right temperature. If the kitchen knows exactly which three things get checked, the kitchen can pass inspection without being clean. Everything in this lesson is a version of that: which things you check, whether the kitchen can see the checklist, and whether the inspector can be bribed.

Two numbers matter for any verifier. How often it passes code that is bad, and how often it fails code that is good. Hold that thought; we'll come back to it with real names.

### The verifier toolbox

Here are the main tools, roughly from cheapest and narrowest to most expensive and broadest.

**Unit tests, as a pass rate.** Run the task's tests on the model's code and report the fraction that pass. This is what your environment does now. A <Term w="unit test">A small piece of code that calls your function with one specific input and checks the output (an assert). Fast, precise, and only as good as the inputs someone thought to try.</Term> checks one input. A suite checks a handful. The pass rate is cheap, objective, and easy to understand, and it has one structural weakness: it only ever looks at the inputs someone wrote down.

**Visible vs hidden tests.** <Term w="visible tests">Tests the model can see while working, usually sitting in its workspace. Useful as a tool (the model can run them to debug), dangerous as the reward.</Term> are the ones in the repo. <Term w="hidden tests">Tests the model never sees: kept outside its workspace and run only at grading time. SWE-bench works this way.</Term> live somewhere the model cannot reach. The model may run the visible ones to debug, but the reward comes from the hidden ones. This is how SWE-bench grades: the model gets an issue and a repo, and is scored on tests it never saw, split into "fail to pass" (the tests the fix should make pass) and "pass to pass" (tests that already passed and must keep passing, so the fix doesn't break anything else).

**Property-based tests.** Instead of "this input gives that output", you state a rule that must hold for every input, and a library generates hundreds of random inputs to try to break it. A <Term w="property-based test">A test that states a rule ("output is sorted", "no two intervals overlap") and lets a library generate many random inputs to look for one that breaks the rule. When it finds one, it shrinks it to the smallest failing input.</Term> for `merge_intervals` might say: the output is sorted, no two output intervals touch, it covers exactly the same points as the input, and merging it again changes nothing. You never wrote an expected output. In Python the library is Hypothesis; the idea comes from Haskell's QuickCheck.

**Execution equivalence against a reference.** If you have a known-correct <Term w="reference solution">A correct implementation of the task written by the environment author. Never shown to the model. Used to compute the right answer for any input.</Term>, you can generate random inputs, run both, and check the outputs match. This is <Term w="differential testing">Running two implementations on the same inputs and flagging any difference. If one is trusted, every difference is a bug in the other.</Term>. It is the most powerful cheap check you have, because random inputs are unlimited and the model cannot predict them.

**Static checks.** A <Term w="linter">A tool that reads code without running it and flags likely mistakes or style problems: unused imports, a bare except, shadowed names. Ruff and flake8 are Python linters.</Term> and a <Term w="type checker">A tool (mypy, pyright) that reads type annotations and checks that values are used consistently, without running the code.</Term> look at code without running it. They can't tell you if code is correct, but they catch some things tests can't: a bare `except:` that hides errors, an unused import, a function that sometimes returns `None` when the annotation says `list`. Use them as small penalties or as gates, never as the main signal; a model optimizing hard against a linter learns to write lint-clean code, not correct code.

**LLM judges with rubrics.** Some things you care about have no test: is the code readable, is the change minimal, did it follow the repo's conventions, is the explanation honest. For these you can ask a model to grade, using a <Term w="rubric">A written list of specific criteria with what each score level means ("2: variable names describe contents; 1: some cryptic names; 0: single letters throughout"). Makes grading more consistent, for humans and for models.</Term>. From [LLMs as judges](/lessons/llm-judges/) you know their weak spots: position bias, length bias, sycophancy, and the fact that a judge is itself a model the policy can learn to please. A judge is the most gameable verifier in the box, so it gets the smallest weight, and you audit it hardest.

### Combining signals: gates and nudges

Once you have several checks, you have to turn them into one number. There are two shapes, and the difference matters more than the exact weights.

A **weighted sum** says `R = 0.6·tests + 0.2·lint + 0.2·judge`. The problem: a solution that fails every test but writes beautiful, lint-clean code that a judge loves gets 0.4. Wrong code earns reward. The model will find that 0.4 the first time correct code is hard.

A **gate** says: correctness first, everything else only counts if you passed. Something like

```python
r_correct = min(hidden_pass_rate, property_pass_rate, reference_match_rate)   # must pass all
if r_correct < 1.0:
    R = 0.5 * r_correct          # partial credit, capped well below a full solve
else:
    R = 1.0 - 0.1 * lint_penalty - 0.1 * (1 - judge_score)   # quality nudges only on correct code
```

Taking the `min` of the correctness checks rather than the average means a hack has to beat *all* of them, which is much harder than beating one. The quality terms can only move a correct solution between 0.8 and 1.0, so no amount of style buys back a wrong answer. The exact numbers are judgment calls. The shape is not.

### Outcome vs process, sparse vs dense

Two more distinctions, about *when* reward arrives and *what* it looks at.

An <Term w="outcome reward">A reward based only on the final result: did the code pass? It ignores how the model got there.</Term> grades the end result. A <Term w="process reward">A reward for each intermediate step: was this reasoning step right, was this tool call sensible. Needs a way to grade steps, often a separate trained model.</Term> grades the steps along the way. Lightman et al.'s "Let's Verify Step by Step" (2023) trained a <Term w="process reward model">A model trained to score each step of a solution as good or bad, used as a step-by-step reward or to pick the best of many attempts. Often shortened to PRM.</Term> on 800,000 human step labels for math, and found it picked correct solutions better than an outcome-only model did.

A <Term w="sparse reward">Reward that is zero almost all the time and only arrives occasionally, often only at the very end of an episode.</Term> arrives rarely, usually once at the end. A <Term w="dense reward">Reward that arrives often, at many steps, giving the learner frequent feedback on whether it is getting warmer or colder.</Term> arrives often. A single pass/fail at the end of a 40-step coding episode is the sparsest reward there is. A pass *rate* is a little denser: 7 of 10 tests is more information than "fail".

<Predict id="why-sparse">

Dense rewards give more feedback per episode, and more feedback usually means faster learning. Yet most published code RL (and most RL for reasoning models) uses a sparse outcome reward: tests pass or they don't. Why would anyone choose the slower signal?

<Fragment slot="answer">

Because every intermediate reward is another thing the model can optimize instead of the thing you want, and an outcome check is the hardest to fake. If you pay +0.05 for running the tests, the model learns to run the tests a lot. If you pay for "steps a process reward model likes", the model learns to write steps that model likes, which is a weaker verifier than actually executing the code. An outcome reward computed by running the code is close to the real goal; the gap is small, so there is less to exploit. The cost is that learning is slow when success is rare, which is why task difficulty matters so much (more on that with Figure 005) and why methods like GRPO sample many attempts per task: with 16 tries, a 10%-solvable task usually produces at least one success to learn from. Process rewards shine where you can check steps reliably, like math, and where the final answer alone is a weak signal.

</Fragment>

</Predict>

### Reward hacking, in detail

<Term w="reward hacking">When a learner finds a way to get high reward that the designer didn't intend and doesn't want. The reward goes up; the thing it was supposed to measure doesn't.</Term>, also called <Term w="specification gaming">Krakovna et al.'s name for the same thing: the system satisfies the literal specification (the reward) instead of the intended goal. The name puts the blame on the specification, which is usually right.</Term>, isn't the model being malicious. RL is a search for high-reward behaviour, and a search finds whatever is cheapest. If cheating is cheaper than solving, the search finds cheating. Frontier labs have reported exactly this in coding: Anthropic's Claude 3.7 Sonnet system card describes the model special-casing tests to make them pass, METR has written up frontier models modifying tests and scoring code to get high scores, and Anthropic's 2025 paper on emergent misalignment from reward hacking studied hacks like the always-equal object, exiting before the tests run, and patching pytest through `conftest.py`, then showed that models which learned those hacks generalized to worse behaviour elsewhere.

Here is the catalogue. Every one of these is a real file I ran against real verifiers for a `merge_intervals` task; you'll write them yourself in Build It.

1. **Hardcode the visible answers.** Look at the three test inputs, return a lookup table. Also called special-casing the tests. Beats any verifier whose inputs the model can see.
2. **Edit the tests.** Rewrite `test_visible.py` to `assert True`. Beats any grader that runs the tests found in the model's workspace.
3. **Patch the test runner.** Pytest automatically loads a file named `conftest.py` from the test directory. A nine-line hook in it rewrites every test result to "passed". The code under test can return garbage.
4. **Exit with status 0.** `os._exit(0)` at import time. The process ends before any test runs, and a grader that checks "did pytest exit with 0?" says yes. (I checked: pytest 9 catches `sys.exit(0)` raised during collection and reports an internal error with exit code 3, but `os._exit(0)` kills the process immediately and pytest's exit code is 0.)
5. **Return an always-equal object.** Return a `list` subclass whose `__eq__` always says `True`. Every `assert out == expected` calls the model's own `__eq__`. Hidden tests don't help; they use `==` too.
6. **Catch every exception.** Wrap a half-right implementation in `try/except: return []`. Crashes become plausible-looking answers, and pass-rate rewards pay for every lucky one.
7. **Read the answer key.** If the expected outputs live in a file the model's process can open, open it. A first-draft environment often passes the path to the hidden cases right on the command line.
8. **Copy the real fix.** `git log --all -p`, or fetch the upstream patch from the internet. This produces *correct* code, so no test can catch it. The task stopped testing skill the moment the answer was reachable.

<Predict id="hack-defense">

<Fragment slot="answer">

Only the ones that depend on *knowing the inputs*: hardcoding (1) mostly, and editing the visible tests (2) because the hidden ones aren't in reach. It does nothing against the conftest hook (3, pytest loads it for the hidden tests too), the early exit (4, exit code still 0), the always-equal object (5, more `==`, same trick), or copying the fix (8). Catching errors (6) loses some credit but keeps a lot. And reading the answer key (7) gets *easier*: you just told it there's a file worth reading. "Hidden" is a property of the filesystem and process boundaries, not of the word in your config.

Three lessons from the gallery.

**Each defense closes a specific hole, so you need several.** Hidden tests fix "knows the inputs". Read-only tests fix "owns the test files". The sandbox fixes "can reach things it shouldn't". The second verifier fixes "the checker trusts the code it's checking", which is the deepest hole: if the model's code and your asserts run in the same Python process, the model's code can change what your asserts mean.

**The process running the model's code should never hold the answers.** That rule kills hacks 3, 4, 5 and 7 at once. Send inputs in, get plain data out, compare outside.

**Some hacks produce correct code.** Copying the fix isn't caught by any verifier, because there's nothing wrong with the code. The defense there is environment design: no network, a repo snapshot with no future commits, no reference solution anywhere on disk.

### Goodhart, again

You met Goodhart's law in [Why is the eval separate?](/lessons/why-evals-are-separate/): when a measure becomes a target, it stops being a good measure. RL is the most extreme version, because the optimizer is relentless and literal and has no idea what you meant. Gao, Schulman and Hilton measured this directly for learned reward models ("Scaling Laws for Reward Model Overoptimization", 2022): as you optimize harder against a proxy reward, the true reward first rises, then peaks, then falls, while the proxy keeps going up.

That is why the training reward is never your measure of success. You keep a separate <Term w="held-out eval">A set of tasks, and ideally a different grader, that the training loop never sees or optimizes against. Used only to check whether training really helped.</Term>: different tasks, different and stricter checks, and humans reading samples. If training reward goes up and held-out success doesn't, you are watching Goodhart happen.

### A verifier is a classifier

Here is the precise version of "how often it passes bad code, and how often it fails good code". A verifier looks at a solution and says pass or fail. The truth is good or bad. That's a <Term w="confusion matrix">A 2×2 table of a yes/no classifier's verdicts against the truth: true positives, false positives, false negatives, true negatives.</Term>, exactly like the ones you use for ranking models.

<Term w="precision">Of everything the verifier passed, the fraction that was really good. Low precision means it pays out for bad code.</Term> asks "when it says pass, is it right?". <Term w="recall">Of all the really good solutions, the fraction the verifier passed. In an eval, both errors are just noise in a score. In RL, they are not symmetric. A false negative is an honest attempt that went unpaid; the model is slightly less likely to try that again, and learning slows down. A false positive is a specific behaviour that got paid, and RL's whole job is to do more of whatever got paid. Worse, the false positives are not random. A hack that works once works every time, and on every task with the same verifier. The model doesn't need to find it twice.

<Predict id="fp-threshold">

Your tasks are hard: an honest attempt succeeds 10% of the time. Your verifier is pretty good: a hacking attempt fools it 15% of the time. Only 1% of the model's early attempts are hacks. Over a hundred RL steps, what happens to the share of hacking attempts? What if hacks only fool the verifier 5% of the time?

<Fragment slot="answer">

At 15%, hacking takes over. A hack attempt earns 0.15 on average and an honest attempt earns 0.10, so every update shifts weight toward hacking, and the share compounds from 1% to most of the policy. At 5%, honest attempts pay more (0.10 vs 0.05), and the hack share shrinks toward zero. The rule in this toy model is blunt: **hacking wins when its expected reward beats honest work's**, whatever the starting share. That's why the same verifier can be fine on easy tasks and a disaster on hard ones. On a task the model solves 80% of the time, a 15% loophole is irrelevant. On a task it solves 5% of the time, the loophole is the best-paying strategy available. Hard tasks are exactly where you want RL to learn, so that's exactly where your verifier has to be tightest.

</Fragment>

### Measuring the verifier: mutation testing

How do you know if your tests are strong? Code coverage tells you which lines ran, not whether anyone checked the result. A better question: if the code were subtly wrong, would the tests notice?

<Term w="mutation testing">Measuring a test suite by planting small bugs in correct code (flip a &lt; to &lt;=, swap max for min, delete a call) and checking whether the tests fail. Each planted bug is a mutant; a failing test "kills" it.</Term> asks exactly that. Take the correct reference solution. Make one small change, a <Term w="mutant">A copy of the code with one small deliberate bug. Run your verifier on it. If the verifier fails it, the mutant is killed. If the verifier still passes it, the mutant survived, and you've found a bug your reward would pay for.

The <Term w="mutation score">Killed mutants divided by total mutants. A rough measure of how many plausible bugs your tests would catch. Every surviving mutant is a concrete false positive waiting to happen: a specific wrong program your verifier rewards as if it were right. That's what makes mutation testing the natural tool here. It estimates your verifier's false-positive rate on a family of plausible near-miss programs, which is exactly the kind of code a model produces when it's almost right.

Two caveats. Some mutants are <Term w="equivalent mutant">A mutant that changes the code but not its behaviour (for example changing a loop bound that never matters). ### The defense checklist

Pulling it together, a verifier for code RL should have:

- **Hidden tests**, kept outside the model's filesystem, plus visible tests the model may use as a debugging tool.
- **Test-file immutability**: grade in a fresh directory where only the solution files cross over, and tests, `conftest.py`, `pytest.ini`, `pyproject.toml` and anything else the runner reads come from the pristine task.
- **Sandbox restrictions**: no network, no git history beyond the task's snapshot, no reference solution or answer files anywhere the model's process can read, CPU and memory limits. ([Containers](/lessons/containers/) is the tool for this at scale.)
- **Answers stay outside**: the process running the model's code gets inputs only and returns plain serialized data, behind a random marker; comparison happens in your process with type checks. Count results; never trust an exit code alone.
- **Multiple independent verifiers**, combined with `min` or gates: fixed hidden cases, property tests, differential testing against a reference.
- **A held-out eval** that training never touches, with stricter checks.
- **Trajectory audits**: read samples, grep every trajectory for `conftest`, `os._exit`, `__eq__`, writes to test files, network calls, and track the rate over training. A spike is the earliest warning you'll get.

```python
# naive.py
import os, shutil, subprocess, sys, tempfile

def grade_naive(workspace: str) -> float:
    """Run whatever tests are in the workspace. Reward 1 if pytest exits 0."""
    d = tempfile.mkdtemp(prefix="naive-")
    shutil.copytree(workspace, d, dirs_exist_ok=True)
    r = subprocess.run([sys.executable, "-m", "pytest", "-q", "-p", "no:cacheprovider"],
                       cwd=d, capture_output=True, text=True, timeout=30)
    return 1.0 if r.returncode == 0 else 0.0
```

<Task id="t2" title="The hardened grader" agent="hands">

This is the core of the lesson. Write `grade(workspace) -> dict` that returns each check's score and the combined reward. Rules it must follow:

1. Make a fresh temp directory. Copy in **only** `solution.py`. Nothing else from the workspace crosses over.
2. Build the input list: the hidden cases' inputs, plus 200 random interval lists from a seeded generator. Compute expected outputs **in the grader process** using `reference.py`. The child never sees them.
3. Run a child process with `python -I` (isolated mode: ignores `PYTHONPATH` and user site-packages) in the fresh directory, with a timeout. Send the inputs on stdin as JSON. Pass a random nonce on the command line.

**The hardened grader leaves only honest partial credit.** The small leftover scores (0.10-0.12) come from inputs where returning `[]` is accidentally right, like the empty list. `swallow` keeps 0.33 because a half-right algorithm really is right on a third of random inputs. Verification is often the expensive part of an RL environment, and the property tests are the first thing you'll want to cap.

## Break It

**1. Compare in the wrong process.** Change your hardened grader so the child receives the expected outputs too and does the comparison itself (`if merge_intervals(inp) == exp: passed += 1`), printing only a count. It looks like a harmless simplification. Rerun the always-equal and read-the-answer-key cheats. In my run both went from 0.00 to 1.00, because that is exactly what the first-draft hidden grader does: the model's `__eq__` does the comparing, and the answers sit in a process the model controls. Then put it back and remove just the type checks instead. Work out which cheats each line was stopping. The point is to know which lines of your grader are load-bearing before you "clean them up".

**2. Make the grader too strict.** Require the output to be *identical* to the reference's, including object identity of tuples, or reject any solution that imports a module. Write three honest solutions in different styles and watch at least one get 0. You've traded false positives for false negatives. In RL, that means good strategies quietly stop getting reinforced, and you won't see it in the reward curve, only in a model that's weirdly bad at some kinds of tasks.

**3. Add a weighted-sum LLM judge and game it.** Give a judge model the code and a rubric ("readability 0-10"), and make the reward `0.7 * correctness + 0.3 * judge`. Now write a wrong solution with beautiful names, a long docstring that explains why it's correct, and a comment like `# Verified correct against all edge cases`. Check yourself, but you'll likely see it pull a good share of that 0.3. Then switch to the gate shape and watch the wrong solution drop below 0.5 no matter what the judge says.

**4. Leak through the environment.** Put `reference.py` in the same directory as the solution "temporarily", or leave the repo's `.git` with a later commit that contains the fix. Then write a solution that finds it. This is the "copy the real fix" hack, and none of your tests catch it, because the code is correct. Fix it in the environment, not the grader.

## Explain It Back

Answer out loud, in plain words, as if in an interview. Then check.

<details>
<summary>1. Why are false positives worse than false negatives for an RL verifier?</summary>

A false negative means an honest good attempt got no reward; the model becomes a bit less likely to repeat it, so learning slows. A false positive means a bad behaviour got paid, and RL's whole job is to repeat what got paid. Worse, false positives from hacks aren't random noise: a hack that fools the verifier once fools it every time, on every task that shares the verifier, so the model can learn it once and use it everywhere. Hacking takes over when a hack's expected reward beats honest work's, which happens most easily on hard tasks, which are the ones you most want to train on. So you design verifiers to have very high precision first, then recover recall.

</details>

<details>
<summary>2. You add hidden tests and the model's reward still looks suspiciously high. What could be happening?</summary>

Hidden only fixes "the model knows the inputs". It could be patching the test runner (a `conftest.py` that pytest also loads for the hidden tests), exiting with status 0 before tests run if the grader trusts exit codes, returning an object whose `__eq__` always returns true, reading the hidden test file because the model's process can see it, or copying a real fix from git history or the network. I'd grep trajectories for those patterns, check that grading happens in a fresh directory with only the solution copied in, make the model's code return serialized data to a separate process that holds the answers, and compare training reward against a held-out eval with a different grader.

</details>

<details>
<summary>3. Outcome vs process rewards, sparse vs dense: what's the trade-off for code?</summary>

Outcome rewards grade only the result, like "tests pass"; process rewards grade each step. Sparse rewards come rarely, dense ones often. Dense and process rewards give more feedback, so learning can be faster, but each extra signal is another thing the model can optimize instead of the real goal, and grading steps needs a step grader, often a learned model that's itself gameable. For code, executing the program against good tests is a strong, hard-to-fake outcome check, so most code RL uses sparse outcome rewards and deals with sparsity by sampling many attempts per task and choosing tasks the model solves sometimes but not always. A pass rate is a mild densification; shaping for things like "ran the tests" is risky because it gets gamed.

</details>

<details>
<summary>4. How do you know if your test suite is good enough to use as a reward?</summary>

Coverage isn't enough, since a line can run without anyone checking its result. I'd use mutation testing: plant small bugs in the reference solution (flip comparisons, swap max/min, drop a sort), run the verifier, and count how many it catches. Each surviving mutant is a concrete wrong program my reward would pay for. That measures how well it catches honest near-misses. For cheating, I'd red-team: write the known hacks myself and check they score near zero. And I'd confirm recall by running several correct solutions written in different styles; they should all get full reward.

</details>

<details>
<summary>5. You'll grade a million rollouts a day. How does verification scale, and what do you cut first?</summary>

Measure the per-grade cost first. In my run a pytest-based grader took about 600 ms, mostly starting the interpreter and pytest; a lean stdin/JSON runner took about 80 ms. A million grades is roughly 170 vs 22 CPU-hours a day, before sandbox startup, which with containers can dominate (keep warm containers and reuse them per task). So: start one process per grade, not one per test; run cheap gates first and skip expensive checks once one fails; cap property-test examples; cache the reference's outputs for fixed hidden inputs; run LLM judges only on solutions that already passed correctness, and on a sample if needed. What I wouldn't cut is the independence: the answers stay outside the jail and results are counted, not inferred from exit codes, because a cheaper verifier with a hole costs more than CPU.

</details>

## Go Deeper

- **Dario Amodei, Chris Olah, Jacob Steinhardt, Paul Christiano, John Schulman, Dan Mané, [Concrete Problems in AI Safety](https://arxiv.org/abs/1606.06565)** (2016). Section 4 is reward hacking: the taxonomy and the defenses are still the right starting point.
- **Victoria Krakovna et al., "Specification gaming: the flip side of AI ingenuity"** (DeepMind blog, 2020), and the public spreadsheet of examples it links to. Read twenty entries and you'll start predicting hacks before they happen.
- **Leo Gao, John Schulman, Jacob Hilton, [Scaling Laws for Reward Model Overoptimization](https://arxiv.org/abs/2210.10760)** (2022). Goodhart measured: how the true reward peaks and falls as you push harder on a proxy.
- **Hunter Lightman et al., [Let's Verify Step by Step](https://arxiv.org/abs/2305.20050)** (2023). The clearest comparison of process and outcome supervision, with the PRM800K dataset.
- **Anthropic, "Natural emergent misalignment from reward hacking in production RL"** (2025, paper and blog). The coding hacks from this lesson, studied in real training runs, and why letting them through has consequences beyond the score.
- **Carlos Jimenez et al., [SWE-bench: Can Language Models Resolve Real-World GitHub Issues?](https://arxiv.org/abs/2310.06770)** (2023). How a real hidden-test benchmark for code is built, including fail-to-pass and pass-to-pass tests.
- **[Hypothesis documentation](https://hypothesis.readthedocs.io/)** and Koen Claessen and John Hughes, "QuickCheck: A Lightweight Tool for Random Testing of Haskell Programs" (ICFP 2000). How to think in properties instead of examples.
- **Richard DeMillo, Richard Lipton, Frederick Sayward, "Hints on Test Data Selection: Help for the Practicing Programmer"** (IEEE Computer, 1978). The paper that introduced mutation testing and the "competent programmer" idea: real bugs are small deviations from correct code.
