## The Problem

You have 10 million relevance scores from the cross-encoder, one float each, and you want their sum (or their mean, or a softmax denominator; same loop). You write the obvious thing:

```python
s = 0.0
for x in scores:
    s += x
```

On an M4 Pro MacBook this takes **107 ms**. `np.sum` on the same numbers in a NumPy array takes **1.2 ms**. That is the famous gap: about 90x.

Ask around and you'll hear "NumPy is written in C". True, and only half the story. Here are two more measurements from the same machine, same 10 million numbers, same Python version:

- Keep the Python loop exactly as written, but build the list so its float objects sit in memory in shuffled order (same values, same list length, same bytecode). The loop now takes **457 ms**. Four times slower, and the interpreter is doing exactly the same work.
- Keep NumPy, but sum the numbers in random order with `a[perm].sum()`. It takes **42 ms**. Thirty-five times slower than NumPy in order, and it's all C.

So there are two different bills. One is paid by running Python bytecode for every element. The other is paid by the memory system, and it charges by *where your bytes sit and in what order you touch them*. NumPy wins on both, which is why its lead looks so big. But you can lose the memory bill in C, in NumPy, and in PyTorch on a GPU, and then "it's written in C" saves you nothing.

This lesson takes the two bills apart and measures each one.

<Origin year="1965-1968" title="A small fast memory in front of a big slow one">

In 1965 Maurice Wilkes, who had built one of the first stored-program computers, wrote a two-page paper called "Slave Memories and Dynamic Storage Allocation". His idea: put a small, fast memory in front of the big slow one, and let the hardware keep copies of recently used words in it automatically, so the programmer never has to manage it. Three years later IBM shipped the idea in the System/360 Model 85 and gave it the name that stuck: a cache.

It only worked because of a fact about programs that Peter Denning and others were measuring at the same time: programs don't touch memory at random. They reuse what they just used and walk to what's next to it. Every cache since, including the ones on your M4 and on the Spark's Grace cores, is a bet on that behaviour. This lesson is about what happens when your code honours the bet, and what happens when it doesn't.

## The Idea

### Two bills

Think of summing numbers as a warehouse job. Someone has to **walk to each shelf and bring the item back** (the memory bill), and someone has to **fill in a form for every item** (the interpreter bill). NumPy is a forklift on a straight aisle: no forms, and the items are lined up in a row. A Python loop over a list fills in a form for each item, and the items are wherever there was space when they were stored.

The form first. When CPython runs `for x in scores: s += x`, it doesn't add two numbers. For every element it runs a handful of <Term w="bytecode">The simple instructions CPython compiles your Python into (FOR_ITER, STORE_FAST, BINARY_OP, ...) and then executes one at a time in a big loop written in C.</Term> instructions: fetch the next item from the list, store it in `x`, load `s` and `x`, check both of their types, find the float-add routine, add the two doubles, and allocate a brand-new float object for the result (Python floats can't be changed in place), then drop the old `s` and update a few <Term w="reference count">The counter in every CPython object of how many references point at it. Touched on almost every operation; zero frees the object.</Term>s. That costs around 10 ns per element on a fast laptop. We'll call this <Term w="interpreter overhead">The work CPython does per operation that isn't your actual math: dispatching bytecodes, checking types, boxing results into objects, refcounting. Usually 10-50x the cost of the arithmetic itself.</Term>. [Why is Python slow?](/lessons/python-speed/) takes that apart instruction by instruction. Here we only need its size.

Now the walk. The add itself needs the 8 bytes of a double, and those 8 bytes have to come from somewhere on the ladder from [How slow is slow?](/lessons/latency-numbers/): L1 at about a nanosecond, RAM at about a hundred. The memory bill is decided by which rung each load hits, and that is decided almost entirely by layout and order.

Here are the numbers for one element, measured on an M4 Pro (CPython 3.14, NumPy 2.5, 10 million float64s, best of several runs). You'll get your own in the Build.

| How | ns per element | Interpreter per element? | Memory pattern |
| --- | --- | --- | --- |
| Python loop, list | 10.7 | yes | pointers in order, objects in order |
| Python loop, list, objects shuffled | 45.7 | yes | pointers in order, objects scattered |
| `sum(list)` | 1.9 | no (C loop) | in order |
| `sum(list)`, objects shuffled | 11.2 | no | scattered |
| `np.sum`, contiguous | 0.12 | no | one dense run |

Read the table in pairs. The first two rows run *identical* bytecode, so the 35 ns difference is pure memory bill. `sum(list)` does the same walk as the loop with no bytecode per element, so loop minus `sum` (about 9 ns) is roughly the interpreter bill. And when the objects are scattered, even the C loop in `sum` slows down by 6x. So a fair summary of the famous 90x: **about 5-10x of it is the interpreter, and the rest is memory layout and what layout lets the CPU do.** Those last words matter, and we'll come back to them with SIMD.

### The cache line

You met the <Term w="cache line">The fixed-size block that moves between RAM and the caches as one unit. 64 bytes on x86 and on most ARM server cores, including the Spark's. 128 bytes on Apple M-series.</Term> in the latency lesson. Here it becomes the main character, so let's look at it closely.

The memory system never moves one byte, or one double. When your code loads 8 bytes that aren't in cache, the hardware fetches the whole aligned line those 8 bytes sit in. On your Mac that's 128 bytes (check: `sysctl hw.cachelinesize` prints `128`). On the Spark and on Intel and AMD chips it's 64.

Two habits make this pay off, and they have names.

- <Term w="Spatial locality">Using data that sits next to data you just used. A line holds 8 or 16 doubles, so reading neighbours means most loads hit the line you already paid for.</Term>: after `a[5]`, you read `a[6]`. It's in the line already.
- <Term w="Temporal locality">Using the same data again soon. If you come back before the line gets pushed out by other data, the second visit is a cache hit.</Term>: after reading `a[5]`, you read it again soon, before newer data pushes the line out of the cache.

Every speedup in this lesson is one of those two, or the third trick below.

### The prefetcher: a clerk who reads ahead

Spatial locality alone would still leave you paying full RAM latency once per line: 100 ns every 16 doubles is about 6 ns per double, much slower than the 0.12 ns NumPy gets. The missing piece is the <Term w="hardware prefetcher">Circuitry next to the caches that watches the stream of addresses that miss, spots a pattern (next line, or every Nth line), and requests lines before the program asks for them.</Term>.

Picture a clerk at the warehouse door watching what you request. You ask for shelf 40, then 41, then 42. Without being told, the clerk sends runners for 43, 44, 45, 46. By the time you ask for 43, it's on the counter. The clerk can also spot a fixed stride (40, 48, 56...). What the clerk cannot do is guess the next item in a random list, or the next object behind a pointer it hasn't loaded yet.

So in-order access converts a **latency** problem into a **bandwidth** problem: many lines in flight at once, arriving back to back, which is exactly the "bytes in flight" idea from the latency lesson. Random access leaves you with latency. On many chips the prefetcher also stops at page boundaries (4 KB on x86 and usually on the Spark's Linux; 16 KB on macOS), since the next page might not even be mapped.

### Why pointer-chasing lists lose

From [Where do my variables live?](/lessons/stack-and-heap/): a list of floats is an array of 8-byte pointers, and each pointer leads to a separate 24-byte float object somewhere on the heap. Reading element `i` is two loads: the pointer, then the object it points to. The pointer array is dense and walked in order, so it's cheap. The objects are where it gets interesting.

**When objects are created in order** (`scores = a.tolist()`, a list comprehension, appending in a loop), CPython's small-object allocator tends to hand out neighbouring addresses one after another. Object `i+1` usually sits right after object `i`. Following the pointers walks forward through memory, and the prefetcher is happy.

**When the visiting order doesn't match the creation order** (you sorted the list, shuffled it for a training epoch, built it out of dict values, or the objects were made at different times by different code), each pointer jumps somewhere new. Now every element is a likely cache miss, and the prefetcher can't predict the next address because it doesn't know it until the pointer is loaded.

Why 45 ns and not the full ~100 ns RAM latency? The *pointers* come from the in-order array, so the CPU knows the next few object addresses early and can have a couple of misses in flight at once. That overlap is called <Term w="memory-level parallelism">Having several cache misses outstanding at the same time, so their waits overlap. Out-of-order cores can track a few dozen per core, if they can find independent loads to issue.</Term>. But the interpreter runs a long stretch of instructions between one object load and the next, which limits how far ahead the core can look, so it only overlaps a few. (That's my best explanation for the exact number. The direction, a big slowdown from scattering alone, is the robust part.)

This is exactly the thing NumPy removes. A NumPy array has no per-element objects and no pointers: element `i` is at `base + 8*i`. The address of every element is known without loading anything. Which leads to the question of what happens when NumPy's elements are *not* next to each other.

### Rows, columns and strides

RAM is one long line of bytes. A matrix is two-dimensional. Something has to decide how to flatten it. C, NumPy (by default) and PyTorch use <Term w="row-major order">Store a matrix one row after another: all of row 0, then all of row 1. Moving along a row moves to the next address. Also called C order.</Term>: row 0, then row 1, and so on. Fortran, MATLAB, Julia and many BLAS libraries use <Term w="column-major order">Store a matrix one column after another. Moving down a column moves to the next address. Also called Fortran order.</Term>.

NumPy generalises this with <Term w="strides">For each dimension, how many bytes to jump to move one step along it. An (R, C) float64 array in row order has strides (8C, 8). The address of a[i, j] is base + i*stride0 + j*stride1.</Term>. Every array is just a pointer, a shape, and a strides tuple. Slicing and transposing don't copy any numbers; they make a new small array object with different strides pointing into the same buffer.

| Loop order | ns per element | |
| --- | --- | --- |

Same additions, same numbers, same compiler, only the loop order swapped. And look at the last two rows: the compiler flag made the good order 5x faster and did nothing for the bad one. That's the third trick, coming up.

**NumPy is usually smart about this, but not always.** For a reduction like `M.T.sum(axis=1)`, NumPy's iterator notices the strides and walks memory in its natural order anyway (I measured 1.36 ms vs 1.19 ms for the un-transposed version: nearly the same). But some operations *must* read in one order and write in another. `M.T.copy()` has to produce a new row-major array from a transposed view, so either its reads or its writes go down columns: 5.4 ms vs 1.2 ms for `M.copy()`. Every time you call `np.ascontiguousarray`, `.copy()` on a transpose, or hand a transposed array to a library that needs C order, you pay that.

You can see strides directly:

```python
>>> a = np.zeros((1000, 10000))
>>> a.strides, a.T.strides, a[:, ::2].strides
((80000, 8), (8, 80000), (80000, 16))
>>> a.flags['C_CONTIGUOUS'], a.T.flags['C_CONTIGUOUS']
(True, False)
```

### SIMD: doing several adds at once

The memory bill explains why a column walk is slow. It doesn't explain why NumPy, in order, gets 0.12 ns per element while a plain C loop over the same in-order data gets 0.53. Both read memory perfectly. The difference is in how the arithmetic is done, and it has two parts.

**Part 1: the dependency chain.** The plain loop is `s += a[i]`. Each add needs the result of the previous add. A floating-point add takes a few clock cycles to produce its answer, so the core sits waiting for `s` before it can start the next one, even though it has spare adders. One cook, one pot, and every ingredient has to wait for the last one to dissolve. That's where 0.5 ns per element comes from: it's the *latency* of one add, not memory.

Fix: keep four running sums, `s0 += a[i]`, `s1 += a[i+1]`, `s2 += a[i+2]`, `s3 += a[i+3]`, and add them up at the end. Four independent chains, and the core runs them in parallel on its several adders. I measured 0.16 ns per element: 3.3x faster from rearranging the arithmetic, no special instructions at all. This is <Term w="instruction-level parallelism">A single core executing several independent instructions at the same time. Modern cores have several adders, multipliers and load units and will overlap any instructions that don't depend on each other.</Term>.

**Part 2: wide registers.** Modern cores also have <Term w="SIMD">Single Instruction, Multiple Data. One instruction operates on a short vector of numbers packed into one wide register, e.g. adds 2 doubles or 4 floats at once on 128-bit NEON.</Term> instructions. A <Term w="vector register">A wide CPU register holding several numbers side by side. 128 bits on ARM NEON (Apple M and the Spark's cores), 256 bits with x86 AVX2, 512 bits with AVX-512.</Term> holds several numbers side by side, and one instruction adds all the lanes at once. ARM's NEON registers are 128 bits: 2 doubles or 4 floats per instruction. Combine wide registers with several accumulators and you get the 0.08 ns per element I measured for an in-cache sum.

**Why doesn't the compiler do this for you?** Because floating-point addition isn't associative. `(a + b) + c` and `a + (b + c)` can differ in the last bits, since each add rounds. Splitting one sum into four partial sums changes the order of additions, so it can change the answer, and C compilers aren't allowed to change your answer without permission. `-ffast-math` is that permission (along with several other, riskier ones; don't use it blindly in real code). For integers, where addition is exact, the compiler vectorizes the plain loop by itself.

NumPy gets permission a cleaner way: its `sum` for floats is documented to use **pairwise summation**, adding numbers in blocks and then adding the block sums. That's both more accurate than one long running sum and naturally split into independent chains the CPU can vectorize. So `np.sum` gets the memory bill right (one dense run) *and* the arithmetic bill right (many independent lanes).

**SIMD helps until memory is the wall.** Look at the C numbers when the array is 800 MB instead of fitting in L1: the vectorized sum drops from 0.08 to 0.11 ns per element, about 71 GB/s, because now it's waiting on RAM, not the adders. The one-accumulator sum doesn't change at all (0.52 → 0.54), because it was never waiting on memory. That's the roofline from [Why ~17 tokens per second?](/lessons/bandwidth-bound/) in miniature: a slow kernel is compute-bound, a fast kernel on big data hits the memory roof.

And notice what SIMD needs: *the numbers packed side by side in memory*, so one load fills one vector register. A Python list can never feed it, because the doubles are inside separate objects. A strided array feeds it badly. Layout isn't just about cache lines; it's what allows the third trick at all.

How to read it, one gap at a time:

- **list loop → `sum(list)`** (10.7 → 1.9): remove the interpreter, keep the layout. About 5.6x. This is the interpreter bill.
- **`sum(list)` → contiguous NumPy** (1.9 → 0.12): remove the pointers and objects, so each number is 8 bytes instead of 40, and the C loop can use several accumulators and SIMD. About 16x. This is the layout bill.
- **list loop → shuffled list loop** (10.7 → 45.7) and **`sum(list)` → shuffled** (1.9 → 11.2): same code, scattered objects. The memory bill, with nothing else changed.
- **contiguous → stride 64 B → stride 128 B** (0.12 → 0.70 → 2.4): NumPy, same count of numbers, more lines per number. At stride 64 B on the Mac, two numbers still share each 128 B line; at stride 128 B, every number costs its own line. The prefetcher still predicts the stride, so this is bandwidth wasted, not latency.
- **random gather** (4.2): about one line per number with no prefetching, saved from disaster only by memory-level parallelism. (It also allocates an 80 MB temporary for `a[perm]`, part of the cost.)

### The same story on a GPU

Everything above gets louder on a GPU, because a GPU is a machine designed to be fed by bandwidth.

An NVIDIA GPU runs threads in groups of 32 called a <Term w="warp">A group of 32 GPU threads that execute the same instruction at the same time, each on its own data. The basic unit the GPU schedules.</Term>. When a warp executes a load, all 32 threads issue their address at the same moment, and the memory system looks at the 32 addresses *together*. It moves data in 32-byte <Term w="sector">The 32-byte unit an NVIDIA GPU's caches and memory move. Four sectors make one 128-byte cache line.</Term>s. If the 32 addresses are neighbours, the warp's whole request is served with a handful of sectors. That's <Term w="coalesced access">When the threads of a warp read or write consecutive addresses, so the hardware can serve all of them with the minimum number of wide memory transactions.</Term>.

GPU memory is fast (the Spark's spec sheet says ~273 GB/s), but inference kernels are already memory-bound, as you saw in [Why ~17 tokens per second?](/lessons/bandwidth-bound/). An uncoalesced kernel that moves 8x the bytes runs close to 8x slower. That's why so much GPU kernel engineering is about layout: tiling matrices into blocks that warps read row-wise, staging them in fast on-chip <Term w="shared memory" label="shared memory (GPU)">A small scratchpad on each GPU multiprocessor (tens to a couple hundred KB) that a block of threads manages by hand. Used to load a tile once, coalesced, then reuse it many times. Not the same as the OS shared memory between processes.</Term>, and reusing each tile many times before going back to main memory. FlashAttention, at its heart, is temporal locality done by hand.

**Where you meet this in PyTorch: `.contiguous()`.** A PyTorch tensor is a pointer, a shape and strides, exactly like a NumPy array. `x.T`, `x.transpose(1, 2)`, `x.permute(0, 2, 1, 3)` and many slices just swap strides. They're free, and the result is non-contiguous. Then one of three things happens:

1. **An op refuses it.** `.view()` needs strides it can reinterpret without moving data, and fails on a transpose: `view size is not compatible with input tensor's size and stride ... Use .reshape(...) instead.` `.reshape()` quietly copies when it has to.
2. **An op handles it, slowly.** Elementwise ops on one tensor keep its layout and run at full speed. Mixing layouts is different: on my Mac's CPU, `x + y` on two 4096 × 4096 float32 tensors took 1.1 ms, and `x.T + y` took 11.7 ms. One of the two inputs has to be read down columns.
3. **An op copies it for you.** Many kernels (custom CUDA ops, some attention implementations, anything that wants a raw pointer) call `.contiguous()` internally, which allocates a new tensor and does the transposing copy, often without you noticing. That copy is the `M.T.copy()` cost from earlier, on every call.

So when you see `q = q.transpose(1, 2).contiguous()` in an attention implementation, it's someone paying the copy once, on purpose, so that the next big kernel gets coalesced reads. `.contiguous()` on a tensor that already is contiguous returns it unchanged, for free. And the CNNs you've trained have a version of this too: `memory_format=torch.channels_last` stores images as N, H, W, C instead of N, C, H, W, so the channels of one pixel sit next to each other, which is what convolution kernels on modern GPUs want to read together.

What to look for:

**The two bills don't simply add.** Loop minus `sum(list)` is 8.8 ns per element for the in-order list (10.7 − 1.9), but 34.5 ns for the shuffled one (45.7 − 11.2). If the interpreter bill were a fixed tax, those would match. They don't because layout and code interact: in the tight C loop inside `sum`, many object loads can be in flight at once, so the misses overlap. In the interpreter loop, each load is surrounded by so much other work that fewer overlap, and each miss is exposed more. "5x interpreter, 16x layout" is a good first story; this is the truer second one.

**The row/column gap appears when the matrix stops fitting in cache.** At n = 256 (512 KB) it was 1.2x for me, at 1024 (8 MB) 1.6x, at 4096 (134 MB) 5.7x. On the Spark, with 64 B lines, the column walk wastes 7/8 of each line instead of 15/16, so if anything expect a slightly smaller ratio than the Mac's at the same size, but a slower row walk too. Measure it.

**`-ffast-math` widens the gap.** It only speeds up the row walk, because only the row walk was waiting on arithmetic. The column walk was waiting on memory all along, and no amount of SIMD helps a loop that's waiting on RAM.

**Sorted gather is 8x faster than random gather** (0.54 vs 4.2) with the same instructions, because sorted indices walk memory forward and the prefetcher can follow.

## Break It

**1. Make the matrix a power of two.** Run `rowcol` with n = 4000, 4096 and 4100. On my Mac the column walk took 2.05, 3.27 and 1.96 ns per element. 4096 is about 60% worse than its neighbours. Each column step at n = 4096 is exactly 32 KB, and a cache decides which of its slots a line may go in from a few bits of the address. Addresses exactly 32 KB apart share those bits, so they all compete for the same few slots and keep evicting each other, while the rest of the cache sits empty. These are called <Term w="conflict misses">Cache misses caused not by the cache being full but by too many lines mapping to the same small group of slots (a "set"). Classic with power-of-two strides.</Term>. The classic fix is padding: allocate rows of 4096 + 8 and ignore the extra. This is why some libraries pad their leading dimension, and why FFT and matrix code benchmarks at 4096 sometimes look weirdly bad.

**2. Let the compiler cheat.** Remove the `__asm__ volatile` barrier from `simd.c`. I got "59,925 GB/s" for the in-cache sum: the compiler saw a function with no side effects called on unchanged data and ran it once. Then delete the final `printf` of the sum and the whole thing may vanish. Every microbenchmark has to make the compiler believe the work matters.

**3. Shrink the problem until NumPy loses.** Time `sum(l)` and `a.sum()` for 10, 100 and 1,000 elements. On my Mac: 59 ns vs 237 ns at 10 elements, about even at 100, and NumPy 5x ahead at 1,000. Every NumPy call pays a fixed few hundred nanoseconds (argument parsing, dtype dispatch, allocating the result) before it touches a single number. Then time `np.array(l).sum()`: it loses at every size, because converting a list to an array is itself a Python-speed loop over objects. NumPy pays off when data *lives* in arrays and many operations happen per conversion.

**4. Defeat the prefetcher with a stride it can't track.** In `five.py`, sum `a[::k]` for k = 1, 2, 4, 8, 16, 32, 64, 512 and plot ns per element. You should see the cost rise until every element is its own line (k = 16 on the Mac, 8 on the Spark), then mostly flatten, since one line per element is one line per element. For large k, each step also crosses a 4 KB or 16 KB page, the prefetcher (on many chips) won't cross pages, and the address translations start missing in the <Term w="TLB">Translation lookaside buffer: a small cache of recent virtual-to-physical address translations. Big strides touch a new page per element and miss here too.</Term>. Look for a second rise.

## Explain It Back

Answer out loud, in plain words, as if an interviewer asked. Then check.

<details>
<summary>1. Why is summing a NumPy array ~100x faster than a Python for-loop over a list of the same numbers?</summary>

Two separate reasons. The interpreter: the Python loop runs several bytecodes per element, checks types, and allocates a new float object for every partial sum, around 10 ns per element. NumPy runs one C loop. And the memory layout: a list is an array of pointers to separate 24-byte objects, so each number costs a pointer plus an object (40 bytes or so), and if the objects aren't in memory order, every element is a cache miss. A NumPy array is one dense run of 8-byte numbers, which uses every byte of every cache line, lets the prefetcher stream it, and lets the C loop use SIMD and several accumulators. On my Mac the split was about 5-6x from the interpreter (loop vs `sum(list)`) and about 16x from layout (`sum(list)` vs `np.sum`). And I can make each one worse independently: shuffle the list's objects and the identical Python loop gets 4x slower.

</details>

<details>
<summary>2. What is a cache line, and what does it have to do with strides?</summary>

The unit the memory system moves: 64 bytes on x86 and on the Spark, 128 on Apple M. Load one double that isn't cached and you get the whole aligned line around it. With stride 1 (contiguous), a 128-byte line serves 16 consecutive doubles, so one miss pays for 16 loads. With a stride of one line or more, every element costs a whole line, so you move 8x or 16x the bytes for the same work. The prefetcher can still predict a constant stride, so you mostly pay bandwidth rather than latency, but you burn bandwidth on bytes you never use. Random order is worst: one line per element and nothing to predict.

</details>

<details>
<summary>3. Your matrix code is 6x slower than a colleague's doing the same math. What's your first guess and how do you check?</summary>

Loop order versus memory layout: walking a row-major array by columns (or a column-major one by rows), so every step lands on a new cache line. Check the strides or the array flags (`.strides`, `.flags`, `.is_contiguous()`), swap the loop order or make the data contiguous in the order you read it, and measure. To confirm it's the cache and not something else, count misses with `perf stat` (L1 refills per element should go from ~1/8 to ~1). Also check the size: if the matrix fits in cache the gap mostly disappears, and if the width is a power of two, suspect conflict misses and try padding.

</details>

<details>
<summary>4. How does this scale? A feature-engineering job sums one column out of a 10M × 64 float32 table. Row-major vs column-major storage: what's the difference in bytes moved, and what changes on a GPU?</summary>

Row-major: each row is 64 × 4 = 256 bytes, and you want 4 of them. Each row is its own line or more, so you pull roughly a 64-byte line per value on the Spark (128 B on the Mac): 10M × 64 B = 640 MB moved for 40 MB of useful data, 16x. Column-major (or a column store like Parquet/Arrow): the column is one dense 40 MB run, read at full bandwidth. At one core's ~50-70 GB/s that's roughly 1 ms for the dense column vs about 10 ms for the row-major scan, and the gap stays 16x however big the table gets, because it's a ratio of bytes moved. On a GPU the same choice shows up as coalescing: a warp of 32 threads reading one column of row-major rows touches 32 separate sectors, 8x the traffic of a coalesced read, so you'd store or transpose the column first. This is why analytics databases are column stores and why feature columns get pulled out into their own arrays before heavy math.

</details>

<details>
<summary>5. What does `.contiguous()` do in PyTorch, and when is it worth calling?</summary>

It returns a tensor whose elements are laid out in plain row-major order in memory. If the tensor already is, it returns the same tensor for free. If it's a view with rearranged strides (after `.T`, `.transpose`, `.permute`, some slices), it allocates a new buffer and copies the data into that order. It's worth calling when the next operations will read the tensor many times and need dense, in-order access: before `.view()`, before a custom kernel that takes a raw pointer, or before an attention kernel that wants each head's rows dense so warps read coalesced. You pay one copy to save a slow, uncoalesced access pattern on every later read. It's not worth calling "just in case" on something you only read once.

</details>
