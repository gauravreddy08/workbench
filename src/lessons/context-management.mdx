## The Problem

You already do this well. Your coding agent finds code by walking the AST instead of dumping files, and you trim what goes into each API call without thinking hard about it. So here is a scene you have probably half-lived.

The agent is 40 steps into a refactor. Early on, at step 3, it read `settings.py` and saw `TIMEOUT_MS = 2350`. At step 9 it ran the server and got a 12,000-token log with one line that mattered: `E4127 upstream closed`. Now, at step 38, it needs both facts. One of three things happens:

1. **It runs out of room.** The prompt is past the model's limit. The API returns an error, or your harness quietly cuts the oldest messages to make it fit, and the config value goes with them. The agent re-reads the file (more tokens) or, worse, guesses `3000`.
2. **It's all still there, and it doesn't matter.** Both facts are in the window, buried at token 8,000 and token 31,000 of a 90,000-token prompt. The model writes a fix that uses the wrong timeout, because a dozen other `TIMEOUT_MS` lines from other files are in there too.
3. **It works, and the bill is strange.** Each step sent the entire history again. Step 38 alone was 90,000 input tokens. The whole run was 2 million input tokens for a task whose interesting content was maybe 5,000.

None of these is the model being dumb. They follow from how the window works, and each can be measured. Today's job: turn "I manage context well by instinct" into numbers in a table.

<Origin year="2017-2025" title="From 512 tokens to a million, and the discovery that bigger isn't better">

The original Transformer and BERT worked on 512 tokens. GPT-2 had 1,024, GPT-3 had 2,048. That was too small to hold a document, let alone a codebase, so in 2020 Patrick Lewis and colleagues at Facebook AI published retrieval-augmented generation: keep the knowledge outside the model, fetch the few passages that matter, and paste them in. For a few years "context management" mostly meant "retrieval, because there's no room".

Then the windows exploded. Anthropic shipped 100,000 tokens in May 2023, OpenAI's GPT-4 Turbo had 128,000 by November, and Google's Gemini 1.5 announced a million in February 2024. The obvious conclusion was that retrieval was over: just put everything in. Two results in 2023 complicated that. In July, Nelson Liu and colleagues at Stanford showed that models used information at the start and end of a long prompt much better than information in the middle ("Lost in the Middle"). In November, Greg Kamradt hid one sentence in long documents and mapped where models could find it, the first "needle in a haystack" test, and the charts had holes in them.

By 2025, with agents running for hundreds of steps, the work got a name: <Term w="context engineering">Deciding, at each step of an LLM application or agent, exactly which tokens go into the model's context, in what order, and what gets dropped or compressed.</Term>, deciding at every step which tokens the model gets to see. Anthropic's engineering blog put it plainly: context is a finite resource with diminishing returns, and the goal is the smallest set of high-signal tokens that gets the job done.

</Origin>

## The Idea

### The window is a desk, not a library

Picture a researcher at a small desk, with a library behind her. Every few minutes an assistant clears the desk and lays out fresh papers, and she reads all of them, start to finish, before she says anything. She has no memory between rounds: if it isn't on the desk, she doesn't know it.

That is a language model in an agent loop. The desk is the <Term w="context window">The maximum number of tokens a model can take as input in one request (plus, for most APIs, the tokens it writes back). Everything the model knows about your task this step has to fit in it.</Term>. The papers are <Term w="tokens">The chunks of text a model reads and writes, usually pieces of words. In English prose a token is about 4 characters or three quarters of a word; code is often similar, but check with your model's tokenizer.</Term>. The assistant laying out papers is your harness. And the model reads everything, every time.

The [tokenizers lesson](/lessons/tokenizers/) showed what a token is. Here is what a token *costs* once it's in the window. Four separate bills.

**Memory.** Every token in the prompt leaves behind a key and a value vector in every layer: the <Term w="KV cache">The stored keys and values for every token processed so far, kept so the model doesn't recompute them for each new token. It grows by one entry per layer for every token.</Term>. From [the KV cache lesson](/lessons/kv-cache/), Llama 3.1 8B in bf16 stores 128 KiB per token. A 100,000-token agent session is about 12.2 GiB of KV cache, close to the size of the model's own weights (about 16 GB in bf16). On an API you don't see this, but the provider does, and it shows up in the price and in the rate limits.

**Money.** APIs charge per token, separately for input and output. As an example, take $3 per million input tokens and $15 per million output tokens, roughly a mid-tier model in 2025 (check the current pricing page for whatever you use). A 100K-token prompt is $0.30 *per call*, before the model writes anything.

**Prefill time.** Before the model writes its first token it has to run the whole prompt through every layer, the <Term w="prefill">The first phase of a request: process all prompt tokens at once to build the KV cache. It is compute-heavy, and its time grows with prompt length. The time it takes is most of the time to first token.</Term>. That is roughly 2 floating-point operations per parameter per token, plus attention, where each token looks at every token before it. For Llama 3.1 8B (32 layers, width 4,096), the attention work for one new token at position n is about 4 × 32 × 4,096 × n FLOPs, which equals the 16 GFLOPs of weight work at n ≈ 30,000. So past about 30K tokens, attention starts to dominate and prefill grows faster than linearly. At an assumed 100 TFLOP/s of real throughput, prefill takes about 0.15 s for 1K tokens, 1.5 s for 8K, 8 s for 32K, and over a minute for 128K (back-of-envelope; real engines and real GPUs differ, and providers use much bigger GPUs and tricks). You will measure your own API's version of this curve in the Build.

**Attention.** The fourth cost doesn't show up on a bill. More tokens means more things competing for the model's attention. We'll come back to this; it's the subtle one.

Notice the proportions. In most coding and browsing agents the history and especially the tool results (file contents, test output, logs, web pages) are the bulk. The system prompt you agonize over is a rounding error. So most of context management is really "what do we do with tool results".

### The loop resends everything

Here is the part that changes how you think about cost. The model has no memory between calls. Your harness gives it memory by resending the whole conversation every time.

A minimal agent loop:

```python
messages = [{"role": "user", "content": task}]
while True:
    reply = llm(system=SYSTEM, tools=TOOLS, messages=messages)   # sends ALL of messages
    messages.append({"role": "assistant", "content": reply.content})
    if reply.stop_reason != "tool_use":
        break
    results = [run_tool(call) for call in reply.tool_calls]
    messages.append({"role": "user", "content": results})          # history grows
```

Step 1 sends the task. Step 2 sends the task, the first reply, and the first tool result. Step 3 sends all of that plus the second pair. If each step adds about the same number of tokens, step k sends about k times that many.

### Prompt caching: the prefix is the deal

You met the mechanism in [Prefix caching](/lessons/prefix-caching/): a server that has already computed the KV cache for some prefix of tokens can skip that prefill on the next request that starts with the same tokens. APIs sell this as <Term w="prompt caching">An API feature where the provider keeps the processed prefix of your prompt for a few minutes, and bills later requests that start with the exact same tokens at a large discount, with lower latency.</Term>. Anthropic makes you mark the end of the reusable part with a <Term w="cache breakpoint">A marker in the request saying "cache everything up to here". The next request reuses it only if every token before the marker is identical.</Term> (`cache_control`) and bills cache writes at 1.25× and cache reads at about 0.1× the normal input price, with a default lifetime of 5 minutes that refreshes on each hit. OpenAI does it automatically above about 1,024 tokens. Check each provider's docs for current numbers.

An agent loop is the perfect customer for this, because the history only ever grows at the end. Each request is the previous one plus a bit. As long as nothing near the top changes, almost every input token is a cache read.

This gives you the first hard rule of context management, and it's about *order*, not size:

> Anything that changes goes as late in the prompt as possible. One changed token invalidates the cache for everything after it.

Put a timestamp in the first line of the system prompt and you pay full price for the whole prompt on every call. Reorder tool definitions between calls (say, by iterating over a Python `set`) and same thing. And here is the twist that matters for the strategies below: **any strategy that edits old history breaks the cache**. Dropping the oldest message changes what comes right after the system prompt. Summarizing old turns rewrites the middle. These save tokens in the window, but each edit forces the provider to re-process everything after the edit at full price (in fact at the 1.25× write price). Sometimes "fewer tokens" costs more money.

### Attention dilution: why more context can make answers worse

Now the cost that isn't on the bill. Recall how attention works from building GPT-2: the current token's query is compared against every key, the scores go through a <Term w="softmax">A function that turns a list of scores into weights that are all positive and add up to 1. Bigger scores get exponentially more weight.</Term>, and the output is the weighted average of the values. The weights add up to 1. That's the whole problem in one sentence: attention is a fixed budget split across every token on the desk.

Make it concrete. Say the one token that matters scores 3 points higher, as a <Term w="logit">A raw score before softmax. Adding 1 to a logit multiplies that item's unnormalized weight by e, about 2.7.</Term>, than each of the others, and all the others score the same. The relevant token's share of attention is e³ / (e³ + n − 1):

| Tokens in context (n) | Relevant token's weight | Score lead needed to keep 50% |
| --- | --- | --- |
| 1,000 | 1.97% | 6.9 |
| 10,000 | 0.20% | 9.2 |
| 100,000 | 0.02% | 11.5 |

(Computed with Python; the second column is ln(n − 1).) Each 10× more context, the relevant token needs about 2.3 more points of score lead just to hold its ground. Real models are much better than this toy: they have many heads and layers, and trained models learn very sharp attention for things like copying. But the pressure is real, and it gets much worse when the haystack contains *near-misses*: a hundred `TIMEOUT_MS = ...` lines, each scoring almost as high as the right one. That is <Term w="attention dilution">The tendency of a relevant piece of context to get less of the model's attention as more tokens compete for it, especially when many of those tokens look similar to it.</Term>, and it is why the second failure in The Problem happens even when everything fits.

### Lost in the middle

Liu et al. (2023) measured something more specific. They gave models a question and 20 retrieved documents, exactly one of which contained the answer, and moved that document from first place to last. Accuracy traced a U: high when the answer was first, high-ish when it was last, and lowest in the middle. For GPT-3.5-Turbo with 20 documents, the middle positions scored *below the closed-book baseline*, where the model got no documents at all. Having the answer in the context, in the wrong place, was worse than not having it. (Numbers from memory of the paper; the shape is the robust part.)

Why a U? It's only partly understood, and there are several contributing stories. Training data puts important things at the start (titles, instructions) and the end (the question you're answering right now), so models learn to look there. Causal attention means early tokens are seen by every later token, and models are known to park a lot of attention on the first few tokens regardless of content. Position encodings like the RoPE you implemented tend to make far-apart tokens score a bit lower on average, which favors what's recent. Whatever the mix, the practical lessons are stable: **put instructions and the question at the end, near where the model writes; put the most important material at the start or end, not buried; and fewer, more relevant documents beat more documents.**

### Needle in a haystack, and why passing it proves little

Kamradt's test is simple: take a long filler document (he used Paul Graham essays), insert one sentence ("The best thing to do in San Francisco is eat a sandwich and sit in Dolores Park on a sunny day") at some depth, ask the model what the best thing to do in San Francisco is, and repeat over a grid of lengths and depths. The output is a heat map. Early 2023-era long-context models had visible red patches. When Claude 2.1 scored poorly on it, Anthropic reported that adding one line to the start of the model's answer ("Here is the most relevant sentence in the context:") took it from 27% to 98%. That tells you how much of the result was about the test's framing.

Today most frontier models score near-perfect on the plain version. That does not mean they use long context well, for three reasons:

1. **It's a lexical match.** The question shares rare words with the needle ("San Francisco", "best thing"). The model can find it the way `grep` would. Benchmarks that remove the word overlap, so that finding the needle needs one step of reasoning (NoLiMa, 2025), show accuracy falling off steeply with length even for strong models.
2. **There is one needle and nothing like it.** Real context has near-misses. RULER (NVIDIA, 2024) added multiple needles, distractors, tracing variables through chains, and aggregation tasks, and found that the <Term w="effective context length">The longest input at which a model still meets some accuracy bar on a benchmark, as opposed to the maximum the API accepts.</Term> where models stay accurate is often much shorter than the advertised one.
3. **Finding isn't using.** Your agent must notice the timeout matters, combine it with the error from step 9, and write a fix. Chroma's 2025 "Context Rot" report found performance degrading with input length even on simple tasks.

So treat the window size as a ceiling and the needle score as a smoke test. What matters is accuracy on *your* task at *your* lengths.

### The toolbox

Every strategy for managing context answers one question: *of everything the agent could know, what goes on the desk this step?* Here they are, each with what it throws away. The pattern to notice is that none of them is free. They trade tokens for something: risk of missing information, cost of extra calls, or latency.

**Stuff everything (preload).** Put the whole corpus in the prompt once, cache it, ask away. Nothing is missed, and with caching it's cheaper than you'd guess. It fails when the corpus doesn't fit, when near-misses dilute attention, and on first-call latency (full prefill). Good for one document or a small repo you'll query many times within the cache's lifetime.

**Retrieval (RAG).** Keep the corpus outside and fetch the few pieces most likely to matter. <Term w="RAG">Retrieval-augmented generation. Before (or during) generation, search an external store for relevant passages and put only those in the prompt.</Term> lives or dies on two choices. First, <Term w="chunking">How you cut documents into pieces for retrieval: fixed size with overlap, by structure (functions, sections, paragraphs), or by meaning. The chunk is the unit that gets found and pasted in.</Term>: too small loses the surrounding meaning ("it returns 3": what does?), too big wastes tokens. For code, one function or class per chunk with its path and imports attached beats fixed windows; your AST lookup already does this. Second, the search: keyword search (<Term w="BM25">A classic keyword-ranking formula: documents score higher for containing rare query words, with diminishing returns for repeats. Great at exact identifiers.</Term>) for identifiers, <Term w="embeddings">Vectors from a model that place texts with similar meaning near each other, so you can search by meaning rather than exact words.</Term> for paraphrase, and a cross-encoder reranker on top, the kind of model you train at work, often the biggest single win (see [vector search](/lessons/vector-search/)). Throws away: whatever the search ranked low. Weak spot: multi-hop questions, unless the model can search repeatedly.

**Just-in-time loading.** <Term w="Just-in-time loading">Fetching information into context only at the step that needs it, through tools, instead of loading it all up front (preloading).</Term> is retrieval as tools: give the model `grep`, `read lines 40-90`, `list directory`, keep only light references (paths, line numbers) in context, and let it pull what it needs. Claude Code navigates repos this way, with no vector index. It costs more steps and latency and trusts the model to know what to look for. Most real systems preload a little (a memory file, the directory layout) and load the rest on demand.

**Tool-result truncation.** The cheapest big win. Cap every tool's output (say 2,000 tokens), keep the head and the tail (errors are usually at the end), and say what you cut: `[... 18,400 lines omitted; call read_log(start, end) for more ...]`. A cousin is clearing old tool results: twenty steps after the agent acted on a file, replace its contents with a stub ("read utils.py, 340 lines"); Anthropic's API calls this context editing. Throws away: verbatim old outputs. Breaks the cache at the edit, so do it in batches.

**Summarization (compaction).** Near the limit, have the model summarize the history, then continue from the summary plus the last few turns. <Term w="compaction">Replacing a long conversation history with a shorter model-written summary of it, so the agent can keep going in a fresh, smaller context.</Term> keeps the gist well and loses specifics badly: exact numbers, the one odd log line, the thing that seemed unimportant at summary time. Tell the compaction prompt what must survive (decisions, file paths, exact values used), and test it: a summarizer that drops one critical fact fails silently.

**Structured memory files.** Instead of hoping a summary keeps the right facts, have the agent write them down on purpose in a `NOTES.md` or progress file and re-read it when needed. This is the `CLAUDE.md` pattern; this site has one, with a "lessons learned" section that past lesson-writing agents added to. MemGPT (2023) took the idea furthest: the window as RAM, external storage as disk, the model paging between them, [virtual memory](/lessons/virtual-memory/) for text. Throws away: whatever the agent didn't think to write down.

### Context engineering: the actual job

Put all of this together and you get a job description. At every step of an agent loop, the harness decides what goes on the desk. A good harness:

- **Keeps the top stable** (system prompt, tool definitions, memory file) and puts anything that changes at the end, so the cache works.
- **Caps every tool result**, with a note on how to get more.
- **Loads just in time** where the model can search, and preloads only what's needed on nearly every step.
- **Writes down what matters** in a memory file, instead of hoping it survives a summary.
- **Compacts with a tested prompt**, rarely and in big batches, because each compaction costs a full-price re-read.
- **Delegates wide, noisy exploration** to sub-agents and keeps their reports.
- **Measures**: tokens in, tokens cached, dollars, seconds and success rate, on tasks long enough to hit the wall.

The last bullet is the one people skip, and it's the rest of this lesson.

```python
"""Generate a fake codebase with planted, checkable facts, plus a session of questions.

python3 make_corpus.py --files 100 --seed 0   ->  corpus/  questions.json
"""
import argparse, json, os, random

WORDS = ("billing ledger refund invoice quota shard replica cache token session audit "
         "export import router queue worker crawler parser ranker index snapshot").split()
FILLER = '''
def {name}(items, limit={n}):
    """Walk the items and keep the ones under the limit."""
    out = []
    for i, x in enumerate(items):
        if i >= limit:
            break
        if isinstance(x, dict) and x.get("ok"):
            out.append(x)
    return out
'''

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--files", type=int, default=150)
    ap.add_argument("--filler", type=int, default=12, help="filler functions per file")
    ap.add_argument("--questions", type=int, default=30)
    ap.add_argument("--seed", type=int, default=0)
    a = ap.parse_args()
    rng = random.Random(a.seed)

    names = set()
    while len(names) < a.files:
        names.add(f"{rng.choice(WORDS)}_{rng.choice(WORDS)}")
    mods = sorted(names)
    facts = {m: {"TIMEOUT_MS": rng.randrange(100, 9999),
                 "RETRY_LIMIT": rng.randrange(1, 20),
                 "entry": f"handle_{m}",
                 "calls": None} for m in mods}
    for m in mods:  # each entry point calls one helper in another module
        facts[m]["calls"] = rng.choice([x for x in mods if x != m])

    os.makedirs("corpus/services", exist_ok=True)
    total = 0
    for m in mods:
        f, dep = facts[m], facts[m]["calls"]
        body = [f'"""Service module {m}."""', f"from services.{dep} import helper_{dep}", "",
                f"TIMEOUT_MS = {f['TIMEOUT_MS']}", f"RETRY_LIMIT = {f['RETRY_LIMIT']}", ""]
        fill = [FILLER.format(name=f"_step_{m}_{k}", n=rng.randrange(5, 500)) for k in range(a.filler)]
        entry = (f"\ndef {f['entry']}(request):\n    data = _step_{m}_0(request.items)\n"
                 f"    return helper_{dep}(data, retries=RETRY_LIMIT)\n")
        helper = f"\ndef helper_{m}(data, retries=1):\n    return [d for d in data][:retries]\n"
        fill.insert(rng.randrange(len(fill) + 1), entry)
        fill.insert(rng.randrange(len(fill) + 1), helper)
        text = "\n".join(body) + "".join(fill)
        total += len(text)
        with open(f"corpus/services/{m}.py", "w") as fh:
            fh.write(text)

    qs, asked = [], []
    for i in range(a.questions):
        if asked and i % 5 == 4:  # every 5th question looks back at an earlier one
            j = rng.choice(asked)
            m = qs[j]["module"]
            qs.append({"id": i, "kind": "recall", "module": m,
                       "q": f"Look back at question {j}. What is RETRY_LIMIT in the module whose "
                            f"function you named in that answer? Reply with the number only.",
                       "answer": str(facts[facts[m]["calls"]]["RETRY_LIMIT"])})
            continue
        m = rng.choice(mods)
        dep = facts[m]["calls"]
        qs.append({"id": i, "kind": "two-hop", "module": m,
                   "q": f"The function handle_{m} calls a helper from another module. "
                        f"Name that helper, then give TIMEOUT_MS from the helper's module. "
                        f"Reply as: helper_name, number",
                   "answer": f"helper_{dep}, {facts[dep]['TIMEOUT_MS']}"})
        asked.append(i)
    json.dump(qs, open("questions.json", "w"), indent=1)
    print(f"{a.files} files, {total:,} chars (~{total // 4:,} tokens by the chars/4 rule), "
          f"{len(qs)} questions")

if __name__ == "__main__":
    main()
```

```python
# llm.py
import json, os, time
import anthropic

MODEL = os.environ.get("CTX_MODEL", "claude-haiku-4-5")   # check the models page for current ids
PRICE = {"in": 1.00, "out": 5.00, "write": 1.25, "read": 0.10}  # $/M and multipliers; check pricing
BUDGET = float(os.environ.get("CTX_BUDGET", "5.00"))     # hard stop in dollars
client = anthropic.Anthropic()
spent = 0.0

def call(system, messages, tools=None, max_tokens=512, tag=""):
    global spent
    if spent > BUDGET:
        raise RuntimeError(f"budget exceeded: ${spent:.2f}")
    t0 = time.perf_counter()
    kw = dict(model=MODEL, max_tokens=max_tokens, system=system, messages=messages)
    if tools:
        kw["tools"] = tools
    r = client.messages.create(**kw)
    dt = time.perf_counter() - t0
    u = r.usage
    read = getattr(u, "cache_read_input_tokens", 0) or 0
    write = getattr(u, "cache_creation_input_tokens", 0) or 0
    cost = (u.input_tokens * PRICE["in"] + write * PRICE["in"] * PRICE["write"]
            + read * PRICE["in"] * PRICE["read"] + u.output_tokens * PRICE["out"]) / 1e6
    spent += cost
    with open("ledger.jsonl", "a") as f:
        f.write(json.dumps(dict(tag=tag, input=u.input_tokens, cache_read=read, cache_write=write,
                                output=u.output_tokens, cost=cost, seconds=dt)) + "\n")
    return r
```

Note that in Anthropic's `usage`, `input_tokens` counts only the uncached part; the total prompt is `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`. To cache a big system prompt, pass `system` as a list of text blocks and put `"cache_control": {"type": "ephemeral"}` on the last stable one. The SDK and field names are as of 2025; check the docs if anything has moved.

The three strategies:

- **(a) stuff.** No tools. The whole corpus goes in the system prompt, each file wrapped like `<file path="services/x.py">...</file>`, marked for caching. History is append-only (questions and answers only), no window limit beyond the model's own.

<details>
<summary>1. Why does an agent's API bill grow faster than linearly with the number of steps, and what are two ways to fix it?</summary>

The model is stateless, so every call resends the whole conversation. If each step adds about the same number of tokens, step k sends about k times that, and the total over n steps is about n²/2 times the per-step size: quadratic. Fix one: prompt caching. The history is append-only, so each request's prefix was already processed; the provider bills it at about a tenth of the price and skips most of the prefill. Total cost becomes close to linear, as long as nothing near the top of the prompt changes. Fix two: keep the per-step growth small: cap tool outputs, clear old tool results, push noisy exploration into sub-agents that return short reports. Compaction also caps the size, but each compaction rewrites the prefix and costs a full-price re-read, so do it rarely.

</details>

<details>
<summary>2. A vendor says their model scores 100% on needle-in-a-haystack at 1M tokens. What does that tell you, and what doesn't it?</summary>

It tells you the model can find a single sentence that shares obvious words with the question, anywhere in a long input: a good sign that position encoding and attention work at that length. It doesn't tell you the model can find information without word overlap (NoLiMa-style tests drop sharply), pick the right fact among many near-identical ones, combine two facts from far apart, or keep reasoning quality over that much text (RULER and "context rot" style results). Attention is a fixed budget split over all tokens, so near-misses compete for it. The only number I'd trust is accuracy on my own task at my own lengths.

</details>

<details>
<summary>3. Explain "lost in the middle" and what you change in a prompt because of it.</summary>

Liu et al. showed that models answer best when the relevant document is at the start or end of a long prompt and worst when it's in the middle; for one model the middle was worse than giving no documents at all. The reasons are partly understood: training data puts important things at the start and end, models put a lot of attention on the first tokens, and position encodings favor recent tokens. So: put instructions and the question at the end, right before the model writes; put the most important material first or last; and send fewer, better-ranked documents rather than more, which is where a good reranker earns its keep.

</details>

<details>
<summary>4. When would you stuff a whole corpus into the prompt, and when would you retrieve? How does the answer change as the corpus grows?</summary>

Stuff when it fits with room to spare, you'll ask many questions within the cache's lifetime, and the content isn't full of near-duplicates: one contract, one paper, a small repo. With caching, the repeat calls are cheap and nothing is ever missed. Retrieve when it doesn't fit, when it changes too often to cache, or when it's full of similar-looking items that would dilute attention. As the corpus grows past the window (say from 100K to 10M tokens) stuffing simply stops being possible, so the question becomes how good your retrieval is: chunking that follows the structure (functions for code), hybrid keyword plus embedding search, a reranker, and letting the agent search repeatedly for multi-hop questions.

</details>

<details>
<summary>5. How does this scale? You serve 1,000 concurrent agent sessions, each holding 100K tokens of context, on Llama 3.1 8B. What breaks first?</summary>

Memory. From the KV cache lesson, Llama 3.1 8B in bf16 stores 128 KiB per token. 100K tokens is about 12.2 GiB per session, so 1,000 sessions is about 12 TiB of KV cache, against 16 GB of weights. No single machine holds that; even a node of eight 80 GB GPUs has 640 GB. So you can hold maybe a few dozen such sessions per node at once, and the rest wait, get evicted (and pay full prefill again when they come back), or need KV offloaded to CPU memory or disk. Every token you keep out of context is memory you get back, which is why context management is also a serving-cost problem, not just an accuracy one. Prefill is the second thing: 100K-token prefills take seconds each, and they compete with decoding for the GPU. Prefix caching helps both, as long as sessions keep their prefixes stable.

</details>

## Go Deeper

- **Nelson F. Liu et al., "Lost in the Middle: How Language Models Use Long Contexts"** (2023, published in TACL 2024), [arXiv:2307.03172](https://arxiv.org/abs/2307.03172). The U-curve paper. Short, clear experiments; read the multi-document QA and key-value retrieval sections.
- **Anthropic, ["Effective context engineering for AI agents"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)** (2025). The practitioner's version of this lesson: just-in-time retrieval, compaction, structured note-taking and sub-agents, from the people who build Claude Code.
- **Anthropic, "How we built our multi-agent research system"** (2025, Anthropic engineering blog). Where the sub-agent token numbers come from, and an honest account of when multiple agents are worth the cost.
- **Greg Kamradt, "Needle In A Haystack: Pressure Testing LLMs"** (2023), code at [github.com/gkamradt/LLMTest_NeedleInAHaystack](https://github.com/gkamradt/LLMTest_NeedleInAHaystack). The original test. Worth reading alongside Anthropic's follow-up post "Long context prompting for Claude 2.1" for how much the prompt mattered.
- **Cheng-Ping Hsieh et al. (NVIDIA), "RULER: What's the Real Context Size of Your Long-Context Language Models?"** (2024). The benchmark that took needle tests apart: multiple needles, variable tracing, aggregation, and "effective length".
- **Patrick Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks"** (NeurIPS 2020), [arXiv:2005.11401](https://arxiv.org/abs/2005.11401). Where RAG starts. Then Anthropic's "Introducing Contextual Retrieval" (2024) for a modern, measured take on chunking plus reranking.
- **Charles Packer et al., "MemGPT: Towards LLMs as Operating Systems"** (2023), [arXiv:2310.08560](https://arxiv.org/abs/2310.08560). The context window as RAM, external storage as disk, the model as its own memory manager. A fun read after [virtual memory](/lessons/virtual-memory/).
- **Anthropic, Prompt caching docs** (docs.anthropic.com / platform docs, "Prompt caching"). The exact rules: breakpoints, minimum lengths, lifetimes, pricing multipliers and the `usage` fields you're logging.
