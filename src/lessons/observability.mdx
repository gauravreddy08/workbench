## The Problem

Your Spark is serving Llama to an agent harness a teammate wrote. One morning there is a message: "the agent sometimes stalls for a second or so before it starts answering. Not always. Started last night maybe?"

You look at what you have. The benchmark harness from the baseline lesson says p50 TTFT is fine. You run five requests by hand: all fast. You open the server's terminal and scroll through forty thousand lines of `got request` and `done`, with no way to tell which `done` belongs to which `got request`, or which ones were slow. You read the code. It looks exactly like it did last week, because it is exactly the same code.

That last point is the whole lesson. **You can't debug production by reading code**, because the code is the same for every request and the behavior isn't. What changed is everything around the code: the inputs (one customer started sending prompts with code blocks), the load (a batch job runs at 2am now), the dependencies (one database shard is sick), and the timing between requests (two of them grabbing the same lock at once). None of that is in the source file. It only exists in the running system, and the running system forgets everything the moment it happens, unless you made it write things down.

Making it write the right things down, in a form you can search and add up later, is <Term w="observability">How well you can figure out what a running system is doing, and why, from the outside, using only what it reports about itself. The word comes from control theory.</Term>. The three classic forms of "writing things down" are logs, metrics and traces. By the end of this lesson you will have all three on your server, and you will use them to find a fault you don't know the location of.

<Origin year="2010" title="Dapper: who made this search slow?">

In the 2000s a single Google web search fanned out to thousands of machines across dozens of services: spelling, ads, images, news, each with its own backends. When searches got slow, every team's dashboard said its own service was fine. Engineers could not see one request's path through the whole system, so they could not say where its time went.

Google's answer, described in the 2010 paper *Dapper, a Large-Scale Distributed Systems Tracing Infrastructure* (Sigelman and colleagues), was to give every request an ID at the front door and pass it along on every internal call. Each service recorded little timed segments, "spans", tagged with that ID, and a collector stitched them back into a tree. To keep the cost tiny they recorded only a sample, about one request in 1,024 in the first version, and it was still enough to find the slow service.

Dapper inspired Twitter's Zipkin (2012) and Uber's Jaeger (2015), which in turn led to two competing open standards, OpenTracing and OpenCensus. In 2019 those merged into OpenTelemetry, which is what you'll use today. Metrics have a parallel story: Google's internal Borgmon inspired Prometheus, started at SoundCloud in 2012.

</Origin>

## The Idea

### Three ways to write things down

Think of a restaurant on a busy night. There are three ways to find out why table 12 waited forty minutes.

- **The order slips.** Every event is written down as it happens: "19:02 table 12 ordered", "19:31 grill fired table 12". Detailed, and you can read any one of them. But a busy night makes thousands, and to answer "were we slow tonight?" you'd have to read them all.
- **The tally board.** A few numbers kept running all night: orders taken, orders sent back, how many tickets are on the rail right now, how long dishes took, bucketed. Tiny, cheap, great for "are we slow?", and useless for "why was *table 12* slow?", because the tally doesn't remember tables.
- **Following one ticket.** Staple a timestamp to the ticket at every station it passes: waiter, grill, plating, pass. For one order you see exactly where the forty minutes went: twenty-eight of them sat on the grill rail.

Those are logs, metrics and traces.

- A <Term w="log">A timestamped record of one event, written by the program as it happens. One line per event: "request 7f3a finished in 1.2 s".</Term> answers **what happened, in detail, for this one event?**
- A <Term w="metric">A number tracked over time, usually aggregated: a count of requests, the current queue length, a histogram of latencies. Cheap because it doesn't keep per-request detail.</Term> answers **how much, how often, how fast, across everything, over time?**
- A <Term w="trace">The full path of one request through a system, recorded as a tree of timed steps (spans), possibly across many processes and machines.</Term> answers **where did the time go inside this one request?**

Each pillar is cheap where another is expensive, which is why you want all three and why they are wired together by one shared thing: an ID.

### Logs: events, made searchable

A `print("done")` is a log, a bad one. Three upgrades turn it into something you can debug with.

**Structure.** Write each event as one JSON object per line, not a sentence. `"request done in 1067 ms for user-0412"` is readable but you can only grep it. `{"msg": "request done", "dur_ms": 1067, "user": "user-0412"}` you can filter (`dur_ms > 1000`), group (`by user`), and count, with `jq` on your laptop or a log store at work. This is a <Term w="structured log">A log line written as machine-readable key-value fields (usually one JSON object per line) instead of free text, so tools can filter and aggregate on the fields.</Term>.

**A request id on every line.** A server handling 16 requests at once interleaves their log lines. Without an ID you can't tell which lines belong together. Generate an ID when the request arrives (or take the one the caller sent in an `X-Request-ID` header), stash it somewhere every function can reach without passing it by hand, and have the log formatter stamp it on every line. In async Python that "somewhere" is a <Term w="contextvar">A variable from Python's contextvars module whose value is private to the current task or thread, so concurrent requests each see their own value. The async-safe version of a global.</Term>. Return the same ID to the caller in a response header, so when your teammate says "request 7f3a was slow", you can find every line it wrote.

**Levels.** Each line gets a severity: `DEBUG` (chatter for developers), `INFO` (normal events worth keeping), `WARNING` (something odd that recovered), `ERROR` (a request failed). In production you usually keep INFO and above.

Then the cost, which is the thing nobody tells you. Say 1,000 requests a second, ten log lines per request, 500 bytes per line. That's 5 MB a second, which is **432 GB a day**. Log stores charge by the gigabyte ingested and stored. So big systems <Term w="sampling" label="log sampling">Keeping only a fraction of events, for example every error but 1% of successful requests, to cut storage cost while keeping the interesting cases.</Term>: keep every error and every slow request, and maybe 1% of the boring successful ones. On your one server you can keep everything. Your company can't.

The other cost is time. A JSON log line formatted in Python cost about 4 µs on my Mac (writing to memory, Python 3.14). Nothing next to a 500 ms request, a lot inside a loop that runs per token.

### Metrics: numbers you can add up

A metric throws away the details on purpose so it can be kept forever and summed across machines. There are three kinds, and Prometheus (the standard open-source metrics system) names them like this:

- A <Term w="counter">A number that only goes up: total requests, total errors, total tokens generated. You look at how fast it climbs, not its value.</Term>. Total requests served. Its value is meaningless (it resets when the process restarts); its **rate** is everything. "Requests per second over the last minute" is the counter's slope.
- A <Term w="gauge">A number that can go up and down and is read as-is: requests in flight right now, queue length, memory used, KV cache fraction in use.</Term>. Requests in flight right now. Queue depth. Memory in use.
- A <Term w="histogram">In metrics, a set of counters, one per latency range ("bucket"), plus a total count and sum. Each observation increments the bucket it falls in. Percentiles are estimated from the bucket counts later.</Term>. Each latency increments one bucket counter. You met the idea in the [tail latency lesson](/lessons/tail-latency/) as the HDR histogram. Prometheus histograms are the same idea with buckets you choose.

Prometheus histograms are <Term w="cumulative buckets">Each bucket counts all observations less than or equal to its upper bound (le = "less or equal"), so the counts only grow from bucket to bucket and the last one, le="+Inf", equals the total.</Term>. Here's what my instrumented stand-in server printed for its end-to-end latency after 300 requests:

```text
llm_request_duration_seconds_bucket{le="0.25"} 0.0
llm_request_duration_seconds_bucket{le="0.5"} 102.0
llm_request_duration_seconds_bucket{le="0.75"} 298.0
llm_request_duration_seconds_bucket{le="1.0"} 300.0
... (every bucket after this also says 300)
llm_request_duration_seconds_bucket{le="+Inf"} 300.0
llm_request_duration_seconds_count 300.0
llm_request_duration_seconds_sum 167.57
```

Read it as: 102 requests took at most 0.5 s, 298 at most 0.75 s, all 300 at most 1 s, and together they took 167.6 s (so the mean was 559 ms). That's the whole histogram: a dozen numbers, however many requests it has seen. Recording one observation took about 0.4 µs on my Mac.

Which metrics? Two recipes cover almost everything:

- The <Term w="RED method">Tom Wilkie's recipe for request-driven services: track Rate (requests per second), Errors (failed requests per second) and Duration (a latency histogram), per service or endpoint.</Term>, for things that serve requests: **R**ate, **E**rrors, **D**uration. This is what your users feel.
- The <Term w="USE method">Brendan Gregg's recipe for resources (CPU, memory, disks, GPU, a lock, a queue): for each, check Utilization (how busy), Saturation (how much work is waiting) and Errors.</Term>, for resources: **U**tilization, **S**aturation, **E**rrors. For your server: GPU utilization, and saturation is the queue of requests waiting for the GPU lock.

The Google SRE book's "four golden signals" (latency, traffic, errors, saturation) are the same idea, the two recipes merged.

### Labels, and the explosion

Metrics get dimensions through <Term w="label">A key-value tag on a metric, like status="error" or endpoint="/v1/chat". Every distinct combination of label values creates a separate time series that is stored on its own.</Term>s. `llm_requests_total{status="ok"}` and `llm_requests_total{status="error"}` are two separate counters, two <Term w="time series">One stream of (timestamp, value) points for one metric with one exact set of label values. The unit Prometheus stores, indexes and charges memory for.</Term>.

The trap is in the multiplication. One histogram with 12 buckets, labelled by endpoint (5 values) and status (3 values), is about 12 × 5 × 3 = 180 series. Fine. Now someone adds `user_id` as a label "so we can see per-user latency". With 100,000 users that's 18 million series. Each active series costs memory in Prometheus (on the order of kilobytes), so this is tens of gigabytes, and it happens silently the day traffic grows. This is a <Term w="cardinality explosion">When a metric's label values have so many possible combinations that the number of time series blows up, eating memory and slowing every query. Classic culprits: user ids, request ids, full URLs, raw prompts.</Term>, and it is one of the most common ways people take down their own monitoring.

The rule: **metric labels must come from a small, fixed set** (status code, endpoint, model name, region). Anything unbounded (user id, request id, prompt text) goes in logs and trace attributes, which are stored per event and built for it.

### Percentiles come from buckets, not from averages

The dashboard most people build first plots average latency. Play with this and you'll see why that's a mistake.

The average moves by 5% × 400 ms = **20 ms**, about 7%. Easy to dismiss as noise on a dashboard. p99 moves from roughly 530 ms to about 730 ms, around **200 ms**, because p99 now lands inside the slow 5%. On my stand-in server under real load (below) it was the same story: mean +31 ms, p99 +326 ms. The users who hit the fault see 400 ms more; the average spreads that over everybody and hides it.

<ObsHistogram />

</Figure>

Two lessons from that figure.

**Percentiles are estimated from buckets.** Prometheus's `histogram_quantile()` finds the bucket that the 99th-percentile request falls in and assumes requests are spread evenly inside it. With a wide bucket the estimate drifts: set 5% and +1000 ms, and p99 lands in the 1 to 1.25 s bucket, where the estimate is off by almost 100 ms. So **put bucket edges where your decisions are**. If your goal is "TTFT under 250 ms", have an edge at exactly 0.25, so "how many were under 250 ms" is an exact count, not a guess.

**You cannot average percentiles.** The p99 of the fleet is not the average of each machine's p99. In fleet mode at 5% and +1000 ms, one sick server out of four pushes the true fleet p99 to about 1.2 s, while the average of the four p99s says 730 ms. Counts add up, percentiles don't. Prometheus histograms are counters, so you add them first and estimate once:

```promql
# right: sum the bucket rates across all instances, then estimate p99
histogram_quantile(0.99, sum by (le) (rate(llm_request_duration_seconds_bucket[5m])))

# wrong: a p99 per instance, then averaged
avg(histogram_quantile(0.99, rate(llm_request_duration_seconds_bucket[5m])))
```

This is the same rule the [tail latency lesson](/lessons/tail-latency/) gave for HDR histograms, now in the language your dashboards speak. (Prometheus also has "summaries", which compute percentiles inside each process. Those can't be added across machines at all, which is why histograms are usually the better choice.)

### Traces: where the time went in one request

A metric told you p99 got worse. It can't tell you why, because it has forgotten every individual request. A trace keeps one request whole.

A trace is a tree of <Term w="span">One timed step inside a trace: a name, a start time, a duration, a parent, and key-value attributes. "tokenize took 2 ms", "database query took 400 ms".</Term>s. The first span, the <Term w="root span">The top span of a trace, with no parent. Usually "the whole request as the first service saw it".</Term>, covers the whole request. Each step inside it is a child span; steps inside those are grandchildren. Every span records which span is its parent, and every span in the tree shares one <Term w="trace id">A random 128-bit number shared by every span of one request, across every service. It is how the collector knows which spans belong together.</Term>.

Drawn on a timeline, a trace is a waterfall. Here is one streaming request to an inference server, through a gateway, a quota database check, the server, and the model. Plant a fault and see which span grows.

Things to notice while you click:

- **Slow DB** happens in the gateway, before the server is even called. The server's metrics would be perfect while users suffer. Only something measuring the whole request (the trace's root span, or the gateway's own metrics) sees it.
- **Cache lock** is a span whose own work takes microseconds but whose duration is 300 ms: it was *waiting*. A CPU profiler would say that code is idle. The trace says it's the problem.
- **GPU queue** grows on every request at once, which is how you tell "overloaded" from "broken".
- **Slow decode** doesn't touch TTFT at all. A TTFT-only dashboard says all is well while every answer takes 70% longer.

Spans also carry <Term w="attribute" label="span attribute">A key-value pair attached to a span, like user="user-0412" or prompt_chars=176. Unlike metric labels, these can have unbounded values, because they are stored per span.</Term>s: the user, the prompt length, the model, the number of output tokens. This is where the high-cardinality detail that's banned from metrics lives. When you find the slow traces, their attributes tell you what they have in common.

### Context propagation: one trace, many processes

Within one process, the tracing library keeps track of "the current span" in a contextvar, so any new span automatically becomes its child. Across processes there's no shared memory, so the parent has to travel with the request. That's <Term w="context propagation">Passing the trace id and current span id from one service to the next inside the request itself (usually an HTTP header), so the receiving service's spans join the same trace.</Term>, and on HTTP it's one header defined by the W3C <Term w="Trace Context">The W3C standard that defines the traceparent header (and tracestate) so tracing works across services written in different languages with different tracing libraries.</Term> standard: `traceparent`.

The last field carries the <Term w="sampling decision" label="head sampling">Deciding at the very start of a request whether to record its trace (say, 1 in 100), and passing that decision downstream in the traceparent flags so every service agrees.</Term>. If the gateway decided not to record this request, every service downstream skips it too, so you never get half a trace. When I ran the current Python SDK, it printed flags `03`: the extra bit is a newer Trace Context addition that marks the trace id as random. Your version may differ.

### SLIs, SLOs and error budgets

Dashboards are for looking. At 3am nobody is looking, so something has to decide when to wake you. The Google SRE book's answer starts with three terms:

- An <Term w="SLI">Service level indicator: a measured fraction of good events. "Fraction of requests whose first token arrived within 250 ms."</Term> is a measurement of how users experience the service, as a ratio: good events over all events.
- An <Term w="SLO">Service level objective: a target for an SLI over a window. "99% of requests get their first token within 250 ms, measured over 30 days."</Term> is the target for it: "99% of requests get their first token within 250 ms, over 30 days."
- The <Term w="error budget">The amount of badness the SLO allows: 1 minus the target. With a 99% SLO, 1% of requests may be bad. It's a budget you can spend on deploys, experiments and incidents.</Term> is everything the SLO lets you get wrong: 1% of requests. If you serve a million requests a month, 10,000 can be slow and you've still met your goal.

Why not aim for 100%? Because the last nines are wildly expensive, users can't tell 99.99% from 100% through their own flaky Wi-Fi, and a team that may never break anything never ships anything. The budget turns "is it reliable enough?" from an argument into arithmetic: budget left means ship; budget gone means slow down and fix things.

Then the <Term w="burn rate">How fast you're spending the error budget, relative to spending it exactly evenly over the window. Burn rate = (bad fraction right now) / (1 − SLO target). 1 means "on track to use exactly all of it"; 10 means "gone in a tenth of the window".</Term>:

```text
burn rate = (fraction of bad requests, recently) / (1 − SLO)
```

With a 99% SLO, 1% bad is burn rate 1: you'll use exactly the whole budget by day 30. 6% bad is burn rate 6: the budget is gone in 5 days.

### Alert on symptoms, not causes

There are two kinds of alerts. A **symptom** is something users feel: errors, slowness, the SLO burning. A **cause** is something you guess might lead to that: CPU at 90%, one replica down, a disk 80% full, GPU memory high.

Page on symptoms. A cause alert fires when nothing is wrong (the GPU at 100% is the GPU doing its job; one replica down while the others absorb the load is fine) and stays silent when something is (the slow-DB fault raises no CPU, no memory, nothing). Every page that turns out not to matter teaches the person on call that pages don't matter. That's <Term w="alert fatigue">When people get so many alerts that don't need action that they start ignoring or muting them, including the real ones.</Term>, and it's how real incidents get slept through. Rob Ewaschuk's rule of thumb from Google: every page should be urgent, actionable, and about something users notice. Causes belong on dashboards, for the human who got paged to look at next.

Burn rate is the symptom alert done well. "14.4x over the last hour" means you'll lose 2% of the month's budget in that hour, which is worth a page. Requiring a short window (say 5 minutes) to also be burning makes the alert stop as soon as the problem stops.

### The fourth pillar: profiles

A trace says which span is slow. It doesn't say which line of code inside the span is burning the time. That's a <Term w="profiler">A tool that measures where a program spends its time, by function and line. A sampling profiler looks at the call stack many times a second and counts what it sees.</Term>'s job, and you used one, `py-spy`, in [Why is Python slow?](/lessons/python-speed/). The production version is <Term w="continuous profiling">Running a low-overhead sampling profiler all the time on every production machine and storing the results, so you can ask "what was this service doing at 3:12am?" after the fact.</Term>: a sampler runs always, at low rate, on every machine, so you can ask what the code was doing at 3:12am after the fact. Google described doing this fleet-wide in 2010 (Google-Wide Profiling); open-source tools like Pyroscope and Parca do it today, and OpenTelemetry is adding profiles as a fourth signal.

One subtlety the cache-lock fault teaches: a normal CPU profile only counts threads that are running. A thread stuck waiting for a lock isn't running, so it's invisible. You need a <Term w="wall-clock profile">A profile that samples every thread whether it is running or waiting, so time spent blocked on locks, I/O or sleep shows up. py-spy's --idle flag includes idle threads.</Term>, or `py-spy dump`, which prints every thread's current stack, waiting or not.

### Observing an LLM server

Everything above applies, with a few numbers that only LLM serving has. Most come straight from the [baseline lesson](/lessons/baseline-vs-fireworks/):

| Metric | Kind | Why |
| --- | --- | --- |
| TTFT | histogram | What chat users feel. Covers queue + prefill. |
| ITL (time per output token) | histogram | Decode speed. Catches slowdowns TTFT misses. |
| Output tokens/s | counter (`rate()` of it) | Aggregate throughput, what you'd bill for. |
| Prompt and output tokens | counters | Cost, and the input to every capacity estimate. |

vLLM and SGLang already expose most of these on a `/metrics` endpoint in Prometheus format. The names change between versions, so `curl` it and look rather than trusting a blog post.

For agents, the trace is the natural unit. One agent run is one trace; each model call and each tool call is a span, with attributes for the model, input and output tokens, the tool name and whether it errored. The waterfall then answers questions that are otherwise miserable: "why did this run take 4 minutes?" (eleven sequential tool calls, one of them a 90 s web fetch), "where do the tokens go?" (the context re-sent on every step). OpenTelemetry has draft conventions for these attribute names (the `gen_ai.*` attributes); most LLM tracing products are this idea with a nice UI.

# deps.py: the "dependencies" of the fake inference server.
# One of three faults is switched on at startup, chosen from FAULT_SEED.
# Don't read past this comment until you've found it with telemetry.
import asyncio, hashlib, os, random, threading, time

_rng = random.Random(os.environ.get("FAULT_SEED", "0"))
_FAULT = _rng.choice(["cache_lock", "slow_quota", "tokenizer"])
if os.environ.get("NO_FAULT"):
    _FAULT = "none"
_cache_lock = threading.Lock()
_cache: dict[str, bool] = {}


def reveal() -> str:
    return _FAULT


async def quota_check(user_id: str) -> bool:
    """Pretend database call: is this user under their rate limit?"""
    await asyncio.sleep(0.003)
    if _FAULT == "slow_quota" and int(hashlib.md5(user_id.encode()).hexdigest(), 16) % 20 == 0:
        await asyncio.sleep(0.4)  # this tenant's row lives on a sick shard
    return True


def tokenize(prompt: str) -> list[int]:
    """Pretend tokenizer. ~1 token per 4 chars."""
    time.sleep(0.0005 + len(prompt) * 2e-7)
    if _FAULT == "tokenizer" and "```" in prompt:
        time.sleep(0.25)  # pathological regex on code fences
    return list(range(max(1, len(prompt) // 4)))


def cache_lookup(prefix_key: str) -> bool:
    """Pretend prefix cache. Shared by every request, guarded by a lock."""
    with _cache_lock:
        if _FAULT == "cache_lock" and random.random() < 0.05:
            time.sleep(0.3)  # "compaction" while holding the lock
        hit = prefix_key in _cache
        _cache[prefix_key] = True
        return hit
````

The server. Four "batch slots" stand in for the GPU; prefill costs 400 µs per prompt token and each output token 20 ms.

```python
# fakellm.py: a stand-in for server_naive.py with the same shape and fake timings.
import asyncio, json, random, time, uuid

from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

import deps

app = FastAPI()
gpu = asyncio.Semaphore(4)       # 4 "batch slots"; the rest queue
PREFILL_S_PER_TOKEN = 0.0004     # 400 µs per prompt token
ITL_S = 0.02                     # 20 ms per output token (50 tok/s)


class ChatRequest(BaseModel):
    messages: list[dict]
    max_tokens: int = 64
    user: str = "anon"


@app.get("/health")
async def health():
    return {"ok": True}


@app.post("/v1/chat/completions")
async def chat(req: ChatRequest):
    rid = f"chatcmpl-{uuid.uuid4().hex[:12]}"
    prompt = "\n".join(m.get("content", "") for m in req.messages)

    async def events():
        await deps.quota_check(req.user)
        ids = await asyncio.to_thread(deps.tokenize, prompt)
        await asyncio.to_thread(deps.cache_lookup, prompt[:64])
        async with gpu:
            await asyncio.sleep(len(ids) * PREFILL_S_PER_TOKEN)        # prefill
            n = random.randint(req.max_tokens // 2, req.max_tokens)
            for i in range(n):                                          # decode
                yield f"data: {json.dumps({'id': rid, 'choices': [{'delta': {'content': f'tok{i} '}}]})}\n\n"
                await asyncio.sleep(ITL_S)
        usage = {"prompt_tokens": len(ids), "completion_tokens": n}
        yield f"data: {json.dumps({'id': rid, 'choices': [{'delta': {}, 'finish_reason': 'length'}], 'usage': usage})}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(events(), media_type="text/event-stream")
```

The load generator is open-loop (from the [tail latency lesson](/lessons/tail-latency/)): it sends at a fixed rate whether or not the server keeps up, from 500 fake users, with a mix of prompts.

````python
# loadgen.py: open-loop load at a fixed rate.  usage: python loadgen.py RATE SECONDS
import asyncio, random, sys, time
import httpx

URL = "http://127.0.0.1:8000/v1/chat/completions"
RATE = float(sys.argv[1]) if len(sys.argv) > 1 else 5.0
DURATION = float(sys.argv[2]) if len(sys.argv) > 2 else 60.0
USERS = [f"user-{i:04d}" for i in range(500)]
PROMPTS = [
    "Summarize this page about solar panels." * 8,
    "Rank these five documents for the query 'cheap flights'." * 12,
    "Explain this code:\n```python\nprint('hi')\n```" * 4,
    "Write a haiku about latency.",
]
WEIGHTS = [50, 30, 5, 15]


async def one(client: httpx.AsyncClient):
    body = {"messages": [{"role": "user", "content": random.choices(PROMPTS, WEIGHTS)[0]}],
            "max_tokens": 32, "user": random.choice(USERS)}
    try:
        async with client.stream("POST", URL, json=body) as r:
            async for _ in r.aiter_lines():
                pass
    except httpx.HTTPError as e:
        print("error:", type(e).__name__)


async def main():
    async with httpx.AsyncClient(timeout=30, limits=httpx.Limits(max_connections=500)) as client:
        tasks, t0, i = [], time.perf_counter(), 0
        while time.perf_counter() - t0 < DURATION:
            tasks.append(asyncio.create_task(one(client)))
            i += 1
            await asyncio.sleep(max(0, i / RATE - (time.perf_counter() - t0)))
        await asyncio.gather(*tasks)
        print(f"sent {i} requests")

asyncio.run(main())
````

A method that works for any incident:

## Break It

1. **Add `user` as a metric label.** Put `labelnames=["user"]` on the duration histogram, run load for a minute, and count lines: `curl -s localhost:8000/metrics | wc -l`. With 500 users and ~15 lines per histogram, expect several thousand lines where there were a few dozen. Now imagine 100,000 users and 50 servers, and Prometheus's memory. Take it out and put `user` on the span instead.
2. **Forget to extract the context.** Remove `context=ctx` from the root span. Jaeger now shows two separate traces per request, one from loadgen and one from the server, with nothing joining them. This is what a single service that doesn't propagate headers does to a whole company's traces: a hole in the middle of every request.
3. **Make telemetry the outage.** Swap `BatchSpanProcessor` for `SimpleSpanProcessor` (exports synchronously, on every span end) and point the exporter at an address that never answers, such as `http://192.0.2.1:4318/v1/traces`. Watch your p99. Each span end now waits for a network timeout inside the request. Lesson: telemetry must never block the work, and its failure must not be your failure. (Check how long the exporter's default timeout is in your version.)
4. **Average the p99s.** Run two copies of the server on ports 8000 and 8001, plant the fault in only one, send load to both, and add a Grafana panel with the "wrong" query from The Idea next to the right one. Measure the gap. Then write a cause alert, "CPU above 80%", and check it against your runs: it fires for none of the three faults, because every one of them is time spent waiting, not computing. On the Spark, the equivalent "GPU above 90%" would fire on every healthy benchmark, because a busy inference server is supposed to be busy. Missed real problems plus constant false alarms: that's alert fatigue in one panel.

## Explain It Back

Answer out loud, in plain words, as if in an interview. Then check.

<details>
<summary>1. What do logs, metrics and traces each answer, and why not just pick one?</summary>

Logs answer "what exactly happened in this event": full detail, one line per event, searchable by any field, but expensive at volume and they don't add up into trends easily. Metrics answer "how much, how often, how fast, over time, across everything": a few counters and histograms, cheap to keep forever and to sum across machines, but they forget individual requests, so they can tell you p99 got worse and not why. Traces answer "where did the time go in this request": a tree of timed spans across services, with attributes. Usually sampled because they're heavier. In an incident you use them in order: a metric alerts you (symptom), traces show you which step (location), logs and span attributes show you which requests and what they share (cause). A request id or trace id on all three is what lets you jump between them. Profiles are the fourth: which line of code inside the slow span.

</details>

<details>
<summary>2. Why can't you average p99s across servers, and what do you do instead?</summary>

A percentile isn't additive. The fleet's p99 is the value 1% of all requests exceed, and that depends on how many requests each server handled and on the shape of each one's tail, none of which the per-server p99s preserve. In Figure 2, one sick server among four pushes the true fleet p99 to about 1.2 s while the average of the four p99s says 730 ms. Counts do add, so you keep histograms (bucket counters) per server, sum the bucket counts across servers, and estimate the percentile once from the total: `histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))`. The estimate is only as precise as the bucket edges, so put edges at the thresholds you care about, like the SLO's 250 ms.

</details>

<details>
<summary>3. How does a trace follow a request from one service to another?</summary>

The first service creates a trace id (128 random bits) and a span id for its current span. When it calls the next service, it adds a `traceparent` HTTP header containing a version, the trace id, its current span id (the parent), and flags including whether this trace is being sampled. The receiving service reads the header and starts its first span as a child of that parent, with the same trace id. Every service ships its own spans to a collector separately; the collector groups them by trace id and uses the parent ids to rebuild the tree. If any service in the middle drops the header, the trace breaks into pieces. Because the sampling decision travels in the header, every service agrees whether to record a given request, so you don't get half-traces.

</details>

<details>
<summary>4. What is an error budget and a burn rate, and why page on burn rate rather than CPU?</summary>

An SLO says what fraction of events must be good over a window, like 99% of requests with TTFT under 250 ms over 30 days. The error budget is the rest: 1% of requests may be bad. Burn rate is how fast you're spending it compared with spending it evenly: current bad fraction divided by 0.01. At 1 you'll use exactly the whole budget by the end of the window; at 6, it's gone in 5 days; at 14.4 for an hour, you've lost 2% of the month's budget in that hour, which is worth waking someone. CPU is a cause, not a symptom: it's high when the server is simply busy (fine) and normal when a database shard is slow (not fine). Paging on it gives false alarms that train people to ignore pages, and misses real problems. Burn rate measures exactly what users feel, and the size of the threshold maps directly to how urgent it is.

</details>

<details>
<summary>5. Your inference service goes from 1 server to 200, with 50 customers. How does your observability have to change?</summary>

Metrics mostly scale fine if labels stay bounded: 200 instances times a few hundred series each is tens of thousands of series, easy for Prometheus. The danger is any label that grows with customers or requests; "customer" with 50 values might be acceptable, "user" or "prompt" never is. You'd add recording rules that pre-aggregate fleet-wide histograms so dashboards don't sum 200 instances on every refresh. Logs stop being free: 200 servers at hundreds of requests a second is terabytes a day, so you keep all errors and slow requests and sample the rest. Traces need sampling too, ideally tail sampling so every slow or failed trace survives. Per-customer questions go to trace attributes and logs. Alerts must be on the fleet SLO, not on individual machines, or one bad host pages you every night. And you'd run a profiler continuously, because with 200 machines something is always slow somewhere.

</details>

## Go Deeper

- **Benjamin H. Sigelman et al., "Dapper, a Large-Scale Distributed Systems Tracing Infrastructure"** (Google technical report, 2010). The paper every tracing system descends from. Short, and the sections on sampling and overhead are still the best argument for why tracing can be always-on.
- **Betsy Beyer, Chris Jones, Jennifer Petoff, Niall Richard Murphy (eds.), _Site Reliability Engineering_** (O'Reilly, 2016), free at [sre.google/books](https://sre.google/books/). Read "Service Level Objectives", "Monitoring Distributed Systems" (the four golden signals) and "Embracing Risk" (error budgets). Then the companion _Site Reliability Workbook_ chapter **"Alerting on SLOs"**, which derives the multi-window burn-rate alerts step by step.
- **Rob Ewaschuk, "My Philosophy on Alerting"** (2013, a Google doc widely linked from the SRE book). The source of "page on symptoms, not causes". Ten minutes, and it will change what you alert on.
- **Brendan Gregg, "The USE Method"** ([brendangregg.com/usemethod.html](https://www.brendangregg.com/usemethod.html)), and **Tom Wilkie, "The RED Method: key metrics for microservices architecture"** (Weaveworks / Grafana Labs blog and talks). The two checklists, from the people who coined them.
- **Prometheus docs, "Histograms and summaries"** ([prometheus.io/docs/practices/histograms](https://prometheus.io/docs/practices/histograms/)). Exactly how `histogram_quantile` interpolates, why summaries can't be aggregated, and how to choose buckets. Also "Metric and label naming" in the same section for the cardinality rules.
- **OpenTelemetry documentation** ([opentelemetry.io/docs](https://opentelemetry.io/docs/)), the Python getting-started page and the concepts pages on signals, context propagation and sampling. Check the GenAI semantic conventions page for the current state of LLM attributes.
- **W3C, "Trace Context"** ([w3.org/TR/trace-context](https://www.w3.org/TR/trace-context/)). The `traceparent` spec. Short and readable; it's where the field layout in Figure 4 comes from.
- **Charity Majors, Liz Fong-Jones, George Miranda, _Observability Engineering_** (O'Reilly, 2022). The argument for wide structured events and high-cardinality debugging, from the people who pushed the word "observability" into software. Read it after you've built the three pillars, as the counterpoint.
