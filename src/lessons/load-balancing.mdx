A load balancer is the front desk of a service: every request walks up to it, and it decides which of several identical copies of your program gets to handle it. Running more copies is how one machine's worth of work becomes many, and the moment you do it, anything a copy was quietly remembering in its own memory stops being shared.

This is the step every real service takes, and it's where your work lives too. An inference fleet with eight GPUs needs something deciding which GPU gets each prompt, and a bad decision can make a quick question wait a full second behind someone's essay. Send a chat's next turn to the GPU that already processed its earlier turns and you skip redoing most of that work; send it anywhere else and you pay for it again. Interviewers ask "what breaks when you add a second server?" because the answer shows whether you've run anything for real.

It builds on [Processes, threads and the GIL](/lessons/processes-threads-gil/), where you saw that one running program can't see another's memory, and [How slow is slow?](/lessons/latency-numbers/), for what a trip across the network costs. It helps to have done [p99 and load testing](/lessons/tail-latency/) before the Measure section. Next come [Rate limits and backpressure](/lessons/rate-limits/), for when even a well-spread fleet gets more traffic than it can take, and [Prefix caching](/lessons/prefix-caching/), the GPU-side half of that chat-turn trick.

## The Problem

You already got the core of this right in the diagnostic. Here's the scene, so we can build on it.

Your FastAPI app works. You log in, it creates a session (who you are, what's in your cart, the conversation so far) and keeps it in a Python dict. Traffic grows, so you run three copies behind a load balancer. You log in. Your next click says "who are you?". You refresh and it knows you again. Refresh again: gone.

You already know why. The login landed on server A, so the session lives in A's memory. The next request landed on B, whose dict has never heard of you. Three copies means three separate heaps, and from [the threads lesson](/lessons/processes-threads-gil/) you know one process can't see another's memory.

The interesting part is everything after that. Should the balancer pin you to A forever? What happens when A crashes, or restarts for a deploy? Why do LLM servers deliberately *want* your next request on the same machine, and why is that fine there but a trap for shopping carts? And how should the balancer choose, when one LLM request takes 40 ms and the next takes 40 seconds?

<Origin year="1994-2011" title="From DNS tricks to stateless processes">

In 1994, NCSA's web server (home of the Mosaic browser) outgrew one machine. Their fix, written up by Katz, Butler and McGrath, was several identical servers, with DNS handing each visitor a different machine's address in rotation. DNS round robin is still around.

It had two problems. DNS answers get cached for minutes, so a dead server kept receiving visitors. And it couldn't send a returning visitor back to the same machine, which mattered once app servers kept logins and carts in memory. Dedicated load balancer boxes appeared in the late 1990s to fix both: they checked which servers were alive, and they could pin a user to one server.

Pinning worked until servers had to restart. In 2011 Heroku's Adam Wiggins wrote *The Twelve-Factor App*. Factor VI says processes should be stateless and share nothing, and names sticky sessions as a violation. Anything that must outlive a request goes in a backing store like a database or Redis. That's where this lesson ends up.

## The Idea

### Bigger machine, or more machines

When one server can't keep up, you have two choices.

<Term w="Vertical scaling">Making one machine bigger: more cores, more RAM, faster disks. Also called scaling up.</Term> means buying a bigger box. It is underrated. No code changes, no new failure modes, and a single modern server is enormous: hundreds of cores and terabytes of RAM are a cloud API call away. The catches are that there's a ceiling (the biggest machine you can buy), the price per unit of capacity rises as you approach it, and it's still one machine: when it reboots, you're down.

<Term w="Horizontal scaling">Adding more machines that each do the same job, and spreading work across them. Also called scaling out.</Term> means running many copies. No ceiling in principle, cheap machines, and one dying is a partial loss instead of a total one. The catch is everything in this lesson: someone has to decide which copy gets each request, and any data a copy keeps in its own memory is invisible to the others.

### What a load balancer is

A <Term w="load balancer">A program (or box) that receives every incoming request or connection and forwards it to one of several backend servers, choosing which one each time.</Term> is a traffic cop. Clients only know its address. Behind it sits a pool of <Term w="backend">One of the servers behind the load balancer that actually does the work. Also called an upstream (nginx's word), a target, or a replica.</Term>s, and for every request it answers one question: who gets this one?

It also answers two quieter questions: which backends are alive right now, and how do we retire one without dropping its work? First, the state problem drawn out.

Two words in that picture. A <Term w="session">Everything the server remembers about one logged-in user between requests: who they are, their cart, their conversation so far.</Term> is the memory. A <Term w="cookie">A small string the server asks the browser to store and send back on every later request to the same site. Here it holds only a random session ID, the key into the server's session dict.</Term> is how the browser carries a key to that memory. The cookie travels with every request. The data it points to does not.

<Term w="State">Any data a server keeps that a later request depends on. If you could kill the process and restart it with no one noticing, it had no state.</Term> is the general name: sessions, but also in-memory caches, rate-limit counters, files on local disk, open WebSockets. There are two ways out:

1. **Make the balancer send each user back to the same server.** That's a <Term w="sticky session">Also called session affinity. The balancer routes every request from one user to the same backend, usually by hashing a cookie or the client's IP, so in-memory state keeps working.</Term>.
2. **Make the servers forget.** Keep the session somewhere every server can read, like Redis or a database, so any server can handle any request. That's a <Term w="stateless server">A server that keeps nothing between requests in its own memory or disk. Everything a later request needs is either in the request itself or in a shared store.</Term>.

Option 1 is a patch, option 2 is the fix. You'll build both and break the patch. First, the balancer itself.

### L4 and L7: what the balancer can see

A request is a stack of envelopes: IP (addresses), inside it TCP (ports, a connection), inside that usually TLS (encrypted), and only then the HTTP request with its path, headers, cookies and your prompt. Balancers are named after how many envelopes they open, using the old <Term w="OSI layers">A numbering of network protocol layers. The ones that matter here: layer 3 is IP (addresses), layer 4 is TCP/UDP (ports, connections), layer 7 is the application protocol, like HTTP.</Term> numbering.

An <Term w="L4 load balancer">Balances at the transport layer: picks a backend when a TCP connection opens, then shovels its bytes back and forth without reading them. Examples: AWS NLB, Google's Maglev, Linux IPVS, HAProxy in TCP mode.</Term> makes one choice per *connection*. It's fast, handles millions of packets per second, and doesn't need your TLS certificate. But it can't read a cookie, can't tell `/healthz` from a 30-second generation, and can't retry a request, because it never sees where one request ends.

That bites with HTTP/2 and gRPC, which send many requests over one long-lived connection. Behind an L4 balancer, all of a client's requests go wherever its one connection landed, forever. This is the classic "gRPC load balancing doesn't work" complaint.

An <Term w="L7 load balancer">Balances at the application layer: accepts the client's connection, decrypts TLS, parses each HTTP request, then opens (or reuses) its own connection to a backend of its choice. Examples: nginx, Envoy, HAProxy in HTTP mode, AWS ALB.</Term> is really a <Term w="reverse proxy">A server that accepts requests on behalf of other servers and forwards them. "Reverse" because it represents the servers, not the clients (a normal proxy represents clients).</Term>. It holds one connection to the client and one to the backend and reads everything in between, so it can route by path, balance per request, add headers, and retry on another backend. It costs more CPU per request and needs your TLS keys. Big systems use both: L4 at the edge spreading connections over a fleet of L7 proxies. nginx is L7 in its `http` block (and L4 in its `stream` block).

### How to choose: the algorithms

Now the interesting question. A request arrives. Three healthy, stateless backends. Who gets it?

**Round robin.** A, B, C, A, B, C. No information needed, perfectly fair by *count*. nginx's default, and nearly perfect if every request costs the same.

**Random.** Fair on average but streaky: sometimes three in a row land on one server while another idles. Worse than round robin for equal-cost requests.

**Least connections.** Send it to the backend with the fewest requests in progress. The balancer knows this for free: requests it forwarded and hasn't heard back from. This is the first algorithm that *reacts*. A backend stuck on a slow request piles up open connections and stops getting new ones.

That matters because round robin is fair by count, not cost, and LLM requests are the extreme case of uneven cost: a one-word classification, then a 2,000-token essay, a factor of a hundred apart. Round robin gives A the next request whether or not A is still writing that essay, and every short request behind a long one waits for it.

About that last one: with S1 at half speed, round robin still sends it a quarter of the requests, but S1 has only a seventh of the capacity (0.5 of 3.5). It gets more work than it can ever finish, its queue grows without bound, and a quarter of your users wait forever. Least connections sees the pile of open requests and routes around it. Degraded machines (a noisy neighbour, a throttling GPU, a cold cache) are common in real fleets. That's the strongest argument for load-aware balancing.

**Power of two random choices.** Least connections assumes one balancer with perfect, current counts. Real systems have many balancers (nginx worker processes, dozens of proxy machines), each with a partial, slightly stale view. If they all send to "the least loaded server", they all pick the *same* one at once and flatten it. This is a <Term w="herd effect">When many independent decision-makers react to the same signal at the same time and all pile onto the same choice, overloading it.</Term>.

The fix is beautifully cheap: pick two backends at random, and send the request to whichever of those two has fewer connections. That's it.

<Term w="Power of two choices">Pick two servers at random and send the request to the less loaded one. Almost as good as checking every server, much more robust to stale information, and costs O(1).</Term> sounds too simple to matter. It matters exponentially. Throw *n* balls into *n* bins at random and the fullest bin gets about ln *n* / ln ln *n*. Let each ball pick the emptier of two random bins and the fullest drops to about ln ln *n* / ln 2. Azar, Broder, Karlin and Upfal proved it, and Michael Mitzenmacher's thesis carried it to load balancing. One extra random look gets most of the benefit of looking at everything, and because the picks are random, a hundred balancers with stale counts don't converge on one victim. Envoy's "least request" balancer uses it by default; nginx calls it `random two least_conn`.

In the simulator, two choices lands between random and least conn, because it models one balancer with perfect information. Two choices earns its place with many balancers and stale counts.

**Weights.** Any of these can be weighted, e.g. `server app1:8000 weight=2;` for the box with twice the GPUs.

### Hashing: when you *want* the same server

Sometimes you want a key to always land on the same backend, because that backend has something useful loaded: a cache, a model, a shard of data. The obvious way is `server = hash(key) % N`.

<Fragment slot="answer">

About **75%**. A user stays put only if `h % 3 == h % 4`, and looking at the 12 possible values of `h % 12`, that happens for just 3 of them (0, 1, 2). If each server held a warm cache for its users, you just made 75% of the caches cold at the moment you were adding capacity because you were overloaded. In general going from N to N+1 moves about N/(N+1) of the keys.

### Why LLM serving routes by prefix

Here hashing becomes central to your work. You know the KV cache: the keys and values for every prompt token, kept on the GPU so they aren't recomputed per new token. Engines like vLLM and SGLang go further with <Term w="prefix caching">Keeping the KV cache for prompts the server has already processed, so a new request that starts with the same tokens (same system prompt, same conversation so far) skips recomputing that part.</Term> (see [the prefix caching lesson](/lessons/prefix-caching/)). A chat resends the whole conversation every turn; an agent resends its system prompt and tools every step. If the server still has that prefix's KV, most of <Term w="prefill">The first phase of generating: running the whole prompt through the model at once to build its KV cache. Cost grows with prompt length. Its time is most of the time-to-first-token.</Term> is skipped. Illustrative numbers: a 10,000-token history at a few thousand tokens per second of prefill is seconds of time-to-first-token cold, well under a second if 9,800 tokens are cached.

Put eight replicas behind round robin and turn 2 has a 1-in-8 chance of finding turn 1's KV. Seven times in eight the prefix is recomputed, and seven GPUs fill their caches with copies of it. Least connections is just as blind.

So LLM routers are <Term w="cache-aware routing">Routing each request to the replica most likely to already hold its prompt prefix in KV cache, while still avoiding overloaded replicas. Also called prefix-aware or KV-aware routing.</Term>. Simple version: consistent-hash on the conversation ID or the first chunk of the prompt. Better version, used by SGLang's router (with similar ideas in NVIDIA Dynamo and llm-d): keep an approximate tree of the prefixes sent to each replica, route to the longest match, and *fall back to the least-loaded replica* when the match is too busy. Pure affinity would recreate Figure 004's slow-server disaster: one popular system prompt, one melting GPU.

This is a sticky session, and it's fine. Why? Because the KV cache is a **cache**. If that replica dies, the next request goes elsewhere, the prefix is recomputed, and the user waits a bit longer. Nothing is lost. Stickiness for *speed* is good. Stickiness for *correctness*, where the only copy of the data lives on one server, is the trap. That's the line to remember.

### Why sticky sessions are a trap

With in-memory sessions and a sticky balancer, everything works in testing. Then:

- **A server crashes.** Everyone pinned to it loses their session, mid-checkout.
- **You deploy.** Each restart is a small crash on purpose, so every deploy logs people out, and the team starts deploying less.
- **You scale.** Pinned users don't move to a new server, so it idles while the hot ones stay hot.
- **Load goes lumpy.** One heavy user, or one office behind one IP, pins a lot of work to one machine, and the balancer isn't allowed to help.
- **It's quietly fragile.** You'll see this live: pin by session cookie, and the login request that created the session wasn't routed by it.

Same root cause each time: the data has one copy, in a place designed to be disposable.

### Stateless servers, state in a shared store

So move the data out, into one shared place, usually <Term w="Redis">An in-memory key-value server. Clients send small commands over TCP (SET, GET, RPUSH, EXPIRE...) and get answers in well under a millisecond on a local network. Popular for sessions, caches, rate limits and queues.</Term> for sessions, or the database for anything that must never be lost. Any server can look up the session ID, the balancer can send each request anywhere, and killing a server bothers nobody.

The cost is one network round trip per request. From [How slow is slow?](/lessons/latency-numbers/), that's on the order of 100-500 µs inside a data centre or between containers on one machine: under 1% of a 40 ms model call. You'll measure it. Two things it doesn't solve:

- **You moved the state, you didn't remove it.** Redis must now not lose it, and must not become the new single point of failure. See [Why do we need databases?](/lessons/why-databases/).
- **Concurrency is back.** Two tabs add to the same cart at once, on two servers. If each reads the session, appends, and writes it all back, one item vanishes: the lost update from the threads lesson, across machines, where no Python lock can help. Same fix: make it one atomic step in the store (Redis's `RPUSH` appends in one command). More in [Transactions](/lessons/transactions/).

### Health checks: knowing who's alive

The balancer finds out a backend is dead in one of two ways. A <Term w="passive health check">Judging a backend's health from real traffic: if forwarding a request fails (connection refused, timeout), count a failure, and after enough failures stop using that backend for a while.</Term> watches real requests. Open-source nginx does this: `max_fails` failures within `fail_timeout` (defaults 1 and 10 s) benches a backend for `fail_timeout`, then tries it again. Free, but a real request had to fail first. An <Term w="active health check">The balancer probes each backend on a timer (say, GET /healthz every 5 s) and removes it after a few failures in a row, before a user hits it. Supported by HAProxy, Envoy, NGINX Plus, cloud balancers and Kubernetes probes.</Term> polls in the background. Detection time is interval times threshold: probe every 5 s, remove after 3 failures, and a dead backend gets traffic for up to 15 s. Two design choices hide in "what does `/healthz` check?":

- **Shallow vs deep.** Shallow: is this process up and answering HTTP? Deep: can it also reach Redis, the database, the model? Deep is dangerous. When Redis hiccups for two seconds, *every* backend fails at once, the balancer removes all of them, and a blip becomes an outage. Balancers defend against this by <Term w="failing open">When every backend looks unhealthy, ignore the health checks and send traffic to all of them anyway, on the theory that the checks are more likely wrong than everything being dead. Envoy calls this the panic threshold.</Term>. Keep the routing check about *this* process.
- **Liveness vs readiness.** Kubernetes made this split explicit. <Term w="Liveness">"Is this process stuck? If not live, restart it." Should only fail if the process truly can't recover by itself.</Term> asks whether to restart the process. <Term w="Readiness">"Should this process receive traffic right now?" Fails while starting up (model still loading), while draining, or while overloaded. Failing it removes the backend from rotation without restarting it.</Term> asks whether to route to it. An LLM server loading weights for two minutes is alive but not ready; confuse the two and it gets restarted in a loop.

### Retries, and why POST is special

When nginx can't connect to a backend, it quietly tries the next one (`proxy_next_upstream`, on by default for errors and timeouts). But if the request was already *sent* and the backend died mid-work, retrying is only safe if doing it twice is harmless: <Term w="idempotent">Doing it twice has the same effect as doing it once. GET, PUT and DELETE are supposed to be; POST is not (two POSTs to /orders make two orders).</Term>. nginx retries in-flight GETs elsewhere, but not POSTs; a POST whose backend died mid-request gets a <Term w="502">HTTP status "Bad Gateway": the proxy couldn't get a valid response from the backend. A 504 is the timeout version.</Term>. Every LLM API (`/v1/chat/completions`, `/v1/messages`) is a POST. You'll see the difference in the Build.

### Draining: leaving without dropping anything

Deploys and scale-downs remove backends on purpose. Done carelessly, everything in flight fails. Done properly it's called <Term w="draining">Taking a backend out of rotation gracefully: stop sending it new requests, let the ones it already has finish, then shut it down. Google's SRE book calls the in-between state "lame duck".</Term>, and it has four steps:

1. **Stop being chosen**: readiness starts failing, or it's deregistered.
2. **Wait for the balancer to notice**, still serving whatever arrives meanwhile.
3. **Finish in-flight work**, with a deadline longer than your longest request. For LLM streaming that can be minutes.
4. **Exit.**

At the process level, `docker stop` and Kubernetes send <Term w="SIGTERM">The polite "please shut down" signal. A process can catch it and clean up. If it doesn't exit within the grace period (10 s for docker stop, 30 s by default in Kubernetes), it gets SIGKILL, which cannot be caught.</Term>. Uvicorn catches it, stops accepting connections, finishes in-flight requests, and exits. `kill -9` sends SIGKILL, and everything in flight dies. One Kubernetes subtlety: SIGTERM and "remove this pod from the balancer" happen *at the same time*, so for a moment new requests still arrive at a process that stopped accepting. The usual fix is a `preStop` sleep of a few seconds.

### Single points of failure

A <Term w="single point of failure">One component whose failure takes the whole system down. Often abbreviated SPOF.</Term> is anything there's exactly one of in the path of every request. Put your finger on each box in the diagram: if this dies, does everything stop?

Your Build has two: nginx and Redis. Three app servers so one can die, then a single balancer in front. Fixes: two balancers sharing a virtual IP that the standby takes over (VRRP, usually via `keepalived`), several balancer IPs in DNS, or a cloud balancer (itself a hidden fleet); and a replicated Redis with failover. There's always another SPOF if you look (DNS, the region, a config push to every balancer at once). The goal isn't zero; it's knowing where they are.

```python
# app.py
import asyncio, os, secrets
from fastapi import FastAPI, Request, Response, HTTPException

SERVER = os.environ.get("SERVER_ID", "app?")
app = FastAPI()

SESSIONS: dict[str, dict] = {}   # the bug: lives in this one process's heap
GPU = asyncio.Semaphore(1)       # pretend accelerator: one request at a time
INFLIGHT = 0

def get_session(request: Request) -> dict:
    s = SESSIONS.get(request.cookies.get("sid", ""))
    if s is None:
        raise HTTPException(401, f"{SERVER}: who are you?")
    return s

@app.post("/login")
def login(user: str, response: Response):
    sid = secrets.token_hex(8)
    SESSIONS[sid] = {"user": user, "cart": []}
    response.set_cookie("sid", sid)
    return {"sid": sid, "served_by": SERVER}

@app.post("/cart")
def add(item: str, request: Request):
    s = get_session(request)
    s["cart"].append(item)
    return {"user": s["user"], "cart": s["cart"], "served_by": SERVER}

@app.get("/cart")
def cart(request: Request):
    s = get_session(request)
    return {"user": s["user"], "cart": s["cart"], "served_by": SERVER}

@app.post("/generate")
async def generate(tokens: int = 50):
    global INFLIGHT
    INFLIGHT += 1
    try:
        async with GPU:                          # queue here if busy
            await asyncio.sleep(tokens * 0.002)  # 2 ms per "token"
        return {"tokens": tokens, "served_by": SERVER}
    finally:
        INFLIGHT -= 1

@app.get("/healthz")
def healthz():
    return {"ok": True, "server": SERVER, "inflight": INFLIGHT}
```

## Break It

**1. Pin by IP.** Swap in `ip_hash;` and run the load generator. Everything lands on one backend, because to nginx all your traffic comes from one address (your Mac, or Docker's gateway). The real-world version is a whole company behind one NAT address. Sticky-by-IP balances *addresses*, and addresses aren't users.

**2. Lose cart items across machines.** Store the session as one JSON blob with a read-modify-write `add_to_cart` (GET, `json.loads`, append, SET), then fire 50 concurrent `POST /cart` calls for one session (`for i in $(seq 50); do curl ... & done; wait`). You should count fewer than 50 items: the lost update, across containers, where no Python lock helps. With `RPUSH` it's exactly 50. (Redis also has `WATCH`/`MULTI` and Lua scripts for multi-step atomic updates.)

**3. Kill the only balancer, or the only Redis.** `docker compose kill nginx`: total outage with three healthy app servers. `docker compose kill redis`: every server up, every request failing. Circle both on your diagram and decide what you'd do about each. (Making `/healthz` check Redis just turns the second into "nginx thinks every backend is dead".)

**4. Drain too fast.** Add `--timeout-graceful-shutdown 1` to the `CMD` and repeat the six-long-POSTs test with `docker compose stop app2`. Uvicorn waits a second, then cancels the running request: on my Mac the client got a `500` and the log said "Cancel 1 running task(s), timeout graceful shutdown exceeded". With `docker compose stop -t 1`, SIGKILL arrives instead and you get 502s. Your grace period must outlast your longest request, and LLM generations can run for minutes.

## Explain It Back

Answer out loud, in plain words, as if in an interview. Then check.

<details>
<summary>1. You run three copies of an app that keeps sessions in memory. What breaks, and what are the two ways to fix it? Which would you pick?</summary>

Each copy is a separate process with its own memory, so a session created on one server doesn't exist on the others, and whenever a user's next request lands elsewhere, they're a stranger. Fix one: sticky sessions, routing each user to the same server by hashing a cookie or IP. Fix two: stateless servers, with sessions in a shared store like Redis keyed by the cookie's session ID. I'd pick the second. With sticky sessions the only copy of the data lives on a disposable server, so crashes and deploys log users out, new servers don't pick up existing users, and load gets lumpy. Stickiness is fine only as a speed optimization on top of shared state, like routing chat turns to the replica with a warm KV cache.

</details>

<details>
<summary>2. Why is round robin a bad choice for an LLM inference fleet, and what would you use instead?</summary>

It's fair by count, but LLM request costs vary by 100x or more, so short requests queue behind long ones (in my test, median 725 ms vs 83 ms with least connections). It also can't route around a degraded replica, which builds an unbounded queue. Better: least outstanding requests, or power of two choices when many balancers share stale information. Best for LLMs: cache-aware routing, which sends a request to the replica most likely to hold its prompt prefix in KV cache and falls back to the least-loaded replica when that one is overloaded, ideally using the engine's own load signals (queue depth, KV cache usage) rather than connection counts.

</details>

<details>
<summary>3. How does this scale? Your stateless app handles 200 requests/s per server and you need 5,000. What changes, and what becomes the bottleneck?</summary>

The stateless app tier scales roughly linearly: 25 servers, plus headroom (say 30-35) to lose a few and still deploy. One nginx can proxy well beyond 5,000 simple requests/s, but you want two for redundancy. The shared stores are where it stops being linear. 5,000 session reads/s is comfortable for one Redis (simple operations commonly reach on the order of 100,000/s per instance; measure yours), but the database is usually the real limit, so you add caching, read replicas, and eventually sharding with consistent hashing. And watch latency budgets: one extra Redis round trip is nothing, ten in series isn't.

</details>

<details>
<summary>4. How do you deploy a new version without dropping a single in-flight request?</summary>

Drain each server before stopping it: stop being chosen (fail readiness or deregister), keep serving until every balancer has noticed (a preStop sleep in Kubernetes, since SIGTERM and endpoint removal race), finish in-flight requests with a deadline longer than the longest request (minutes for LLM streaming), then exit before SIGKILL. Roll a few servers at a time so capacity stays up. The balancer can safely retry connection failures, and idempotent requests even after sending; POSTs need idempotency keys to be retryable.

</details>

<details>
<summary>5. Your active health check probes every 5 s and removes a backend after 3 failures. A backend dies. What happens to traffic, and what would you change?</summary>

For up to about 15 s (3 × 5 s) it still looks healthy and keeps getting its share of requests, which fail unless they're retried elsewhere (connect failures, idempotent requests). Add passive checks, which bench it on the first failed connection. A shorter interval detects faster at the cost of more probes and false alarms. Keep the check shallow: if it checked Redis, one Redis blip would mark every backend down, and you'd want the balancer to fail open rather than route to nothing.

</details>

## Go Deeper

- **Google, _Site Reliability Engineering_, chapters 19 and 20: "Load Balancing at the Frontend" and "Load Balancing in the Datacenter"** (free at [sre.google/books](https://sre.google/books/)). How Google actually does it: DNS and L4 at the edge, then weighted least-loaded balancing, subsetting, and the "lame duck" draining state. The best single read for this lesson.
- **Michael Mitzenmacher, "The Power of Two Choices in Randomized Load Balancing"** (IEEE TPDS, 2001, from his 1996 thesis), and his follow-up **"How Useful Is Old Information?"** (2000). The math behind two choices, and the proof that it survives stale load information where "pick the least loaded" collapses.
- **David Karger et al., "Consistent Hashing and Random Trees: Distributed Caching Protocols for Relieving Hot Spots on the World Wide Web"** (STOC 1997). The original consistent hashing paper, written to solve the web caching problem that became Akamai.
- **Daniel E. Eisenbud et al., "Maglev: A Fast and Reliable Software Network Load Balancer"** (NSDI 2016). Google's L4 balancer: how a fleet of commodity machines replaces hardware balancers, with its own consistent hashing so any machine picks the same backend for a connection.
- **Adam Wiggins, _The Twelve-Factor App_, factor VI "Processes"** ([12factor.net/processes](https://12factor.net/processes)). One page. The canonical statement of "stateless processes, state in backing services, no sticky sessions".
- **nginx docs: [ngx_http_upstream_module](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)** (every method, `max_fails`, `zone`, `hash ... consistent`) and **[ngx_http_proxy_module's `proxy_next_upstream`](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_next_upstream)** (exactly when nginx retries, and why POST is special).
- **Lianmin Zheng et al., "SGLang: Efficient Execution of Structured Language Model Programs"** (2024, RadixAttention), plus the SGLang router docs for its cache-aware policy. Where prefix-aware routing in LLM serving comes from. Check the current docs; this area moves fast.
- **Martin Kleppmann, _Designing Data-Intensive Applications_, chapter 1 (scalability) and chapter 6 (partitioning)**. Scaling up vs out, and why naive hash-mod-N partitioning hurts when you rebalance.
