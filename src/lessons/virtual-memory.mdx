## The Problem

You want to try a 70B model on the Spark. Full bf16 weights are about 140 GB, which is more than the box's 128 GB, so you grab an 8-bit checkpoint: about 70 GB. Plenty of room. `free -h` says around 115 GB available. You write the obvious script:

```python
state = torch.load("llama-70b-int8.pt")   # read weights into memory
model = build_model()
model.load_state_dict(state)
model.to("cuda")                           # move to the GPU
```

It runs for a few minutes. The disk light blinks. The desktop gets sluggish. Then the terminal prints one word and your prompt comes back:

```text
Killed
```

No Python traceback. No `MemoryError`. No `CUDA out of memory`. `echo $?` says `137`. Nothing in your code caught anything, because nothing in your code was ever told. Something outside your process decided it should stop existing.

Three things here should bother you.

1. Python never raised `MemoryError`. Every allocation it asked for *succeeded*. So who said no, and when?
2. You had 115 GB available and needed 70 GB. Where did the rest go?
3. `.to("cuda")` is supposed to put things on the GPU. Why would that use up memory the CPU needs?

All three answers live in one idea: the addresses your program uses are not real. They're a story the kernel and the CPU tell each process, and the story has fine print. This lesson reads the fine print.

<Origin year="1962" title="The Atlas computer and the one-level store">

In the 1950s, programmers had a small, fast main memory and a big, slow drum. If your program didn't fit in main memory, you split it into pieces yourself and wrote code to swap the pieces in and out by hand, called "overlays". Some estimates had programmers spending half their time on this plumbing.

The Atlas team at Manchester (Tom Kilburn and colleagues) had a radical idea: let the *machine* do it. Every program would see one big, uniform memory. Hardware would chop that memory into fixed-size pages, keep a table saying which pages were actually in core memory and which were on the drum, and when a program touched a page that wasn't in core, the hardware would stop, fetch it, and carry on. They called it the "one-level store". We call it virtual memory, and every phone, laptop and GPU server you've used since works this way.

The OOM killer is the other end of the story. Unix systems made `fork` cheap by not copying memory until it was written, and Linux went further: it lets programs reserve more memory than exists, betting most of it will never be used. When the bet loses, something has to give. Since the late 1990s, the Linux answer has been a kernel routine that picks a process and kills it.

</Origin>

## The Idea

### A hotel with fake room numbers

Picture a hotel where every guest is told: "Your rooms are numbered 0 to 1,000,000. Use whichever you like." That's absurd, the hotel only has 500 rooms. But it works, because the front desk keeps a private book for each guest: "Guest A's room 7 is really room 212. Guest A's room 900,000 is really room 31." The guest never sees the book. They just walk to "room 7" and the desk silently sends them to 212. Most guests only ever use a handful of rooms, so 500 real rooms go a long way.

And if a guest *reserves* rooms 1 through 50,000 and never visits them? The desk writes "reserved" in the book and assigns nothing. A real room is handed over only the first time the guest actually opens the door.

That's virtual memory. The guest is your process, the fake room numbers are <Term w="virtual addresses">The addresses a program sees and uses. Every pointer in your program is one. They are translated into real RAM locations on every memory access, by hardware, using tables the kernel maintains.</Term>, the real rooms are <Term w="physical memory">The actual RAM chips. A physical address names a real location on a real memory chip.</Term>, the front desk is the CPU's <Term w="MMU">Memory management unit. Hardware in each CPU core that translates every virtual address into a physical one, using the current process's page table.</Term> plus the kernel, and the book is the page table.

In [Where do my variables live?](/lessons/stack-and-heap/) you drew one process's memory as a long strip: code at the bottom, heap growing up, stack growing down, with a huge empty gap in the middle. That strip is the guest's view: room numbers. The gap costs nothing, because nobody's assigned a real room to it. In [Processes, threads, and the GIL](/lessons/processes-threads-gil/) you saw that address `0x10a3f2c0` in one process and the same address in another point at different RAM. That's just two guests, two books.

### Pages: translating in chunks, not bytes

Keeping a book entry for every single byte would be insane: the book would be bigger than the memory. So memory is translated in fixed-size chunks called <Term w="pages">Fixed-size, aligned chunks of virtual memory, the unit the OS and MMU translate, protect and move around. Typically 4 KB on x86 Linux.</Term>. Physical RAM is chopped into chunks of the same size called <Term w="frames" label="page frames">Page-sized slots of physical RAM. A virtual page is mapped onto exactly one frame (or onto none, if it isn't in RAM).</Term>. The book only needs one entry per page.

Page size depends on the machine:

| Machine | Page size | Offset bits |
| --- | --- | --- |
| x86-64 Linux (most servers) | 4 KB | 12 |
| Apple Silicon macOS (your Mac) | 16 KB | 14 |
| ARM64 Linux | 4 KB, 16 KB or 64 KB, chosen when the kernel is built | 12, 14 or 16 |

The Spark is ARM64 Linux, so its page size depends on how NVIDIA built DGX OS's kernel. Some NVIDIA ARM server kernels use 64 KB pages; I'm not sure which the Spark ships. Don't trust me, ask the machine: `getconf PAGESIZE`. On the Mac it prints `16384`. Write the Spark's number down, every calculation below depends on it.

A virtual address splits cleanly in two. The low bits are the <Term w="offset">Which byte inside the page. With 4 KB pages, the low 12 bits (2^12 = 4096). This part is never translated.</Term>, the high bits are the <Term w="virtual page number">The address with the offset bits chopped off. It's the key looked up in the page table.</Term>. Translation swaps the page number for a frame number and keeps the offset as is.

### The page table, and why it's a tree

The book is called the <Term w="page table">The per-process data structure, kept by the kernel in RAM, that maps each virtual page number to a physical frame number plus permission bits. The MMU reads it directly.</Term>. Each entry, a <Term w="PTE">Page table entry. 8 bytes holding a frame number plus flags: present, writable, user-accessible, accessed, dirty, and so on.</Term>, holds a frame number and a few flag bits. The important ones: *present* (is this page in RAM at all?), *writable* (can you store to it?), *dirty* (has anyone written it since it was loaded?).

Why a tree and not one big array? Do the math. A 48-bit address space with 4 KB pages has 2<sup>36</sup> pages, about 69 billion. At 8 bytes per entry, a flat table would be 512 GB *per process*. Instead, x86-64 uses a four-level tree: the page number is cut into four 9-bit pieces, each indexing a 512-entry table that points to the next. The trick is that a whole subtree can be missing. The huge empty gap between your heap and stack has no tables at all, so a typical process's page tables are a few hundred KB to a few MB.

They're not free, though. Touch 100 GB with 4 KB pages and you need 26 million PTEs, about 200 MB of page tables just to describe where your memory is. That's one reason big-memory workloads use bigger pages.

Each process has its own tree; threads in one process share one tree, which is what "threads share an address space" means in hardware.

### The TLB: a tiny cache that makes it all affordable

If every memory access needed four extra memory reads to walk the tree, programs would run several times slower. So each core keeps a <Term w="TLB">Translation lookaside buffer. A small, very fast cache inside each core of recently used virtual-page-to-frame translations. A hit costs about a cycle; a miss triggers a page table walk.</Term>, a tiny cache of recent translations. A modern core has a first level of a few dozen entries and a second level of one to a few thousand (spec-sheet figures vary by core; treat these as order-of-magnitude).

Here's a number worth having in your head, the TLB's *reach*: entries times page size. Around 1,500 entries times 4 KB pages covers about 6 MB. Your model weights are 70 GB. Every time a decode step streams through the weights, it blows through the TLB thousands of times over. That's why the GPU's MMU and serious CPU workloads use <Term w="huge pages">Pages much larger than the base size, typically 2 MB (or 1 GB) on x86 and on ARM64 with 4 KB base pages. One TLB entry then covers 512 times more memory. Linux can create them automatically (Transparent Huge Pages).</Term>: one 2 MB page covers what 512 small pages would, so the same TLB reaches 3 GB.

With 64 KB base pages (if the Spark has them), reach is 16 times bigger for free.

### Lazy allocation: malloc is a promise

Now the part that explains "Python never raised MemoryError".

When your program calls `malloc(100 GB)` (or `np.zeros`, or `torch.empty`), the C library asks the kernel for address space with a system call named <Term w="mmap">The system call that adds a new region to a process's address space. It can be anonymous (plain memory, starts as zeros) or backed by a file (the region shows the file's contents).</Term>. The kernel does almost nothing. It writes down one note, "addresses X to X+100 GB belong to this process, readable and writable, start as zeros", and returns. No frames assigned. No page table entries filled in. Your process's <Term w="VSZ">Virtual size: the total of all address ranges the process has reserved, touched or not. Also called VIRT in top or VmSize in /proc. Mostly meaningless as a measure of memory use.</Term> jumps by 100 GB. Its <Term w="RSS">Resident set size: how much of the process's memory is actually in physical RAM right now. The number that matters for running out of memory.</Term> doesn't move at all.

The real work happens later, one page at a time, the first time you touch each page.

### Page faults: the CPU asks the kernel for help

When the MMU walks the tree and finds no valid entry, or finds one that doesn't allow what you're trying to do (writing a read-only page), it can't finish the instruction. It raises a <Term w="page fault">A hardware exception raised when a memory access can't be translated, or isn't allowed. The CPU stops the instruction and jumps into the kernel, which either fixes things up and retries, or kills the process.</Term>: the instruction stops, the CPU jumps into the kernel, and the kernel looks up the faulting address in its notes.

Not every fault is an error. Most are the lazy plan working as designed. The kernel sorts them into three cases:

- **Address not in any region you reserved.** You really did touch memory that isn't yours. The kernel sends `SIGSEGV`: a segfault, exactly what you saw with the stack's guard page in the stack-and-heap lesson.
- **Reserved, and the data is already in RAM somewhere (or it's just zeros).** First touch of fresh memory, a file page already in the cache, or a copy-on-write (coming up). The kernel grabs or points to a frame, fills in the PTE, and returns. Your instruction runs again and succeeds. This is a <Term w="minor fault">A page fault the kernel resolves without any disk I/O: zero-fill a fresh page, map a page that's already in the page cache, or copy a page. Costs well under a microsecond to a few microseconds.</Term>.
- **Reserved, but the data is on disk.** A page of a memory-mapped file that isn't cached yet, or a page that was pushed out to swap. The kernel issues a read, puts your thread to sleep until it arrives, maps it, and resumes. This is a <Term w="major fault">A page fault that needs disk I/O to resolve: reading a file page or swapping a page back in. Costs tens of microseconds on fast NVMe, milliseconds on spinning disks.</Term>.

Measured on my Mac: filling a fresh 4 GB NumPy array the first time took 0.21 s (19 GB/s) and took 262,149 faults, almost exactly 4 GB / 16 KB = 262,144. Filling it again, with every page already mapped, took 0.086 s (46 GB/s). The difference, spread over the faults, is about 0.5 µs per minor fault, including zeroing a 16 KB page. Put that on the [latency ladder](/lessons/latency-numbers/): a minor fault costs about as much as five trips to RAM (~100 ns each), cheap one at a time but it adds up over millions of pages. A major fault from NVMe (tens of microseconds or more) is roughly a hundred times worse again.

Here is all of it at once. Play with it: malloc, touch, fork, touch in the child, run out of frames, turn swap on and off.

### Overcommit: the kernel's bet

So `malloc` is a promise, and the kernel makes the promise before checking whether it can keep it. On Linux this is a policy called <Term w="overcommit">Letting processes reserve more memory than RAM plus swap can actually back, on the bet that most of it will never be touched. Linux does this by default.</Term>, controlled by `/proc/sys/vm/overcommit_memory`:

| Value | Name | What it does |
| --- | --- | --- |
| 0 | heuristic (default) | Refuses only obviously absurd requests, roughly a single allocation bigger than RAM plus swap. Everything else is granted. |
| 1 | always | Never refuses. `malloc(1 TB)` succeeds on a laptop. |
| 2 | never (strict) | Keeps a running total of promised memory and refuses once it passes `swap + RAM × overcommit_ratio / 100` (ratio defaults to 50). |

Why bet at all? Because programs reserve far more than they use. Every thread reserves an 8 MB stack and touches a few KB. And above all, `fork`: when a 20 GB process forks to run a tiny shell command, strict accounting would need another 20 GB "just in case" the child writes every page, even though it's about to throw them away with `exec`. With overcommit, that fork just works.

The cost: the kernel has written more cheques than it can cash. If enough processes touch their memory at once, there's no frame for the next faulting page, and the fault can't fail politely. Your program isn't calling a function, it's executing a store instruction; there's no return value to put `NULL` in. The kernel has to make room, right now.

Before killing anyone, the kernel tries to free frames. Not all memory is equal here, and the difference is the key to the "where did my 115 GB go" mystery.

**File-backed pages** hold a copy of something that's on disk: the code of `python3` itself, a shared library, a file you read, or a file you `mmap`'d. Linux keeps recently read file data in RAM in the <Term w="page cache">The kernel's in-RAM copy of recently read or written file data, shared by every process. It grows into free RAM and shrinks when programs need memory.</Term>. If a file page is *clean* (unchanged since it was read), the kernel can just drop it: if anyone needs it again, it reads it from disk again. Cheap to reclaim.

**Anonymous pages** are memory with no file behind them: your heap, your stack, NumPy arrays, every PyTorch CPU tensor you built with `torch.load`. There's no copy anywhere else. The only way to free one is to write it somewhere first, and that somewhere is <Term w="swap">Disk space (a partition, a file, or compressed RAM like zram) where the kernel parks anonymous pages it needs to evict. Touching a swapped page later is a major fault.</Term>. If there's no swap, or it's full, anonymous memory can't be reclaimed at all. It stays until the process frees it or dies.

That's why `free -h` has a "free" column and an "available" column. "Free" is RAM nobody is using, often small because the page cache happily fills idle RAM. "Available" is the kernel's estimate of what it could hand you without swapping: free plus most of the reclaimable cache. "Available" is the number to believe.

When reclaim can't keep up and swap is out, the kernel runs the <Term w="OOM killer">The Linux kernel routine that, when memory is exhausted and can't be reclaimed, picks one process and kills it with SIGKILL to free its memory. OOM = out of memory.</Term>. It scores every process and kills the highest. You can read the score yourself in `/proc/<pid>/oom_score`, from 0 to 1000. In modern kernels it's roughly "what fraction of memory this process is using" (RSS plus swap plus page tables) scaled to 1000, plus an adjustment you can set in `/proc/<pid>/oom_score_adj`, from -1000 (never kill me) to +1000 (kill me first). The logic is blunt on purpose: killing the biggest process frees the most memory with the fewest deaths.

The victim gets <Term w="SIGKILL">Signal 9. The one signal a process can't catch, block or clean up after. The kernel just stops it and frees its memory. A shell reports it as exit code 137 = 128 + 9.</Term>. That's why your script printed "Killed" and nothing else. Python never got a chance to raise anything. The confession is in the kernel log, which you read with `sudo dmesg` or `journalctl -k`:

```text
Out of memory: Killed process 48213 (python3) total-vm:142336704kB, anon-rss:117440512kB, file-rss:2048kB, shmem-rss:0kB, UID:1000 pgtables:230400kB oom_score_adj:0
```

That line (real shape, illustrative numbers) says who died, its address space (`total-vm`, the VSZ), and the real anonymous memory it held (`anon-rss`).

One more killer to know about on Ubuntu-based systems: `systemd-oomd`, a userspace daemon that watches memory *pressure* and may kill a whole group of processes (a terminal session, a service) before the kernel's killer ever runs. If something dies and `dmesg` is silent, check `journalctl -u systemd-oomd`. Whether DGX OS enables it, check yourself: `systemctl status systemd-oomd`.

### cgroups: a smaller box with its own killer

The global OOM killer protects the whole machine. A <Term w="cgroup">Control group. A Linux kernel feature that puts a set of processes in a group and limits or measures what they use together: memory, CPU, I/O. Docker and systemd are built on it.</Term> lets you draw a smaller box around a set of processes and give it its own memory limit. In cgroup v2 (what modern Ubuntu uses), the limit lives in a file called `memory.max`, current usage in `memory.current`, and a counter of kills in `memory.events`.

Over its limit, the group first reclaims its own pages, and if that fails, the OOM killer runs on *only that group*. The log line says `Memory cgroup out of memory`.

Docker's `--memory=512m` is exactly this: it puts the container in a cgroup with `memory.max` set to 512 MB. That's how you'll trigger the OOM killer below without risking the Spark: the explosion happens inside a 512 MB box. Two things that trip people up. Page cache from files read inside the container counts against its limit too (but it's reclaimable, so it usually just gets squeezed). And the kernel only charges what's *resident*: a container with a 512 MB limit can still `malloc` 100 GB. Lazy allocation works inside the box too.

### fork and copy-on-write

Now `fork`. In the threads lesson you saw that a forked worker is a new process with its own address space, a copy of the parent's. Copying 20 GB on every fork would make `fork` take seconds. So it doesn't copy. It copies the *page table*, and then marks every writable page as read-only in both parent and child.

Now both processes point at the same frames. Reads are free: no faults, no copies. The first time *either* process writes to one of those pages, the MMU sees a write to a read-only page and faults. The kernel notices this is a <Term w="copy-on-write">COW. Sharing a page between processes read-only, and copying it only when one of them writes to it. Makes fork nearly free, and means memory is only duplicated where the copies actually differ.</Term> page, copies that one page to a fresh frame, gives the writer the copy with write permission, and resumes. Only the pages that actually differ get duplicated.

For C programs this is beautiful. For Python it has a nasty edge.

This is the famous "DataLoader memory leak" that isn't a leak. You build a dataset as a Python list of a million dicts of strings, start 8 workers with `num_workers=8`, and over the first epoch memory climbs to roughly 9 times the dataset size. Each worker, just by indexing into the list, slowly copies the pages it touches. `top` shows every worker with a large RSS and you panic. Two things to keep straight:

- RSS counts shared pages in *every* process that maps them, so summing RSS across workers overcounts, especially right after fork. A fairer per-process number is <Term w="PSS">Proportional set size. Like RSS, but each shared page is divided by the number of processes sharing it. Summing PSS across processes gives the true total. Linux shows it in /proc/PID/smaps_rollup.</Term>, and the honest "how much did this process cost me" number is its private dirty memory.
- But the growth over the epoch is real: the copies really happen.

The fix is to keep your data out of millions of Python objects: store it in NumPy arrays, Arrow tables, or a memory-mapped file, and index into those. Raw buffers stay shared. One more twist: this only applies when workers are created with `fork`. With `spawn` or `forkserver`, the dataset is pickled and *fully* copied into each worker up front. Python 3.14 changed the default start method on Linux from `fork` to `forkserver`, so check what your DataLoader actually uses (`multiprocessing_context`, and `mp.get_start_method()`). Don't assume.

### mmap: borrowing a file as memory

The last tool. `mmap` with a file instead of anonymous memory creates a region whose pages *are* the file's pages in the page cache. Touch byte 4,000,000 of the region and you get byte 4,000,000 of the file: the first time via a major fault (read from disk) or a minor one (already cached), every time after just a normal load.

For model weights this changes everything about memory accounting. A safetensors file loaded with `mmap` costs no anonymous memory at all. Its pages are clean file pages: they count in RSS (as `file-rss`), they're shared with every other process that maps the same file, and under pressure the kernel can drop them instead of killing you, because it can always re-read them. Contrast `torch.load` without `mmap`, which reads the file into freshly allocated anonymous memory: now the same 70 GB exists twice, once in the page cache and once in your heap, and only the page cache copy is reclaimable.

### Unified memory: one pool for CPU and GPU

Back to the Spark. On a normal workstation, the GPU has its own memory (VRAM) on its own board, and `.to("cuda")` copies bytes across PCIe into that separate pool. Running out of VRAM gives you `CUDA out of memory`, a Python exception you can catch. System RAM is a different pool with a different killer.

The Spark's GB10 is built differently. Its CPU and GPU share one pool: 128 GB of LPDDR5x, at about 273 GB/s (spec-sheet numbers). There is no separate VRAM. A `cudaMalloc` for the GPU and a `malloc` for Python come out of the same physical frames. Linux sees all of it as system RAM, and the GPU driver allocates its memory from that RAM too. (Expect a bit under 128 GB to show up in `free`, since firmware and the kernel reserve some. Check yours.)

Now the opening scene makes sense. `torch.load` read the 70 GB file, which filled the page cache, and copied it into 70 GB of anonymous memory. Fine so far: "available" covered it, because the kernel quietly dropped page cache. Then `.to("cuda")` started allocating GPU memory, from the same pool, while the CPU copy still existed. Somewhere past 115 GB of anonymous plus GPU memory, reclaim had nothing left to drop, there was little or no swap, and the kernel's OOM killer picked the process with the biggest score. That was you. `cudaMalloc` didn't fail politely, because on unified memory the pressure lands on the whole system, not on a separate GPU pool. (Exactly when the CUDA driver gives a clean `out of memory` versus when the kernel kills the process depends on how the driver allocates and pins memory on GB10. Watch for both.)

The fixes follow from the model: never hold two full copies. Load with `mmap` (safetensors, or `torch.load(..., mmap=True)`) and move tensors to the GPU one at a time so file pages can be dropped as you go, or load straight onto the device (`device_map`, `safetensors` with `device="cuda"`). Or use 4-bit weights, which at about 35-40 GB give you room for a KV cache too, a story for [How much memory does a model need?](/lessons/memory-math/).

```python
# probe.py
import os, sys, resource, subprocess

PAGE = os.sysconf("SC_PAGE_SIZE")

def faults() -> tuple[int, int]:
    """(minor, major) page faults so far in this process."""
    r = resource.getrusage(resource.RUSAGE_SELF)
    return r.ru_minflt, r.ru_majflt

def mem() -> dict:
    """RSS and VSZ in MB. On Linux, also anonymous vs file-backed RSS."""
    if sys.platform == "linux":
        out = {}
        with open("/proc/self/status") as f:
            for line in f:
                k, _, v = line.partition(":")
                if k in ("VmRSS", "VmSize", "RssAnon", "RssFile", "RssShmem", "VmPTE"):
                    out[k] = int(v.split()[0]) / 1024  # kB -> MB
        return out
    rss, vsz = subprocess.run(["ps", "-o", "rss=,vsz=", "-p", str(os.getpid())],
                              capture_output=True, text=True).stdout.split()
    return {"VmRSS": int(rss) / 1024, "VmSize": int(vsz) / 1024}

def show(label: str) -> None:
    m = mem()
    mi, ma = faults()
    parts = " ".join(f"{k}={v:,.0f}MB" for k, v in m.items())
    print(f"{label:<18} {parts}  minflt={mi:,} majflt={ma:,}")
```

What the numbers should tell you:

**Reserving is free; touching costs.** The VSZ jump with no RSS change is lazy allocation, in one line of output. Faults ≈ bytes / page size is the proof that memory arrives one page at a time, on first touch.

**A minor fault costs around half a microsecond to a microsecond.** That's cheap per page and expensive in bulk. Touching 70 GB of fresh memory with 4 KB pages is about 18 million faults; at roughly 0.5 µs each, around 9 seconds of pure fault handling, before you've done anything useful. With 64 KB pages it's 1.1 million faults. Page size matters when the numbers get big, which is why your Spark measurement is the one to compare.

**COW is about writes, and Python reads are writes.** On Linux, `A.sum()` should copy essentially nothing; `for x in L` should copy roughly the full ~200 MB of objects; `A.copy()` allocates 40 MB of new memory (that's new anonymous memory, not a copy-on-write, so check which counter it shows up in).

**The hog dies near 512 MB, not at 512 MB exactly.** Python itself, the interpreter's own pages and any page cache charged to the container all count. The last printed `memory.current` should be within one chunk of `memory.max`.

## Break It

**1. Ask for zeros vs ones.** In the 512 MB container, run `np.zeros(10 * 2**30, dtype=np.uint8)` and then `np.ones(...)` with the same size. The first survives and holds almost nothing. The second dies. Same size, same allocation call underneath, but `ones` has to write every byte, and every written page is charged to the cgroup. Lesson: "how big is my array" is the wrong question; "how much of it have I touched" is the right one.

**2. Make yourself the preferred victim.** Run two hogs in one container (`-m 1g`), one of them after `echo 1000 > /proc/self/oom_score_adj` (raising your own score needs no privileges; lowering it does). Let them grow at the same rate. The adjusted one dies first, even when it's smaller. This is how systemd and Kubernetes steer the killer away from important processes and toward expendable ones.

**3. Thrash.** Run the hog in a container with `-m 512m --memory-swap 2g` (512 MB of RAM, 1.5 GB of swap), and change it to cycle through all its chunks, reading one byte per page, after each new allocation. It no longer dies quickly. It just gets slower and slower, and `vmstat 1` on the host shows swap traffic (`si`, `so`) pegged. This is <Term w="thrashing">When the pages a program needs keep being pushed to swap and pulled back, so the machine spends nearly all its time moving pages instead of computing. Usually worse than being killed outright.</Term>, and it's why many ML boxes run with little or no swap: a fast, clean OOM kill is better than a training job crawling at 1% speed for hours. (Needs swap on the host; if `swapon --show` is empty, read this one rather than run it.)

**4. The fake leak.** Fork 8 children that each iterate the list and then sleep. Sum their RSS, then sum their `Pss` from `smaps_rollup`, and compare both with `free`'s change. RSS overcounts the shared pages; PSS and `free` agree. Swap the list for the NumPy array and the per-child growth vanishes.

## Explain It Back

Answer out loud, in plain words, as if in an interview. Then check.

<details>
<summary>1. What is virtual memory, and why do we bother with it?</summary>

Every process uses fake addresses. The CPU's MMU translates each one into a real RAM location, page by page (4 KB or 16 KB or 64 KB chunks), using a per-process page table the kernel maintains, with a small cache (the TLB) so translation is nearly free. That buys three things: isolation (a process can only reach frames its table points to, so one can't scribble on another), the illusion of a huge contiguous memory regardless of where the frames really are, and laziness (memory can be promised now and backed later, shared between processes, or pushed to disk, all invisibly to the program).

</details>

<details>
<summary>2. My process has a VSZ of 300 GB and an RSS of 4 GB on a 128 GB machine. Is that a problem?</summary>

No. VSZ is address space reserved: thread stacks, a big `mmap`, an allocator's arenas, CUDA's reservations. None of it costs RAM until touched. RSS is what's actually in RAM, and 4 GB is fine. What I'd actually watch: RSS (better, PSS or private memory if many processes share pages), the anonymous part of it, since file-backed pages are reclaimable, and how it grows over time. VSZ matters only under strict overcommit (mode 2), where reservations themselves count against a limit.

</details>

<details>
<summary>3. Python got "Killed" with no traceback while loading a model. Walk me through what happened and how you'd fix it.</summary>

Allocations succeeded because Linux overcommits: `malloc` only reserves address space. Memory was actually consumed as pages were touched, one minor fault at a time. Once anonymous memory (plus, on the Spark, GPU allocations from the same unified pool) used up what reclaim could free, and there was no swap left, a fault had no frame to get, and the kernel's OOM killer picked the process with the highest oom_score (roughly, the biggest share of memory) and sent SIGKILL. That can't be caught, so: no traceback, exit code 137. I'd confirm with `dmesg` (the "Out of memory: Killed process" line with anon-rss). Fix: don't hold two copies: load with mmap (safetensors) so weights are reclaimable file pages, move them to the GPU tensor by tensor or load straight to the device, or use smaller weights. And test risky loads inside a cgroup limit so the failure is contained.

</details>

<details>
<summary>4. DataLoader workers' memory grows during the epoch even though they only read the dataset. Why, and what do you do?</summary>

Workers are forked, so they start out sharing the parent's pages copy-on-write. But reading a Python object changes its refcount, which is a write to the page that holds it, so each touched page gets copied into the worker. With a dataset stored as millions of Python objects, each worker slowly builds its own full copy. Also, RSS overcounts shared pages, so summed RSS looks worse than reality; PSS is the fair measure. Fix: store the data in a few big buffers (NumPy, Arrow, an mmap'd file) so reads don't write, or keep only file paths and offsets in Python. And check the start method: with spawn or forkserver (Python 3.14's Linux default), the dataset is pickled and copied into each worker up front.

</details>

<details>
<summary>5. How does memory use scale as you touch 1 GB, 10 GB, 100 GB with 4 KB vs 64 KB pages? What else scales?</summary>

RSS scales linearly with what's touched, whatever the page size. What changes is the bookkeeping. Faults: bytes / page size, so 100 GB is ~26 million faults at 4 KB, ~1.6 million at 64 KB; at around half a microsecond each that's about 13 seconds vs under one. Page tables: ~8 bytes per page, so ~200 MB at 4 KB vs ~13 MB at 64 KB. TLB reach: ~1,500 entries cover ~6 MB at 4 KB vs ~96 MB at 64 KB, so fewer misses when streaming big tensors. The costs of big pages: more waste for small allocations (a 1-byte touch costs a whole page) and more copying per copy-on-write fault. That trade is why big-memory systems lean toward huge pages.

</details>
