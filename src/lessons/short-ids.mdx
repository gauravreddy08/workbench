A short ID is a tiny name you hand out for something bigger: the `aB3x9Qz` at the end of a short link, an order number, an invite code. Every one must be different from every other one ever handed out, and it should be short enough to read aloud.

It sounds like the easiest part of any system, and it's the part people get wrong in interviews. Pick the codes at random and they start clashing far, far sooner than the size of the space suggests. Pick them in order and anyone can count your customers by making two links a week apart. Run the code on many servers at once and two of them will hand out the same name in the same millisecond. Each of those has a precise answer, and the answers are short once you've seen them.

You know from [Indexes](/lessons/indexes/) that a database can keep a column sorted and find any value in a few page reads; here that same structure becomes the referee that refuses duplicates. [Transactions](/lessons/transactions/) showed you the bug where two requests both check, both decide it's safe, and both write; here it comes back wearing a different hat. This lesson is the core of the [URL shortener](/lessons/url-shortener/) capstone, and the ID schemes at the end are the ones you'll meet in every big system's primary keys.

## The Problem

You watched a friend do an interview: "Build a URL shortener with Claude Code, then explain it and make it production-ready." The agent produced something that worked in ten minutes. The core of it looked like this:

```python
def make_code() -> str:
    return base64.b64encode(os.urandom(6)).decode()[:6]

def shorten(url: str) -> str:
    code = make_code()
    if db.execute("SELECT 1 FROM links WHERE code = ?", (code,)).fetchone():
        code = make_code()                       # try once more
    db.execute("INSERT INTO links (code, url) VALUES (?, ?)", (code, url))
    return code
```

Then the interviewer started asking questions, and each one landed on a different crack.

"Why 6 characters? How many links before two of them get the same code?" The tempting answer is "64⁶ is about 69 billion, so never." The real answer is that the first clash is expected after about **330,000** links, less than five millionths of the space. (6 base64 characters hold 36 bits; you'll derive the 330,000 yourself.)

"I see a `+` and a `/` in some codes. What happens when someone clicks `sho.rt/ab+c/d`?" About 17% of 6-character base64 codes contain one of those two characters, and both of them mean something in a URL.

"Two servers, same moment, same random code. What happens?" Both check, both see it's free, both insert. Either you now have two links with one code, or one user gets an error page, depending on whether the table has a uniqueness rule. The retry-once line doesn't help with either.

"Could I use a counter instead?" Sure, and then link 1,000,000 is followed by 1,000,001, and a competitor who makes a link on Monday and another on Friday knows exactly how many links your customers made that week.

None of these are exotic. They are the four questions of this lesson, and every system that hands out names faces them.

## The Idea

### What a short code has to be

Write down the requirements before choosing anything, because the three strategies later each give up a different one.

1. **Short.** People read it, type it, and fit it in a tweet. Every character costs.
2. **Unique.** Two links must never share a code, ever, across every server, for the life of the service. This one is not negotiable: a clash sends someone to the wrong page.
3. **Safe inside a URL.** No character that a browser, a proxy or a web framework will reinterpret.
4. **Ideally not guessable.** Nobody should be able to list other people's links by trying codes one after another.

The first three are about the alphabet and the length. The fourth is about how you pick codes.

### Counting in base 62

You already count in base 10: ten symbols, `0` to `9`, and when you run out you carry into the next column. `427` means 4 hundreds, 2 tens and 7 ones, and each column is worth 10 times the one to its right.

A short code is the same thing with more symbols. Take every character that is completely boring in a URL: the ten digits, the 26 lowercase letters and the 26 uppercase letters. That's 62. Give each a value: `0`-`9` are 0-9, `a`-`z` are 10-35, `A`-`Z` are 36-61. Now each column is worth 62 times the one to its right, and that's <Term w="base62">Writing numbers with 62 symbols (0-9, a-z, A-Z) instead of 10. Each extra character multiplies the number of possible codes by 62. The order of the alphabet is a convention; libraries differ, so pick one and never change it.</Term>.

To turn a number into base 62, do what you'd do by hand for any base: divide by 62, the remainder is the last character, repeat with what's left.

Decoding is the other direction: start at 0, and for each character, multiply what you have by 62 and add the character's value. `"4c92"`: 0·62 + 4 = 4; 4·62 + 12 = 260; 260·62 + 9 = 16,129; 16,129·62 + 2 = 1,000,000. That's the whole algorithm, both ways, and you'll write it in Build It.

Each character multiplies the count by 62. So N characters give 62ᴺ codes:

| 5 | 916,132,832 | 916 million | 29.8 |

| 8 | 218,340,105,584,896 | 218 trillion | 47.6 |

The last column says the same thing in bits. One base62 character carries log₂ 62 ≈ 5.95 <Term w="bits">The number of yes/no questions needed to pin down a value. A code with b bits of information has 2^b possible values. 7 base62 characters ≈ 41.7 bits, because 2^41.7 ≈ 62^7.</Term>, a hair under 6. You'll need bits in a minute, because the rule for when random codes clash is easiest to say in bits.

Two other numbers from the same arithmetic. A 64-bit integer, the biggest number most databases store natively, is at most 11 base62 characters. A full 128-bit UUID is 22.

### Why not base64?

<Term w="base64">A standard way (RFC 4648) to write arbitrary bytes as text using 64 symbols: A-Z, a-z, 0-9, plus + and /, with = added at the end as padding. Each character carries exactly 6 bits, which is why it's the default for encoding binary data.</Term> is the encoding everyone has in their fingers, and it's what the agent reached for. It has two more symbols than base62, so each character carries exactly 6 bits, which makes it neat for turning raw bytes into text. The trouble is which two symbols, and the padding.

| Character | What it means in a URL |
| --- | --- |
| `/` | Separates path segments. `sho.rt/ab/cd` asks for the path `ab`, then `cd`; your router never sees a code called `ab/cd`. |
| `+` | In query strings and form data, decoders turn it into a space. `?c=ab+cd` arrives as `ab cd`. |
| `=` | Padding on the end, and also the separator between a query-string key and its value. |

You can escape all of these as `%2F`, `%2B`, `%3D`, but then your 6-character code is 8 characters, and every layer between the user and your server (browsers, proxies, chat apps that turn text into links, analytics scripts) has to get the escaping right. About 17% of random 6-character base64 codes contain a `+` or a `/`, so this isn't a rare edge.

The standard has an answer: <Term w="base64url">The URL-safe variant of base64 from RFC 4648, section 5: + becomes - and / becomes _. Padding is usually dropped. Used in JWTs and many tokens.</Term> swaps `+` for `-` and `/` for `_`, and you usually drop the padding. Those two are genuinely safe in URLs, and base64url is a perfectly good choice for long tokens (JSON Web Tokens use it). For short codes that humans see, most people still pick base62, for small human reasons: a hyphen splits a word when you double-click it, `a-_b` reads like punctuation, and codes ending in `-` or `_` look like typos. Base62 costs you 0.05 bits per character, which is nothing.

Some services go further and drop characters people confuse, like `0`/`O` and `1`/`l`/`I`. Bitcoin addresses use <Term w="base58">Base62 minus 0, O, I and l, so a code read aloud or copied by hand can't be misread. Each character carries about 5.86 bits.</Term> for exactly that reason. Same idea, smaller alphabet.

### Three ways to pick the code

Now the real decision. The alphabet and the length tell you how many codes exist. They don't tell you which one to hand out next.

**1. Count, then encode.** Keep a counter. Link 1 gets `1`, link 62 gets `10`, link 1,000,000 gets `4c92`. In a database this is the auto-incrementing primary key you get for free. There are no clashes, ever, because no number is handed out twice. Codes are as short as possible: you don't need 7 characters until link 56.8 billion. And in [Indexes](/lessons/indexes/) you saw that ever-increasing keys always land in the rightmost leaf of the B-tree, which is the cheapest possible insert.

The cost is that the codes are a story anyone can read. They are <Term w="enumerable">Possible to list completely by counting through them. If codes are sequential, an outsider can visit 1, 2, 3, ... and see every link, including ones meant to be shared with only one person.</Term>: anyone can walk `4c92`, `4c93`, `4c94` and see every link people made, including ones meant for one recipient. And they leak volume. Make a link on Monday, another on Friday, subtract, and you know how many links all your competitor's users made that week. In World War II, Allied statisticians did exactly this with the serial numbers on captured German tanks and estimated production more accurately than the spies did. It's still called the German tank problem.

**2. Pick at random, let the database refuse duplicates.** Draw 7 characters from a cryptographically secure random source, and try to insert. If that code is already taken, the database says so, and you draw again. Nothing about one code tells you anything about any other, so there's no volume to read and no order to walk. The cost: clashes can happen, so you need a uniqueness rule in the database and a retry loop, and you need to know how often retries happen. That's the next section, and it's the surprise.

**3. Hash the URL, keep the first few characters.** Run the long URL through SHA-256, write the result in base62, keep 7 characters. The same URL always gives the same code, so if a million people shorten the same news article you store it once, and you can check "have I seen this URL?" without storing anything new.

Two catches. First, a <Term w="hash function">A function that turns any input into a fixed-size, scrambled-looking output. The same input always gives the same output, and any change to the input changes the output completely. SHA-256 outputs 256 bits.</Term> truncated to 7 characters is just 41.7 bits of scrambled output, and different URLs collide exactly as often as random codes do. You still need the uniqueness rule, and a way to resolve a clash (hash `url + "#1"`, then `url + "#2"`, ...), and now the code for a URL depends on what was inserted before it. Second, the "free" deduplication isn't free: to find an existing link for a URL you have to look it up by URL, which means a unique index on the URL column, and with that index you could deduplicate random codes just as well. And often you don't want deduplication at all: two customers shortening the same URL usually want separate click counts and the right to delete their own link.

| | Count + base62 | Random + unique rule + retry | Hash of URL, truncated |
| --- | --- | --- | --- |
| Clashes | Never | Rare; retry | Rare; rehash with a suffix |
| Guessable / enumerable | Yes: next code is +1 | No (with a secure random source) | No, but anyone with the URL can compute its code |
| Leaks how many links you have | Yes | No | No |
| Same URL twice | Two codes | Two codes | One code |
| Code length | Grows from 1 char | Fixed | Fixed |
| Many servers | Needs a shared counter (see later) | Only the database's uniqueness check | Same as random |
| B-tree inserts | Always at the right edge: cheap | Random spots: costlier | Random spots: costlier |

Most real shorteners use the database's own counter internally (it's the primary key) and either show it directly, show it scrambled (later), or show a separate random code. The rest of this section is about making option 2 safe, because it's the one with a trap.

### The birthday paradox

Now swap birthdays for codes. You have N possible codes and you've handed out n at random.

1. There are n(n−1)/2, roughly n²/2, pairs of codes.
2. Each pair clashes with probability 1/N.
3. So you expect about **n² / 2N** clashing pairs.
4. Turned into a probability, the chance that *no* pair clashes is about e^(−n²/2N). Set that to one half and solve: **n ≈ √(2 ln 2 · N) ≈ 1.18 √N**.

That's the <Term w="birthday bound">The rule that random picks from N possibilities start colliding after about √N picks, not N/2. With b-bit random values, expect collisions around 2^(b/2). Named after the birthday paradox.</Term>. You'll also see a slightly different constant, √(πN/2) ≈ 1.25 √N. That's the *average* number of draws until the first clash, rather than the point of a 50% chance. They're the same idea, about 6% apart, and you'll measure both.

In bits, it's even simpler: **b random bits start clashing at about 2^(b/2)**. Half the bits. Your 41.7-bit, 7-character codes behave like 21 bits, about two million, as far as "first clash" goes.

### "Some clash somewhere" vs "my insert clashes"

Here's the part that makes random codes usable anyway. The birthday bound answers "has *any* pair ever clashed?" That's the right question if you never check. But you do check: the database refuses a duplicate, and you draw again. The question that matters for a retry loop is different: **when I draw one new code, what's the chance it's already taken?**

That's just the fraction of the space already used: **n / N**. With 100 million links in a 7-character space, it's 100,000,000 / 3,521,614,606,208, about **1 in 35,000**. A retry is a rounding error. You'd expect around 1,400 retries over all 100 million inserts, each one costing a single extra database round trip.

And the average number of tries per insert, when a fraction f of the space is full, is 1 / (1 − f). At 10% full, 1.1 tries. At 50% full, 2. At 90% full, 10. At 99%, 100. I measured that by filling a 3-character space (238,328 codes) to 99%: 1.10, 2.00, 4.01, 9.76 and 68.7 tries per insert around 10%, 50%, 75%, 90% and 99% full, against 1.10, 1.98, 3.92, 9.52 and 66.7 from the formula at the middle of each window. The formula is exact; random codes are fine until the space is a meaningful fraction full, and then they fall off a cliff.

So both statements are true at once, and you need both in an interview: **with 7-character random codes, a clash somewhere is certain after a few million links, and still almost no single insert ever has to retry.** The first is why you need the uniqueness rule. The second is why the retry loop is cheap.

Move the sliders. The blue curve is "some two links share a code, if nobody checked". The dashed one is "the next new code is taken", which is what a retry costs you.

The last readout is the one to stare at: **random guesses per real link found**. That's N / n, and it's the same number as the retry rate, upside down. With 100 million links in a 7-character space, someone guessing codes at random finds a real link once every 35,000 tries. At 100 requests a second, that's one stranger's link every six minutes. "Not guessable" is about how *sparse* the space is, not just how random the codes are. If the links point at private documents, you need longer codes, or rate limits on lookups, or both. Researchers have done exactly this scan against real short-link services and found shared cloud documents and map directions people assumed were private (see Go Deeper).

### Where uniqueness actually comes from

So the plan for random codes is: draw, insert, and if the code is taken, draw again. The only question left is who decides "taken". The tempting answer is your code:

```python
if not db.execute("SELECT 1 FROM links WHERE code = ?", (c,)).fetchone():
```

The fix is to stop asking and let the database be the referee. Declare the column unique:

```sql
CREATE TABLE links (
  id   INTEGER PRIMARY KEY,
  code TEXT NOT NULL UNIQUE,
  url  TEXT NOT NULL
);
```

A <Term w="unique constraint">A rule in the schema that no two rows may have the same value in a column. The database enforces it with a unique index and rejects any insert or update that would break it, no matter how many clients are writing at once.</Term> is enforced with a <Term w="unique index">A B-tree index (from the indexes lesson) that refuses to hold two equal keys. Inserting into it finds the leaf where the key belongs; if the key is already there, the insert fails.</Term>. That's the same B-tree from [Indexes](/lessons/indexes/), with one extra rule: when an insert walks down to the leaf where the key belongs and finds it already there, it fails instead of adding a second copy. The database makes that find-and-insert one step that nothing else can interleave with (for the B-tree, it holds a lock on the leaf page while it checks and writes; Postgres additionally waits for any other in-progress transaction that inserted the same key, to see whether it commits). So when two inserts of `aB3x` race, exactly one wins. The other gets a uniqueness error, which you catch and treat as "draw again".

The pattern is called **insert and catch the conflict**, and it beats check-then-insert three ways:

- **It's correct.** Your check was a guess about the future; the index is the truth at the moment of writing.
- **It's faster.** One round trip instead of two in the common case.
- **The index you need for it is the index you needed anyway**, because every redirect looks links up by code. Without it, the "check" in check-then-insert is a scan of the whole table. In my runs, 40,000 check-then-inserts without a unique index took 11.9 s; with the unique index, 2.4 s.

Two details that differ by database. In SQLite (and in Python's `sqlite3`), a failed insert raises `sqlite3.IntegrityError` and you can just loop. In Postgres, an error inside a transaction aborts the whole transaction, so the clean way is `INSERT ... ON CONFLICT (code) DO NOTHING RETURNING id`: if nothing comes back, the code was taken, and the transaction is still usable. Both databases support that `ON CONFLICT` form, which is often called an <Term w="upsert">Insert, or if the row would break a unique rule, do something else instead (nothing, or update the existing row). Written INSERT ... ON CONFLICT in Postgres and SQLite.</Term>.

And the primary key itself is a unique constraint. The auto-increment counter from strategy 1 is unique for the same reason: the database owns it.

### Many servers: where does the next number come from?

Random codes need no coordination beyond the unique index. Counters do. With one database, the counter is easy: the database hands out the next number, atomically. Postgres calls it a <Term w="sequence">A database object that hands out increasing numbers. Each call to nextval() returns a new value, even across concurrent transactions, and is never rolled back, so failed inserts leave gaps.</Term>, SQLite and MySQL an auto-increment key.

The trouble starts when you grow. Split the links table across 16 database servers, or run in three regions, and there is no single place that knows "the next number". Make one, and every insert anywhere in the world waits on a round trip to it (tens of milliseconds across an ocean, from [How slow is slow?](/lessons/latency-numbers/)), and when it's down, nobody can create anything. One counter is a <Term w="single point of failure">One component whose failure stops the whole system, no matter how many copies of everything else you run.</Term> and a bottleneck. Three standard ways out.

**Hand out blocks.** The counter doesn't hand out one number; it hands out a thousand. Each server, on start-up and whenever it runs out, does one atomic update:

```sql
UPDATE counters SET next = next + 1000 WHERE name = 'links' RETURNING next;
```

If that returns 3,001, the server owns 2,001 through 3,000 and hands them out from memory with no further coordination. The counter now sees one request per thousand IDs instead of one per ID. If a server crashes, the rest of its block is never used, which is fine: IDs need to be unique, not consecutive. IDs are no longer in exact creation order across servers, only roughly. This idea is old and has many names (hi/lo in the Hibernate library, "segments" elsewhere).

- **41 bits of time**: milliseconds since a custom starting point (Twitter's is in November 2010). 2⁴¹ milliseconds is about 69.7 years, so Twitter's IDs run out in 2080.
- **10 bits of machine number**: up to 1,024 machines. (Twitter's code split this into 5 bits of datacenter and 5 of worker.)
- **12 bits of sequence**: a counter for IDs made in the same millisecond on the same machine, up to 4,096. If a machine somehow needs a 4,097th in one millisecond, it waits for the next millisecond.

That's 4,096,000 IDs per second per machine, about 4 billion per second across 1,024 machines, with no network traffic at all. Two machines can't clash because their machine bits differ. One machine can't clash with itself because time or the sequence always moves forward. And because time is in the high bits, sorting by ID sorts by creation time, which is why tweet IDs also tell you, roughly, when a tweet was posted.

The two things that break it are both about its assumptions. If two machines are given the same machine number (a config mistake, a recycled container), they can mint identical IDs. And if a machine's clock jumps *backwards* (a time-sync correction), it could re-issue IDs it already issued; Twitter's implementation refuses to make IDs until the clock catches up again. Instagram's variant, built inside Postgres, used 41 bits of time, 13 bits of shard number and 10 bits of sequence: same idea, different split.

A Snowflake ID written in base62 is 11 characters. Good for internal keys, a bit long for a short link.

**Use a big random number: UUIDs.** A <Term w="UUID">Universally unique identifier: a 128-bit value, usually written as 36 characters like 3f2a6c1e-8b4d-4f0a-9c77-2e1d5b8a9f03. Several versions exist; v4 is random, v7 starts with a timestamp.</Term> is the "pick at random" strategy taken to its limit. Version 4 has 122 random bits. By the birthday bound, the first clash is expected after about 2.9 × 10¹⁸ of them: make a billion a second and you'd expect your first clash after about 92 years. So nobody checks. Every machine generates them independently and the database's primary key is the backstop that will, in practice, never fire.

The catch is the one you measured in [Indexes](/lessons/indexes/): random keys land at random spots in the B-tree, so every insert touches a different leaf, the working set no longer fits in cache, and pages split all over the tree. **UUIDv7** (standardized in RFC 9562, 2024) fixes that by putting a 48-bit millisecond timestamp first and filling the rest with 74 bits of randomness. New keys land at the right edge of the tree, like a counter, but machines still need no coordination. On my Mac, inserting 2 million UUIDv4 primary keys into a SQLite table with an 8 MB cache took about **21 seconds**; the same with UUIDv7 took **1.6 seconds**. Python 3.14 added `uuid.uuid7()` to the standard library, and Postgres 18 added a built-in `uuidv7()` function.

At 22 base62 characters, UUIDs are wrong for a short link but often right for the internal primary key. Many systems use both: a UUIDv7 or Snowflake as the row's real key, and a separate short code for humans.

### Hiding a counter

Last trick. Suppose you want the counter's best property (never a clash, no retries) without its worst one (anyone can read and walk the sequence). Scramble it: show the user not `encode(id)` but `encode(scramble(id))`, where `scramble` is a <Term w="permutation">A reshuffling of a set: every input maps to exactly one output in the same set, and no two inputs share an output. So scrambling distinct IDs always gives distinct codes, and you can always undo it.</Term> of the number range. Because every input has its own output, distinct IDs still give distinct codes, so there's still nothing to retry.

The neat way to build a reversible scramble is a <Term w="Feistel network">A way to build a reversible scramble from any one-way mixing function: split the bits into halves L and R, replace them with R and L xor F(R), and repeat a few rounds. It can always be undone by running the rounds backward, whatever F is.</Term>. Split the 40-bit ID into two 20-bit halves, L and R. One round replaces (L, R) with (R, L xor F(R)), where F is any mixing function at all, for example a keyed hash of R cut to 20 bits. Four rounds scramble thoroughly. And it can always be undone: knowing the new pair, you can recompute F(R) and xor it back out, whatever F was. That's the trick DES used, and it's why it works with a hash that can't itself be reversed. 2⁴⁰ is about 1.1 trillion, which fits in 7 base62 characters. Run it on IDs 1, 2, 3 with a key and you get codes like `iMLvQ4k`, `drYt842`, `8VPuRdB`, with no visible order.

Be honest about what this buys. It hides the order and the volume from a casual observer. It's obfuscation, not proven security: a home-made 4-round cipher with a secret key is not something to bet private documents on, and it doesn't change the density argument at all. With 100 million links in a 7-character space, a random guess still finds a real link 1 in 35,000 times, scrambled or not. Libraries like Sqids (formerly Hashids) do a lighter version of this with a shuffled alphabet, and say plainly in their docs that it isn't encryption. If guessing a code must be infeasible, use random codes from a secure source, make them long enough that the space stays sparse, and rate-limit lookups.

## Break It

**1. Seed every worker the same.** Give each process `random.Random(int(time.time()))` "for reproducibility" and use it to draw 7-character codes. All eight processes start within the same second, so they get the same seed and draw the same sequence of codes, in lockstep. On my Mac, 8 × 5,000 inserts with 7-character codes, where you'd expect zero retries, took **140,628**. Every worker after the first to reach each code loses and retries, again and again. This is the real-world version: containers started together, each seeding from the clock. Use `secrets`, which reads from the operating system's secure random source and has no seed to get wrong. (Python's `random` module is also predictable: its docs say plainly not to use it for anything security-related.)

**2. Lose the leading zeros.** Generate random codes with `encode(secrets.randbelow(62**7))` instead of `encode_fixed(..., 7)`. About 1 in 62 codes comes out shorter than 7 characters. Now store them, and have some other part of the system pad codes to 7 characters "to normalize" them: `"abc"` and `"0000abc"` are the same number but different strings, and you've built two names for one link, or worse, one name that resolves differently depending on which code path reads it. Decide once whether a code is a string or a number, and make every layer agree.

**3. Cross the 2⁵³ line.** Generate a Snowflake ID and send it to a browser as a JSON number. JavaScript stores all numbers as 64-bit floats, which hold integers exactly only up to 2⁵³ (about 9 × 10¹⁵). A current Snowflake is about 2 × 10¹⁸. In Python, `int(float(x))` shows the damage: `2117490424925942011` comes back as `2117490424925942016`. The last digits are silently wrong, and now the client asks for a tweet that doesn't exist. Twitter's API added an `id_str` field for exactly this. Send big IDs as strings.

**4. Fill a small space.** Use 3-character random codes in your hammer and insert 230,000 links (97% of the space) with `max_tries = 10`. Watch retries per insert climb, and then watch `insert_with_retry` start raising: at 97% full, the chance that 10 draws in a row are all taken is 0.97¹⁰ ≈ 74%. Your retry limit is now a feature switch that turns the service off. Real services watch the fill fraction and add a character long before this.

## Explain It Back

Answer out loud, in plain words, as if in an interview. Then check.

<details>
<summary>1. Why base62 and not base64 for short links? How many 7-character codes are there?</summary>

Base64 uses `+`, `/` and `=` padding. In a URL, `/` splits the path, `+` turns into a space in query strings and forms, and `=` is the key-value separator; you'd have to percent-escape them, which makes codes longer and depends on every layer escaping correctly. Base64url swaps in `-` and `_`, which are safe, and it's fine for long tokens, but for short human-facing codes people prefer just letters and digits: they double-click cleanly, read aloud, and don't look like punctuation. Base62 is 0-9, a-z, A-Z. 7 characters give 62⁷ = 3,521,614,606,208, about 3.5 trillion codes, or about 41.7 bits.

</details>

<details>
<summary>2. You pick 7-character codes at random. When does the first clash happen, and why is that not a problem?</summary>

By the birthday paradox, the number of pairs grows as the square of the number of codes, so clashes start around the square root of the space: a 50% chance after about 1.18 × √(3.5 trillion) ≈ 2.2 million links. With 100 million links, many clashes would have happened if nobody checked. But we do check: the code column has a unique index, so a clash just makes the insert fail and we draw again. The chance a single new code is taken is the fraction used, 100 million / 3.5 trillion ≈ 1 in 35,000, so retries are negligible until the space is a sizable fraction full; tries per insert are 1 / (1 − fill). The thing to watch is the fill fraction, and the same number, upside down, is how many random guesses an attacker needs per real link.

</details>

<details>
<summary>3. Why is "check if the code exists, then insert" wrong, and what do you do instead?</summary>

Because there's a gap between the check and the insert. Two servers can draw the same code, both check, both see nothing, and both insert: either a duplicate (no unique rule) or a crash on the second (with one). It's the same check-then-act race as write skew in transactions; the check can't lock a row that doesn't exist yet. Instead, put a unique constraint on the column and just insert. The database's unique index makes the check and the write one step, so exactly one insert wins and the other gets a conflict, which you catch and retry with a new code. In Postgres, use `INSERT ... ON CONFLICT (code) DO NOTHING RETURNING id` so the conflict doesn't abort the transaction. It's also one round trip instead of two.

</details>

<details>
<summary>4. Counter, random, or hash of the URL? What does each cost?</summary>

A counter encoded in base62 never clashes, gives the shortest codes, and inserts cheaply at the right edge of the B-tree, but it's enumerable (anyone can walk the codes) and leaks your volume (two links a week apart tell a competitor how many you made). Random codes leak nothing and need no coordination beyond the unique index, at the cost of rare retries and random inserts into the index. Hashing the URL gives the same code for the same URL, so you can deduplicate, but truncated hashes clash like random codes, so you still need the unique rule and a rehash-on-clash scheme, dedup needs an index on the URL anyway, and most products want separate links per user. A common answer: database counter as the internal key, random 7-8-character code for the public link.

</details>

<details>
<summary>5. How does this scale to 10,000 new links a second, from 50 servers, for 10 years?</summary>

First the total: 10,000 × 86,400 × 365 × 10 ≈ 3.2 trillion links. That's 90% of the 7-character space, which for random codes means 10 tries per insert by the end, and nearly every random guess by an attacker hits a real link. So go to 8 characters (218 trillion): 1.4% full at the end, about 1.015 tries per insert. For the IDs themselves, one central counter is a bottleneck and a single point of failure for 50 servers, especially across regions. Options: each server leases blocks of, say, 10,000 IDs from a counter row, so the counter sees one request a second instead of 10,000; or Snowflake-style IDs (41 bits of time, 10 of machine, 12 of sequence: 4 million per second per machine with no coordination, as long as machine numbers are unique and clocks don't jump back); or UUIDv7 for internal keys, which also sort by time so B-tree inserts stay at the right edge. The unique index on the public code is the one thing that stays, and it's sharded with the table: if links are split across databases by code, each code's uniqueness is checked by exactly one shard.

</details>

## Go Deeper

- **Twitter Engineering, "Announcing Snowflake" (2010)**, and the original code at **[github.com/twitter-archive/snowflake](https://github.com/twitter-archive/snowflake)**. The requirements (tens of thousands of IDs per second, highly available, roughly time-sorted, 64 bits) and the 41/10/12 layout, in the authors' words. The README is short; read it.
- **Instagram Engineering, "Sharding & IDs at Instagram" (2012).** A Snowflake variant generated inside Postgres with a few lines of PL/pgSQL, and a clear comparison of the options they rejected (UUIDs, a central ticket server).
- **Flickr, "Ticket Servers: Distributed Unique Primary Keys on the Cheap" (code.flickr.net, 2010).** The odd/even pair of MySQL counters. Short, practical, and the clearest case for "a counter is fine if you're careful about what happens when it dies".
- **[RFC 9562: Universally Unique IDentifiers (UUIDs)](https://www.rfc-editor.org/rfc/rfc9562)** (2024). Defines UUIDv7 and explains, in its motivation (section 2), why time-ordered keys are better for database indexes. Read sections 5.4 and 5.7 and section 6 on generation.
- **[RFC 4648: The Base16, Base32, and Base64 Data Encodings](https://www.rfc-editor.org/rfc/rfc4648)**. Section 4 is base64 with `+`, `/` and `=`; section 5 is the URL-safe alphabet. Ten minutes, and you'll never be vague about it again.
- **Martin Georgiev and Vitaly Shmatikov, "Gone in Six Characters: Short URLs Considered Harmful for Cloud Services" (2016).** They scanned the code space of real URL shorteners and found private cloud documents and map directions. The density argument from this lesson, done for real.
- **Michael Luby and Charles Rackoff, "How to Construct Pseudorandom Permutations from Pseudorandom Functions" (SIAM Journal on Computing, 1988).** Why a few Feistel rounds over a good keyed function give a permutation that looks random. The theory under the counter-scrambling trick.
- **Alex Xu, _System Design Interview, Volume 1_, chapters 7 ("Design a unique ID generator in distributed systems") and 8 ("Design a URL shortener").** The interview framing of exactly this material. Useful to check your answers against the format interviewers expect.
