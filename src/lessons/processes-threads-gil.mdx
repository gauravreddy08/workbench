## The Problem

You have a preprocessing script. It reads 2 million query-document pairs, cleans the text, and hashes each one so you can dedupe before training the cross-encoder. It takes 40 minutes. The Spark has 20 CPU cores. You open Activity Monitor (or `htop`) and see one core at 100% and nineteen doing nothing.

So you do the obvious thing. You wrap the loop in a `ThreadPoolExecutor(max_workers=20)`. It takes 41 minutes.

Then you try a `ProcessPoolExecutor(max_workers=20)` instead. It takes 3 minutes. Same function, same data, one word changed.

Then, emboldened, you use the same thread pool to fetch 5,000 web pages for a scraping job, and that one goes from 40 minutes to 2. Threads are useless for one job and magic for the other. If you can't explain why, you will keep guessing, and the guesses will be wrong in expensive ways: a `DataLoader` that starves the GPU, a server that falls over at 50 users, a script that deadlocks once a week.

The explanation has three layers. What the operating system gives you (processes and threads). How it shares a few cores among many of them (the scheduler). And one specific decision CPython made in the early 1990s (the GIL).

<Origin year="1960s" title="Many programs, one very expensive computer">

Early computers ran one job at a time. While a job waited for a tape drive, the CPU, the most expensive thing in the building, sat idle. Time-sharing systems like CTSS at MIT (1961) and later Multics and Unix fixed this by keeping several programs loaded at once and switching between them many times a second, each fenced off in its own memory. That fenced-off running program got a name: a process.

Threads came later, in the 1980s and 90s (Mach, then POSIX threads standardised in 1995), when people wanted several flows of control *inside* one program that could share its memory cheaply, for example a server handling many clients, or a GUI that stays responsive while it computes. Python added threads in the early 90s, and to keep its interpreter simple and safe, it put one big lock around the whole thing. That lock is the GIL, and we are still talking about it thirty years later.

</Origin>

## The Idea

### A program is a recipe, a process is someone cooking it

A <Term w="program">A file on disk containing machine code (or, for Python, the interpreter binary plus your .py files). Inert. It does nothing until the OS loads it.</Term> is a file. `python3` is a program. `train.py` is a file the program reads. Neither one does anything while it sits on disk.

When you type `python3 train.py`, the <Term w="kernel">The core of the operating system. The one program that talks to hardware directly and decides who gets the CPU and memory.</Term> creates a <Term w="process">A running instance of a program, plus everything the OS tracks for it: its own memory, its open files, an ID, and at least one thread.</Term>. Run the same command in two terminals and you get two processes from one program, the way two cooks can follow the same recipe in two separate kitchens.

That is the analogy for this lesson, so let's set it up properly. A **process is a kitchen**: it has walls, its own pantry, its own equipment. A **thread is a cook** working in that kitchen. A kitchen needs at least one cook to get anything done. Several cooks in one kitchen share the pantry and the counters, which is fast (no walking to another building) and dangerous (two cooks grab the same bowl).

Here is what the kernel actually keeps for each kitchen.

Four things to notice.

1. **A PID.** The <Term w="PID">Process ID. A number the kernel hands out so you (and `kill`, `ps`, `top`) can name a process.</Term> is just a number, but it is how every tool refers to the process.
2. **Its own address space.** In [Where do my variables live?](/lessons/stack-and-heap/) you saw the layout: code at the bottom, globals, the heap growing up, the stack growing down. Each process gets a whole private copy of that picture. Address `0x10a3f2c0` in process 4121 and the same address in 4188 point to different physical RAM, because the kernel and the CPU's <Term w="MMU">Memory management unit. Hardware in the CPU that translates the addresses a program uses (virtual addresses) into real RAM locations, using a per-process table the kernel sets up.</Term> translate addresses through a different table for each process. That is the wall. One process cannot scribble on another's memory, which is why a crash in one Python script doesn't take down your browser.
3. **Open files.** Every file, socket, or pipe a process has open gets a small integer, a <Term w="file descriptor">A small number (0, 1, 2, 3...) that a process uses to refer to an open file, socket, or pipe. 0, 1 and 2 are stdin, stdout and stderr.</Term>. The table of them belongs to the process.
4. **At least one thread.** The kernel doesn't run processes. It runs threads. A process with zero threads is just a reserved room nobody is cooking in.

### What a thread owns, and what it shares

A <Term w="thread">One sequence of instructions being executed, with its own position in the code and its own stack. Threads live inside a process and share its memory.</Term> is the part that actually executes. To execute code you need exactly three private things:

- An <Term w="instruction pointer">A CPU register holding the address of the next machine instruction to run. Also called the program counter. It is the "you are here" marker in the code.</Term>: where you are in the code.
- The CPU <Term w="registers">A handful of tiny, ultra-fast storage slots inside the CPU core (a few dozen on ARM64) where the values being worked on right now live.</Term>: the values you are in the middle of computing.
- A **stack**: your chain of function calls and their local variables, exactly the stack from the last lesson. The <Term w="stack pointer">A register holding the address of the top of this thread's stack.</Term> says where its top is.

Everything else is shared with every other thread in the same process: the code, the globals, the heap, the open files. Here is the address space from last lesson, now with three cooks in the kitchen.

Two consequences fall straight out of this picture.

**Threads are cheap to create and cheap to talk between.** Making a thread means allocating a stack and a small kernel record, not a whole new address space. On an M-series Mac, starting a Python thread takes around 40 microseconds (measure it yourself in the Build). And two threads can share data with zero copying: a list built by one thread is the very same object on the very same heap for the other.

**Threads can trample each other.** That same sharing means two threads can read and write the same object at the same moment with nothing to stop them. We'll make that happen shortly.

Processes are the mirror image: expensive to create, expensive to talk between (you have to copy data across the wall), and safe by default.

### One core, many threads: the scheduler

Your Mac has somewhere around 8 to 16 cores. `ps` on a quiet laptop shows hundreds of processes and thousands of threads. How do thousands of cooks share a dozen stoves?

By taking turns, very fast. The part of the kernel that decides who goes next is the <Term w="scheduler">The part of the kernel that decides, many times a second, which ready thread runs on which core next, and for how long.</Term>. At any moment every thread is in one of three states:

- **Running**: on a core right now.
- **Ready**: could run, waiting for a free core.
- **Blocked** (or waiting): can't run until something happens, like bytes arriving on a socket, a disk read finishing, or a timer going off. A blocked thread uses *no* CPU.

A running thread gets a <Term w="time slice">How long the scheduler lets a thread run before it may swap in another ready thread. Roughly a few milliseconds on Linux and macOS; it varies with OS, version and load.</Term> of a few milliseconds. When the slice runs out, or when the thread blocks on its own (it asked to read a socket and the data isn't there yet), the kernel performs a <Term w="context switch">Saving one thread's registers, instruction pointer and stack pointer into memory, and loading another's, so a core can switch from running one thread to another.</Term>: it saves the outgoing thread's registers to memory, loads the incoming thread's registers, and jumps to its instruction pointer. The cook steps away from the stove, leaves a note saying exactly where they were, and the next cook picks up their own note.

How expensive is that? Approximate numbers, and they vary a lot by hardware and OS:

| Switch | Direct cost (rough) | Why |
| --- | --- | --- |
| Thread to thread, same process | ~1-5 µs | Save and load registers, run the scheduler. Memory map stays the same. |
| Process to process | a few µs direct, more in effect | Also switch the address-translation tables. Cached translations in the <Term w="TLB">Translation lookaside buffer. A small cache in the CPU of recent virtual-to-physical address translations. Switching processes can invalidate it.</Term> may be thrown out, and the new process finds the CPU caches full of someone else's data. |

From [How slow is slow?](/lessons/latency-numbers/): a few microseconds is thousands of RAM reads, but tiny next to a 5 ms slice or a 50 ms network round trip. Context switching is cheap enough that thousands per second is fine, and expensive enough that hundreds of thousands per second will eat a core.

### Concurrency vs parallelism

Now two words that get used interchangeably and shouldn't be.

- <Term w="Concurrency">Having several tasks in progress over the same period, so their lifetimes overlap. They might take turns on one core.</Term> is about **structure**: several tasks are *in progress* at once. One cook juggling three dishes, stirring one while another simmers, is concurrent.
- <Term w="Parallelism">Several tasks literally executing at the same instant, on different cores.</Term> is about **execution**: several tasks are *running at the same instant*. Three cooks at three stoves is parallel.

Concurrency is possible on one core. Parallelism needs more than one. And the key insight for everything that follows: **concurrency alone is enough to speed up waiting**, because while one task waits, another can use the core. **Only parallelism speeds up working**, because the total amount of computing has to be split across more cores.

That split, waiting vs working, has names. A job is <Term w="CPU-bound">Its speed is limited by how fast the CPU computes. Give it a faster or extra core and it finishes sooner.</Term> if it spends its time computing (counting primes, tokenizing text, parsing JSON in pure Python). A job is <Term w="I/O-bound">Its speed is limited by waiting for input/output: network, disk, another service. The CPU is mostly idle.</Term> if it spends its time waiting (HTTP calls, database queries, reading files from a network drive).

### The GIL

Here is the twist. In standard CPython there is one lock, the <Term w="GIL">Global Interpreter Lock. A single lock inside CPython that a thread must hold to run Python bytecode. Only one thread per process holds it at a time.</Term>, and a thread must hold it to execute Python <Term w="bytecode">The simple instructions CPython compiles your .py code into (LOAD_FAST, BINARY_OP, ...) and then runs one by one in a loop.</Term>. One kitchen, one recipe book, and only the cook holding the book may cook. Other cooks can still *wait* for the oven without the book. But to chop, stir, or do anything else that is Python code, you need the book.

So in a single Python process, no matter how many threads you start and how many cores you have, **at most one thread is running Python code at any instant**. Threads still give you concurrency. They do not give you parallelism for Python code.

Play with it. Start with CPU-bound work, 4 threads, 4 cores, GIL on. Then flip the GIL off. Then switch to I/O-bound work and flip it back on.

Three things to take away from the timeline:

1. **CPU work, GIL on:** wall time equals serial time. Four threads on four cores take as long as one thread doing it all, because they take turns holding the lock. (Real CPython is often a little *worse* than serial here, because handing the lock back and forth has a cost.)
2. **CPU work, GIL off:** with enough cores, wall time divides by the number of threads. This is what processes give you today, and what free-threaded Python promises.
3. **I/O work, either way:** each thread computes for a moment, then waits. The waits overlap. A dozen threads waiting on a dozen sockets is concurrency, and the GIL barely matters because waiting doesn't need it.

### When the GIL lets go

The GIL is not held forever by whoever grabs it. CPython releases it in two situations.

**On a timer.** Since Python 3.2, a thread that holds the GIL while others are waiting is asked to drop it after a <Term w="switch interval">How long a thread may hold the GIL while another thread wants it before being asked to give it up. Default 5 ms; see sys.getswitchinterval().</Term> of 5 ms (`sys.getswitchinterval()` returns `0.005`). This is what gives you concurrency between CPU-bound threads: they share one core's worth of Python, fairly.

**Around anything slow that doesn't touch Python objects.** C code inside CPython and inside extension libraries can explicitly release the GIL before doing a long operation, and take it back after. This is the part that makes Python threads useful in practice. Things that release it:

- Blocking I/O: `socket.recv`, `requests.get` (underneath), file reads and writes, `subprocess` waits.
- `time.sleep`.
- `hashlib` on large buffers (CPython releases it for inputs over about 2 KB), `zlib` compression.
- Most heavy NumPy operations (large array math, matrix multiplies that call into BLAS) and PyTorch ops, which run in C++ or on the GPU.

### Why does the GIL exist?

Because of how CPython frees memory. In the last lesson you saw every Python object on the heap carries a header. One field of that header is a <Term w="reference count">A counter in every CPython object of how many references point to it. When it drops to 0 the object is freed immediately.</Term>. Every time you assign a variable, put an object in a list, or pass it to a function, its count goes up; every time a reference goes away, it goes down. Hitting zero frees the object.

That counter is touched constantly, by every line of Python. If two threads do `count = count + 1` on the same object's counter at the same time, one update can be lost (you'll see exactly how in the next section). A lost decrement leaks memory forever. A lost increment frees an object while someone is still using it, and the program reads garbage or crashes.

There were two ways to make that safe. Put a small lock (or an <Term w="atomic operation">A CPU instruction that reads and modifies a memory location as one indivisible step that no other core can interrupt halfway. Safe, but slower than a plain increment.</Term>) on every refcount change, which slows down every single Python program, including the vast majority that never use threads. Or put one lock around the whole interpreter. Guido van Rossum chose the second in the early 1990s, when nearly every computer had one core and parallelism was irrelevant. It had a huge side benefit: C extension authors could write code assuming nobody else was touching Python objects at the same time. A lot of the ecosystem (NumPy among it) grew up on that assumption.

People have tried to remove it many times. Larry Hastings' "Gilectomy" (around 2016) replaced the GIL with fine-grained locks and got correct multi-threaded Python that was much slower single-threaded. That trade-off is the whole story: removing the GIL is easy, removing it *without making everyone else slower and breaking every C extension* is the hard part.

### Free-threaded Python

That hard part is now largely done. <Term w="PEP 703">"Making the Global Interpreter Lock Optional in CPython", by Sam Gross, accepted in 2023. Describes a CPython build with no GIL.</Term> proposed a build of CPython with no GIL, using tricks to keep single-thread speed tolerable: biased reference counting (the thread that owns an object updates its count cheaply; other threads use slower atomic updates), "immortal" objects whose counts never change (like `None` and small ints), and per-object locks inside lists and dicts.

The status, as of late 2026, as best I can state it (check the current Python docs, this is moving):

- **Python 3.13** (October 2024) shipped the free-threaded build as **experimental**. It's a separate binary, usually called `python3.13t`.
- **Python 3.14** (October 2025), under PEP 779, made the free-threaded build **officially supported**, but still **optional and not the default**. The normal `python3` you install still has a GIL. Single-threaded code runs somewhat slower on the free-threaded build (the docs quoted roughly 5-10% for 3.14).
- C extensions have to be rebuilt and marked as safe without the GIL. If you import one that isn't, the interpreter can turn the GIL back on for the whole process. `sys._is_gil_enabled()` tells you which you got.

You'll run the free-threaded build in the Build section, and it is the cleanest possible demonstration that the GIL, not threads, was the bottleneck.

### Race conditions, and locks

Free-threaded or not, threads share memory, and shared memory has a classic failure. Take `counter += 1`. It looks like one step. It's three:

1. **Read** `counter` from the heap into a register (in Python: onto the interpreter's stack).
2. **Add** 1 to it.
3. **Write** the result back to `counter`.

If thread A reads 41, then thread B reads 41 before A writes, both compute 42, and both write 42. Two increments, one effect. That is a <Term w="race condition">A bug where the result depends on the exact timing or interleaving of threads. Usually rare, which is why it's hard to catch.</Term>: the answer depends on who got there first. Try to find the bad order yourself, then turn the lock on and try again.

</Figure>

The fix is a <Term w="lock">Also called a mutex (mutual exclusion). An object only one thread can hold at a time. Others that try to acquire it block until it is released.</Term>. Wrap the read-add-write in `with lock:` and it becomes a <Term w="critical section">A stretch of code that must not be run by two threads at once, because it reads and then writes shared state.</Term>: only one thread inside at a time. The cost is that threads now wait for each other there, so you keep critical sections short.

Two notes that will matter when you run this for real.

**The GIL is not a lock for your code.** It protects the interpreter's insides, not your logic. It can be handed to another thread between your read and your write. In recent CPython versions (3.10 onward), the interpreter only offers to switch threads at certain points, such as the jump back to the top of a loop, so a bare `counter += 1` in a tight loop happens to almost never race on a normal build. That is an accident of implementation, not a promise, and it disappears entirely on the free-threaded build. To see the race reliably on a normal build, you'll put something between the read and the write that releases the GIL, like `time.sleep(0)`.

**Processes don't have this problem by default**, because they don't share memory. Which brings us to the other way out.

### Processes: the other way around the GIL

Each Python process has its own interpreter and therefore its own GIL. Run 8 worker processes and you have 8 interpreters, each running Python on its own core, in true parallel. That's what `multiprocessing` and `ProcessPoolExecutor` do. The price is the wall between kitchens.

You pay twice.

**Startup.** A new process needs a new interpreter. There are three <Term w="start method">How multiprocessing creates a worker: fork (clone the parent), spawn (start a fresh python and re-import your module), or forkserver (fork from a clean helper process).</Term>s:

- `fork`: clone the parent process. Fast (well under a millisecond to tens of ms depending on how big the parent is), and the child starts with a copy of everything the parent had in memory. The kernel makes this cheap with <Term w="copy-on-write">Parent and child share the same physical memory pages after fork, and a page is only actually copied when one of them writes to it.</Term>. The catch: only the thread that called `fork` exists in the child. If another thread was holding a lock at that moment, the child inherits a locked lock that nobody will ever release. Deadlock.
- `spawn`: start a brand new `python` and have it import your main module. Safe, slow: on an M-series Mac a bare pool of workers takes around 60-90 ms to start in my test, and if your module imports `torch` at the top, every worker pays that import too, often a second or more.
- `forkserver`: start one clean helper process early, then fork workers from it. Safe and fairly fast.

The defaults differ by OS, which is why the same script behaves differently on your Mac and the Spark. macOS has defaulted to `spawn` since Python 3.8. Linux defaulted to `fork` for decades, and Python 3.14 changed the Linux default to `forkserver`. Verify on each machine with `multiprocessing.get_start_method()`, and check the `multiprocessing` docs for your version.

**Communication.** Workers can't see the parent's heap, so every argument and every return value is serialised with <Term w="pickle">Python's built-in way of turning an object into bytes and back. Works on most objects; costs time proportional to the object's size and complexity.</Term>, written into a <Term w="pipe">A one-way byte channel the kernel provides between processes. One side writes bytes, the other reads them.</Term>, read, and unpickled. For small arguments (two integers saying which chunk to process) this is nothing. For a million-element list per task, it can cost more than the work.

The escape hatch is <Term w="shared memory">A region of physical RAM that the kernel maps into several processes' address spaces at once, so they read and write the same bytes with no copying.</Term>: `multiprocessing.shared_memory`, or a NumPy array backed by it, or PyTorch's `tensor.share_memory_()`. The bytes live in one place and every process sees them. You're back to sharing, so you're back to needing locks if anyone writes.

### Where this shows up in ML

**`DataLoader(num_workers=8)` uses processes**, not threads. Each worker is a separate Python process running your `Dataset.__getitem__`: decoding images, tokenizing text, augmenting. That's CPU-bound pure-Python-ish work, exactly what the GIL would serialise. The batches come back as tensors placed in shared memory, so only a small handle is pickled, not the data. (When `pin_memory=True`, a *thread* in the main process copies batches into page-locked memory, and that's fine because the copy happens in C with the GIL released.)

A real-world bite from the stack-and-heap lesson: under `fork`, workers share the parent's dataset via copy-on-write. But merely *reading* a Python object changes its reference count, which writes to the object's header, which forces the kernel to copy that page. A dataset stored as a giant Python list of strings slowly gets copied into every worker, and memory use climbs with `num_workers`. Storing it as NumPy arrays (one object, no per-item refcounts) avoids that.

**The tokenizers warning.** If you've seen `huggingface/tokenizers: The current process just got forked, after parallelism has already been used. Disabling parallelism to avoid deadlocks...`, that's the fork-with-threads problem from above. The fast tokenizer runs its own thread pool (in Rust, outside the GIL). When the `DataLoader` forks workers after that pool started, the library turns its parallelism off in the children to avoid inheriting a locked lock. Set `TOKENIZERS_PARALLELISM=false` to choose explicitly, or avoid tokenizing in the parent before the fork.

**Why your training loop is fine with the GIL.** The Python in a training step mostly *launches* work: "multiply these tensors", "run this attention kernel". CUDA launches are asynchronous, the GPU runs the kernels while Python moves on to queue the next one, and the heavy CPU-side ops release the GIL. One Python thread can usually keep a GPU busy. When it can't (lots of tiny kernels, so Python's per-launch overhead dominates), the fixes are CUDA graphs and `torch.compile`, not more threads.

## Break It

**1. Fix (and then exaggerate) the load imbalance.** Change `chunks(k)` so the pool gets 64 small chunks instead of `k` big ones, but keep `k` workers. Rerun 4 and 8 processes. The speedup should move closer to the worker count, because a worker that finishes early just grabs the next chunk. Then go the other way: 1,000 tiny chunks of 2,000 numbers each. It gets slower again. Each task now costs a pickle round trip and a trip through the pool's queue, and those per-task costs start to matter. There's a sweet spot, and `ex.map(..., chunksize=...)` exists to help you find it.

**2. Make pickling cost more than the work.** Build 8 lists of 1,000,000 ints and `ex.map(sum, lists)` with 8 threads, 8 processes, and serially. Processes lose badly: on my Mac, threads took 24 ms, serial 26 ms, processes 88 ms. Summing a list is fast C code. Pickling 8 lists of a million ints (about 5 MB each), pushing them through a pipe and unpickling them is not. Lesson: processes win when the work per byte sent is large. Send indices or file paths, not data, and let workers load their own input.

**3. Forget the main guard.** Delete `if __name__ == "__main__":` from `cpu.py` and run the process version on your Mac. With `spawn`, each worker imports your file to find `count_primes`, which runs your top-level code, which tries to create another pool. Python stops this with a `RuntimeError` about "the current process has finished its bootstrapping phase". On Linux with plain `fork` the same script might seem to work, which is exactly how "works on the Spark, crashes on my Mac" bugs are born.

**4. Oversubscribe the cores.** Write a job where each task does a NumPy matrix multiply on a 2,000 × 2,000 matrix, and run 20 of them in a 20-process pool on the Spark. Then rerun with `OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1` set in the environment. The second run is likely faster. NumPy's matrix multiply calls BLAS, which starts its own threads (often one per core), so 20 processes times 20 BLAS threads is 400 threads fighting over 20 cores, and the scheduler spends time context switching instead of computing. This is why PyTorch's DataLoader workers and many job schedulers set thread counts to 1 per worker.

<details>
<summary>1. What's the difference between a process and a thread? What does each one own?</summary>

A process is a running program with its own private memory (address space), its own open files, a PID, and at least one thread. A thread is one line of execution inside a process: it owns only its stack, its registers and its position in the code. All threads in a process share the heap, globals, code and open files. So threads are cheap to create and can share data with no copying, but can corrupt shared data; processes are isolated and safe, but expensive to start and must copy data to communicate.

</details>

<details>
<summary>2. What is the GIL, why does CPython have it, and when is it released?</summary>

A single lock a thread must hold to run Python bytecode, so only one thread per process runs Python at a time. It exists mainly because every object has a reference count that changes constantly; one global lock made those updates safe without slowing down single-threaded code, and let C extensions assume nobody else is touching Python objects. It's released every 5 ms by default if another thread wants it, and around blocking or long C operations: socket and file I/O, `time.sleep`, large `hashlib` inputs, most heavy NumPy and PyTorch ops. Free-threaded CPython (PEP 703; experimental in 3.13, officially supported but optional in 3.14) removes it, at some single-thread cost.

</details>

<details>
<summary>3. Your preprocessing script is slow. When do you reach for threads, processes, or async?</summary>

First find out what it's slow *at*: watch `top` or profile. If one core is pegged running Python code (tokenizing, parsing, regex, cleaning text), it's CPU-bound: use processes (`ProcessPoolExecutor`, or `DataLoader` workers), give each worker a chunk index or a file path rather than the data, and keep chunks big enough that pickling is negligible. If the heavy work is already in C that releases the GIL (NumPy, hashlib on big buffers, a Rust tokenizer's batch call), threads may be enough and avoid the copying. If it's mostly waiting (downloading, calling an API, reading from S3), it's I/O-bound: threads work well up to hundreds of concurrent requests; for thousands, async is cheaper, because each waiting request costs a small object instead of a whole thread. And if it's both, combine: processes for compute, threads or async inside for the waiting.

</details>

<details>
<summary>4. A CPU-bound pure-Python job takes 60 s on one core. What's the best case on the Spark with 20 processes, and why won't you hit it?</summary>

The ideal is 60 / 20 = 3 s. You won't get there because: (a) half the Spark's cores are efficiency cores, slower than the other half, so the 20 workers don't finish together; (b) the work might not split evenly, and the pool waits for the slowest chunk; (c) starting 20 processes and pickling arguments and results costs real time, more under `spawn` or with heavy imports; (d) any serial part of the program (reading the input, merging results) doesn't speed up at all, which is Amdahl's law: if 10% is serial, you can never beat 10x; (e) if the workers stream through lots of memory, they compete for the same memory bandwidth. A realistic answer is "somewhere around 4-6 s, and I'd measure the scaling curve to see where it bends".

</details>

<details>
<summary>5. Why does PyTorch's DataLoader use processes, yet a training loop with one Python thread keeps the GPU busy?</summary>

Data loading runs your Python code (`__getitem__`: decode, tokenize, augment) and is CPU-bound, so threads would be serialised by the GIL; separate processes each have their own GIL and run in parallel, and they hand back batches through shared memory so the tensors aren't copied through a pipe. The training loop is different: Python just launches GPU kernels, which run asynchronously while Python queues the next ones, and heavy CPU-side ops release the GIL. The GIL only hurts when Python itself is the thing doing the work.

</details>

## Connections

This lesson leans on [Where do my variables live?](/lessons/stack-and-heap/): threads are "one address space, many stacks", and the GIL exists because of the refcount in every heap object's header. The context-switch costs only make sense next to [How slow is slow?](/lessons/latency-numbers/).

It sets up [Waiting vs working](/lessons/waiting-vs-working/), with a question you should now be able to feel. Threads are a fine way to wait: each blocked thread costs no CPU, and the GIL doesn't care. But each one still costs a stack (Linux reserves 8 MB of address space for one by default, though only the pages it touches use real RAM), a kernel record, a turn in the scheduler, and a context switch every time it wakes up. Fifty threads waiting on fifty requests is easy. Your LLM app needs to wait on 10,000 slow model calls at once. Is 10,000 threads really the best way to wait, or is there something much cheaper?

Later, [Why ~17 tokens per second?](/lessons/bandwidth-bound/) explains reason (e) in question 4: why adding cores stops helping once every core is waiting on the same memory.
