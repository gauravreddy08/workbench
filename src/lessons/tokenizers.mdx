Before a language model reads a single word, a small program chops your text into pieces and swaps each piece for a number from a fixed list, because numbers are all the model can take in. That program is the tokenizer, and its pieces, usually a word or part of a word, are tokens.

Almost everything you count in this field is counted in those pieces. Fireworks, the service you are benchmarking your inference server against, bills per token, and your own server's speed is measured in tokens per second. Your cross-encoder can only read so many tokens of a page before it has to cut the rest off, and an agent's memory fills up token by token. When a model can't count the letters in a word, or mangles a long number, the tokenizer is usually the first suspect.

This is the first step of the model you already built in GPT-2: the IDs that went into its first layer came from here. It explains a line item in [How much memory does a model need?](/lessons/memory-math/), where the size of that fixed list turns out to be a surprising share of a small model, and it sets up [Train a small LM, end to end](/lessons/tiny-lm/), where you will train your own tokenizer before you train the model.

## The Problem

You have built GPT-2 from scratch. The first line of your model was `nn.Embedding(50257, 768)`. Where did 50,257 come from? You probably took it from the paper and moved on, because the model starts at token IDs and the tokenizer was somebody else's library.

Here is what that library decides for you. Paste this into a terminal with `tiktoken` installed:

```python
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")   # GPT-4's tokenizer
print(enc.encode(" strawberry"))              # [73700]
print(enc.encode("strawberry"))               # [496, 675, 15717]
```

The same word is one token with a space in front of it and three tokens without. The model never sees the letters s-t-r-a-w-b-e-r-r-y. It sees the number 73700, an ID with no letters inside it. Then people ask it how many r's are in strawberry and are surprised when it guesses.

Now the part that touches you directly. I took Article 1 of the Universal Declaration of Human Rights, in English, Hindi and Telugu, and counted tokens. In English it is 33 tokens for GPT-2, GPT-4 and GPT-4o alike. In Telugu it is 429 tokens for GPT-2, 279 for GPT-4, 78 for GPT-4o. Same meaning. If you paid per token, a Telugu speaker using GPT-4 paid about eight times what you paid, and got an eighth of the context window to work with.

Cost, context length, spelling, arithmetic, fairness across languages, even a few famous bugs where a model goes haywire on one specific word: all of them come from one small, unglamorous preprocessing step. Let's open it up.

<Origin year="1994 / 2016" title="A compression trick, rescued for translation">

In February 1994, Philip Gage published "A New Algorithm for Data Compression" in *The C Users Journal*. The idea fit in a paragraph: find the most common pair of adjacent bytes in a file, replace every occurrence with a byte value the file doesn't use, write down the substitution, and repeat until no pair is common enough to be worth it. He called it byte pair encoding. It was simple and fast to decompress, and then, like most compression schemes, it was mostly forgotten.

Twenty years later, neural machine translation had a vocabulary problem. Models picked the 30,000 to 50,000 most common words and mapped everything else to a single "unknown" symbol. Names, rare words and compounds (German loves compounds) all came out as unknown, so the translator literally could not translate them. In 2015 Rico Sennrich, Barry Haddow and Alexandra Birch at Edinburgh posted "Neural Machine Translation of Rare Words with Subword Units" (published at ACL 2016). They took Gage's loop and ran it on characters inside words instead of bytes in a file. Frequent words ended up as one symbol, rare words as a few familiar pieces, and nothing was ever unknown. In 2019, GPT-2 moved the same loop back down to raw bytes, which is where nearly every large model's tokenizer lives today.

</Origin>

## The Idea

### A token is an ID for a chunk of text

A neural network only eats numbers. To feed it text you need two things: a way to cut the text into pieces, and a fixed list that gives every possible piece a number. The piece is a <Term w="token">One chunk of text that the model treats as a single unit, and the integer ID that stands for it. Could be a letter, a word, part of a word, a space, or a few raw bytes.</Term>. The fixed list is the <Term w="vocabulary">The complete, fixed list of tokens a model knows, each with an ID from 0 to V-1. Its size V is decided before training and baked into the model's first and last layers.</Term>. The program that does the cutting and the numbering, in both directions, is the <Term w="tokenizer">The program that turns text into a list of token IDs (encoding) and token IDs back into text (decoding). It's trained separately from the model, before the model exists.</Term>.

Each ID then picks a row from the embedding table you built in GPT-2: a learned vector of 768 numbers. That is the only thing the model ever knows about the token. If the token is " strawberry", the model knows one vector. It doesn't know that vector was spelled with three r's unless it learned that fact from seeing the word spelled out somewhere in training.

So the real question is: where should the cuts go?

### Why not letters? Why not words?

Try the two obvious answers.

**Letters.** The vocabulary is tiny (a few hundred symbols covers most of the world's alphabets, if you're careful) and nothing is ever unknown. But sequences get long. English averages a bit under 4 characters per GPT-4 token on typical prose (you'll measure it), so a character-level model sees each text as roughly 4 times as many positions. Your context window holds 4 times less text. Every generated letter costs a full forward pass, so generation is about 4 times slower. And attention compares every position with every other position, so its cost grows with the square of the length: 4 times longer is about 16 times more attention work. The model also spends its capacity relearning, over and over, that t-h-e is a word.

**Words.** Sequences are short, and each token carries a whole meaning. But how many words are there? I counted the distinct words in the prose of this site's own lessons, about 1.3 MB of text: 9,538 different words, and 3,252 of them appeared exactly once. Count only the first half of the text and you get 6,776, so the list was still growing fast when the text ran out. Real web text has every name, typo, number, URL, hashtag, and every form of every word ("tokenize", "tokenizes", "tokenizing", "tokenizer", "tokenizers"). A word vocabulary that covers it has millions of entries, and each one needs its own row in the embedding table, trained from however few times that word appeared. Whatever doesn't make the list becomes an <Term w="unknown token">A single placeholder, often written [UNK], used for any piece of text that isn't in the vocabulary. Its meaning is lost: every unknown word maps to the same vector.</Term>, and its meaning is gone.

**Subwords** are the compromise. Keep common words whole (" are", " useful"), and break rare words into pieces you've seen many times ("Token" + "izers"). The sequence stays short for normal text, the vocabulary stays a manageable size, and any word can be built from parts. The question becomes how to choose the pieces, and BPE's answer is: let the data decide, by merging whatever appears together most often.

But before merging anything, we need to decide what the smallest piece is. Letters sound natural. They are a trap.

### Bytes, and why "letters" is the wrong floor

Text in a computer is stored as numbers. The international standard, <Term w="Unicode">The standard that gives every character in every writing system a number, called a code point, written like U+0C05 (Telugu letter A). About 150,000 characters are assigned so far, including emoji.</Term>, gives every character a number called a code point. "a" is U+0061. Telugu "అ" is U+0C05. 😀 is U+1F600.

Code points go up to about 1.1 million, so they don't fit in one byte. The standard way to store them as bytes is <Term w="UTF-8">The way almost all text on the web and on disk is stored: each Unicode character becomes 1 to 4 bytes. Plain English letters are 1 byte each, so ASCII text is already valid UTF-8.</Term>, which uses a clever variable-length scheme: 1 byte for plain English letters, 2 for most accented Latin, Greek, Cyrillic, Arabic and Hebrew letters, 3 for most other scripts (Hindi, Telugu, Chinese, Japanese), and 4 for emoji and rarer characters.

Now the key move. If the smallest unit is a character, your base vocabulary needs every Unicode character (about 150,000), and a character you didn't include is unknown. If the smallest unit is a **byte**, the base vocabulary is exactly 256 entries, the values 0 to 255, and every possible string, in any language, any emoji, even corrupt binary junk, is some sequence of bytes. Nothing can ever be unknown. This is <Term w="byte-level BPE">BPE that starts from the 256 possible byte values instead of from characters. Introduced for GPT-2 (2019). Any input can be encoded, so there is no unknown token.</Term>, and it's what GPT-2, GPT-4, Llama 3, Qwen and most other recent models use.

The cost: before merges, a byte-level tokenizer sees "తెలుగు" as 18 tokens. Everything now depends on which merges it learned.

### BPE training: count pairs, merge the winner, repeat

Here's the whole algorithm.

1. Turn the training text into a list of byte values. These are your starting tokens, IDs 0 to 255.
2. Count every adjacent pair of tokens in the text. (In "hello", the pairs are h-e, e-l, l-l, l-o.)
3. Take the most frequent pair. Give it a new ID, 256. Replace every occurrence of that pair in the text with 256. Write down the rule: (a, b) → 256. That rule is a <Term w="merge">One learned rule of the form "when token a is followed by token b, replace both with the new token c". A BPE tokenizer is nothing more than 256 byte tokens plus an ordered list of merges.</Term>.
4. Go back to step 2. Now the new token can itself be part of a pair. Stop when you've added as many tokens as you want.

The vocabulary size is a knob you choose: 256 + number of merges. GPT-2 did 50,000 merges (plus one special token, which is how you get 50,257). The output of training is just the ordered list of merges. That's the tokenizer.

### Encoding: replay the merges in the order they were learned

Training happens once, on a big corpus. Encoding happens every time someone sends text. To encode a new string:

1. Turn it into bytes.
2. Look at every adjacent pair. Among the pairs that have a merge rule, find the one whose rule was learned **earliest** (lowest merge number).
3. Apply that merge everywhere in the string. Repeat until no adjacent pair has a rule.

Why earliest, not "most frequent in this string"? Because later merges were learned on text where the earlier merges had already been applied. Merge #500 might be (" th", "ink"); the token " th" only exists because merge #12 created it. Replaying in training order reproduces exactly the pieces the model saw during training. Pick a different order and you'll still decode back to the right text, but you'll produce token sequences the model has never seen, and it will behave worse. (You'll make this mistake on purpose in Break It.)

Decoding is the easy direction: look up each ID's bytes, concatenate, and decode the bytes as UTF-8. Keep that "concatenate first, decode after" in mind. It comes back to bite in Break It.

### Pre-tokenization: fences that merges can't cross

If you run BPE on raw text with no boundaries, it will happily learn merges that span words. I tried it on 150 KB of this site's prose: within 300 merges it had learned tokens like "e the ", "of the ", "is the ", "s. " and ".\n- **". That wastes vocabulary on accidental phrases, and it means "dog." "dog!" "dog?" and "dog " all end up as different, unrelated tokens.

So before BPE runs, text is chopped into chunks by a regular expression, and merges only happen inside a chunk. This is <Term w="pre-tokenization">A first pass that splits text into chunks (roughly: words, numbers, punctuation runs, whitespace) with a regex, before BPE runs. Merges are never allowed to cross a chunk boundary.</Term>. GPT-2's pattern is:

```text
's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+
```

Read it as alternatives, tried left to right: common English contractions; an optional space then a run of letters (`\p{L}` is "any letter in any script"); an optional space then a run of digits; an optional space then a run of punctuation; then whitespace. The `\s+(?!\S)` part grabs a run of spaces but leaves the last one to attach to the next word. That's why the space lives at the *front* of a word in GPT-style tokenizers: " strawberry" is one chunk, and "strawberry" at the start of a line is a different chunk, which is exactly the one-token-vs-three-tokens surprise from the start of this lesson.

GPT-4's `cl100k_base` pattern made a few deliberate changes. Contractions are case-insensitive. Runs of digits are cut into groups of **at most three** (`\p{N}{1,3}`). Newlines get their own handling, so code indentation compresses. Here's what the two patterns do to one line, measured with `tiktoken`'s own patterns:

```text
input: "Hello world, it's 2026!!   x=1234567\n    return"
gpt2:   'Hello' ' world' ',' ' it' "'s" ' 2026' '!!' '  ' ' x' '=' '1234567' '\n   ' ' return'
cl100k: 'Hello' ' world' ',' ' it' "'s" ' ' '202' '6' '!!' '  ' ' x' '=' '123' '456' '7' '\n' '   ' ' return'
```

Small regex choices, big consequences. Hold on to the digit grouping; it explains a lot about arithmetic.

### The other families: WordPiece, SentencePiece, Unigram

You'll meet two other names. Briefly:

- <Term w="WordPiece">Google's subword method (Schuster and Nakajima, 2012), used by BERT. Like BPE, but picks the merge that most increases the likelihood of the training data rather than the most frequent pair. Pieces that continue a word are marked with ##.</Term> is BERT's tokenizer. Encoding is greedy longest-match: take the longest vocabulary entry that matches the start of the word, then continue. Continuation pieces get a `##` prefix. BERT's version works on characters, not bytes, so it has an `[UNK]`. I ran Telugu through `bert-base-uncased`: almost every word came back as `[UNK]`. That's 17 tokens for the sentence, which looks cheap until you realize the meaning was thrown away.
- <Term w="SentencePiece">A tokenizer library from Google (Kudo and Richardson, 2018) that treats the input as a raw stream, including spaces, so it needs no language-specific word splitting. It can train either BPE or Unigram models. Used by T5, Llama 1 and 2, Gemma.</Term> is a library, not an algorithm. It treats the space as an ordinary symbol (shown as ▁) so it works on languages that don't put spaces between words, like Japanese and Chinese. It can train BPE or a <Term w="Unigram">A subword method (Kudo, 2018) that works backwards from BPE: start with a huge candidate vocabulary and repeatedly delete the pieces whose removal hurts the likelihood of the training text least. Encoding picks the most probable split.</Term> model, and it can fall back to bytes for characters it hasn't seen ("byte fallback"), which Llama 2 used.

The family differences matter less than the shared idea: frequent things get short codes. BPE byte-level won mostly because it's simple, fast and can't fail on any input.

### How big should the vocabulary be?

Vocabulary size V is a trade between two costs.

**More tokens in the vocabulary means shorter sequences.** More merges, more whole words and common phrases, fewer tokens per sentence. Shorter sequences mean more text fits in the context window, fewer forward passes to generate a reply, less attention work, and a smaller <Term w="KV cache">The memory where a model keeps the attention keys and values of every past token so it doesn't recompute them. It grows with every token in the context.</Term> (see [the KV cache lesson](/lessons/kv-cache/)).

**More tokens in the vocabulary means bigger matrices.** The embedding table has V rows of d numbers. The output layer, which scores every possible next token, is another d × V matrix (unless the model ties them together), and computing a probability for every vocabulary entry happens at every single position. And each extra token is rarer, so its row gets fewer training updates.

From the models' published config files (check `config.json` on Hugging Face yourself):

| Model | Vocab V | Width d | Embedding V × d | Share of params |
| --- | --- | --- | --- | --- |
| GPT-2 small | 50,257 | 768 | 38.6M | ~31% of 124M (tied in/out) |
| Qwen2.5-0.5B | 151,936 | 896 | 136M | ~28% of ~494M (tied) |
| Llama 3 8B | 128,256 | 4,096 | 525M, ×2 untied = 1.05B | ~13% of ~8B |

For a small model, the vocabulary is a large share of everything it has. For a big model it's a modest tax, and the sequence-length savings pay for it many times over: Meta reported that Llama 3's 128K tokenizer (100K tokens from `tiktoken` plus 28K added for other languages) encodes English text in about 15% fewer tokens than Llama 2's 32K one. That's why vocabularies grew: GPT-2 50K, Llama 2 32K, GPT-4 100K, Llama 3 128K, Qwen2.5 152K, GPT-4o 200K, Gemma 256K. As models got wider, the per-token matrix cost shrank relative to the model, while serving many languages and long contexts made every saved token worth more.

### What tokenization does to models

Now the payoff: a list of strange model behaviors that stop being strange once you think in tokens.

**Cost and context are counted in tokens.** API prices, rate limits and context windows are all per token, not per word or character. For English with a GPT-4-class tokenizer, the rule of thumb is about 4 characters per token, or roughly 0.75 words. For code it's lower; for most non-Latin scripts it's much lower.

**Spelling and letter counting.** " strawberry" is ID 73700 in GPT-4's tokenizer. To count its r's, the model has to have memorized what's inside that ID, from rare places in training where words get spelled out. Ask it to spell the word with spaces first ("s t r a w b e r r y") and every letter becomes its own token, and the task gets far easier. Modern models often answer correctly anyway, because they've been trained on this exact meme and on spelling things out step by step, but the underlying weakness is still there. You'll reproduce it on a small model.

**Arithmetic on long numbers.** GPT-2 split "1234567890" as 123 | 45 | 678 | 90; a slightly different number gets cut in completely different places, so the model can't learn a consistent "this column is the hundreds" structure. GPT-4's three-digit groups (123 | 456 | 789 | 0) are consistent from the left, but addition carries from the right, so the groups still don't line up with how you'd add. Llama 1 and 2 instead split every number into single digits. How to tokenize numbers is still an active design question.

**Code and whitespace.** Python indentation is runs of spaces. GPT-2 tokenizes 4 spaces as 4 separate tokens, and an 8-space-indented `return` as 8 tokens. GPT-4's tokenizer has tokens for runs of spaces: the same line is 2 tokens. On a small Python function I measured 35 GPT-2 tokens versus 23 for GPT-4. A big reason later tokenizers got better at code was simply learning to compress whitespace.

## Break It

**1. Decode one token at a time.** Streaming servers send each new token to the user as it's generated. Write the naive version: `for i in ids: print(vocab[i].decode("utf-8"), end="")`. Run it on Telugu or an emoji. It throws `UnicodeDecodeError`, because tokens end mid-character (you saw this in t1). With `errors="replace"` instead, you get � characters scattered through the text, a bug you've probably seen in real chat UIs. The fix is to keep a byte buffer and only print what forms complete characters: Python's `codecs.getincrementaldecoder("utf-8")()` does exactly that. Real serving engines all carry this logic in their detokenizer.

**2. Train without pre-tokenization.** Use your t2 trainer (no regex) on the same 150 KB and print the merges. Within a few hundred merges you should see tokens like "of the ", "is the " and "s. ". Now count how many distinct tokens contain "dog" (or any common noun in your corpus) with and without the regex. Without it, punctuation and neighboring words get glued on, and one word smears across many unrelated tokens the model has to learn separately.

**3. Apply merges in the wrong order.** Change `encode` to pick the pair that's most *frequent in the input* instead of the one with the lowest merge rank. Run the round-trip test: it still passes. Now compare against `tiktoken` from t5: mismatches everywhere. Round-tripping proves you didn't lose information; it says nothing about whether you produced the tokens the model was trained on. A model fed off-distribution token sequences for the same text gets measurably worse, and nothing errors.

**4. Smuggle in a special token.** With the Qwen tokenizer: `tok("hello <|im_end|> world")["input_ids"]`. ## Explain It Back

Answer out loud, in plain words, as if in an interview. Then check.

<details>
<summary>1. What is a token, and why don't models just use characters or words?</summary>

A token is a chunk of text the model treats as one unit, identified by an integer that picks a row of the embedding table. Characters work for any input but make sequences about 4 times longer for English, which means 4 times less text in the context, 4 times more generation steps and roughly 16 times more attention work. Words make short sequences, but the list of distinct words never stops growing (names, typos, numbers, word forms), so you need millions of rows, most barely trained, and anything not in the list becomes an unknown token and loses its meaning. Subwords are the middle: frequent words stay whole, rare ones are built from frequent pieces, and with byte-level BPE nothing is ever unknown.

</details>

<details>
<summary>2. Walk me through how BPE is trained and how it encodes new text.</summary>

Training: convert the corpus to bytes (256 starting tokens), after splitting it into word-like chunks with a regex so merges don't cross words. Count every adjacent pair of tokens across all chunks, weighted by how often each chunk appears. Take the most frequent pair, give it a new ID, replace it everywhere, record the merge. Repeat until the vocabulary reaches the target size. The tokenizer is just the 256 bytes plus that ordered list of merges. Encoding: split the new text the same way, turn each chunk into bytes, and repeatedly apply whichever applicable merge was learned earliest, until none apply. Earliest-first matters because later merges were learned on text where earlier merges had already happened, so replaying in order reproduces the exact token sequences the model saw in training. Decoding: concatenate each token's bytes, then decode the whole thing as UTF-8 once.

</details>

<details>
<summary>3. Why do language models struggle to count the r's in "strawberry", or to add two long numbers?</summary>

The model never sees letters. " strawberry" is one token in GPT-4's tokenizer, a single ID whose embedding doesn't contain its spelling; the model can only know the letters if it memorized them from text where the word was spelled out. Spacing the letters out turns each into its own token and the task becomes easy. For numbers, tokenizers chop digits into chunks: GPT-2 did it inconsistently (123|45|678|90), GPT-4 uses groups of three from the left, but carrying in addition goes from the right, so the chunks don't line up with place value. Some models (Llama 1 and 2, Qwen) split every digit separately to make the structure consistent.

</details>

<details>
<summary>4. You're designing a new model. Vocab of 32K or 256K? How does that choice scale?</summary>

A bigger vocab means fewer tokens per text: more text per context window, fewer decoding steps per reply, a smaller KV cache per document, and much better treatment of non-English languages and code if the tokenizer's training data includes them. The costs are the embedding and output matrices, each V × d: for Llama 3 8B, 128,256 × 4,096 is about 525M parameters each, about 1.05B of the 8B total since they're untied; at every position the output layer scores all V tokens; and each extra token is rarer, so its embedding gets fewer updates (the extreme case is a glitch token). For a small model, a 256K vocab could be most of its parameters, so 32K-64K is sensible. For a big model the matrices are a small share and sequence savings dominate, which is why frontier vocabularies grew to 100K-256K. I'd decide by measuring tokens per byte on the target data mix at several vocab sizes and comparing that to the parameter cost.

</details>

<details>
<summary>5. Why does the same request cost more in Telugu than in English, and what could a model provider do about it?</summary>

A BPE tokenizer is a compression scheme trained on a particular text mix. If that mix is mostly English, it learns long merges for English and few or none for Telugu. Telugu also starts at 3 bytes per code point in UTF-8, and its vowel signs are separate code points. So with GPT-2 every Telugu byte stayed its own token (429 tokens for UDHR Article 1 against 33 in English), and GPT-4's tokenizer still used about 8.5 times as many. The user pays more, gets less context, waits longer, and often gets worse answers. Fixes: train the tokenizer on a more balanced language mix and give it a larger vocab (GPT-4o's 200K vocab brings Telugu to about 2.4 times English; Llama 3 added 28K tokens for other languages), or price per character instead of per token.

</details>

<details>
<summary>6. What was SolidGoldMagikarp?</summary>

A glitch token. GPT-2/GPT-3's tokenizer was trained on data with lots of Reddit, including r/counting, where a few usernames appeared thousands of times, so " SolidGoldMagikarp" became a single token. The model itself was trained on differently filtered data where that token almost never appeared, so its embedding stayed close to its random starting point. When prompted with it, the model behaved erratically: refusing, substituting other words, or producing nonsense. Lesson: the tokenizer and the model should be trained on the same data distribution, and it's worth checking for vocabulary entries that the model's training data barely contains.

</details>
